title: How the connect flow works

---

Connecting a domain is a short pipeline on top of the
[connection lifecycle](/docs/concepts/connections):

1. [**Create a connection**](/docs/connect-flow/create-a-connection):
   `POST /v1/connections` starts the process and returns the connection plus its
   authoritative desired DNS records.
2. [**Apply the records**](/docs/connect-flow/verify-and-go-live): pick a
   **rail** (below) to get the records into the customer's DNS.
3. **Go live**: the propagation poller promotes the connection to `live` once
   every desired record resolves; the edge then issues TLS on the next handshake
   and you receive a `connection.live` [webhook](/docs/webhooks/overview).
4. [**Offboarding**](/docs/connect-flow/offboarding): how a domain is removed.

## The ways to connect [#the-four-rails]

A domain reaches `live` through one of six ways, by the names the console, the
widget and these docs share (see the [glossary](/docs/concepts/glossary#ways-to-connect)).
Five of them are rails that write the domain's records. The sixth, DNS hosting,
moves the domain's DNS to CustomDomain™, which then writes every record. The best
way that can finish for the domain is chosen from `POST /v1/domains:check` (its
`rails` and `recommended_rail`); the widget drives them automatically.

| Way | Rail | Endpoint | How it applies records |
| --- | --- | --- | --- |
| **Sign in with** your provider (OAuth, flagship, "Mode C") | `oauth` | `POST /v1/connections/{id}/oauth:start` → `GET /v1/connect/oauth/callback` | Customer authorizes with their DNS provider in a popup; the callback writes records with the access token, used **once** unless the sign-in is kept as a [managed sign-in grant](/docs/connect-flow/managed-connections#managed-sign-in-grants). |
| **One-click setup** (sync + async) | `domain_connect` | `POST /v1/connections/{id}/domainconnect:start` | Returns a provider-hosted apply URL; the provider applies a signed template. No server-to-server token. |
| **Secure sign-in** | `cloud_browser` | `POST /v1/connections/{id}/browser:start` | For a provider with no sign-in a third party can use (GoDaddy, Namecheap, IONOS and more). The customer signs in to the provider in a temporary browser. Where the provider allows it, a lasting API key is made there and kept as a [provider account](/docs/connect-flow/provider-accounts#keys-made-at-a-secure-sign-in), and the records are written and kept correct through the provider's API; otherwise they are added on the provider's own DNS page once the customer approves them. A person is always there: the widget and the console start it, never an API key or an agent. Offered to selected workspaces for now. See [Secure sign-in](/docs/guides/secure-sign-in). |
| **API key** (BYO) | `api_key` | `POST /v1/connections/{id}/apply` | You pass a scoped provider token in the request; it writes the records **once** and is discarded afterwards. To keep a key, connect it as a [provider account](/docs/connect-flow/provider-accounts) (the console's [keep box](/docs/dns/provider-setup#remembering-a-key-optional) does this). |
| **Add the records** (manual) | `manual` | (none, just the record set) | Customer copies the records from `GET /v1/connections/{id}/records`; the poller waits for them to appear. |
| **DNS hosting** | `rails.nameservers` | `POST /v1/connections/{id}/managed-dns`, `POST /v1/connections/{id}/nameservers:migrate` | The domain's owner changes its nameservers once, where it was bought, to CustomDomain™'s. CustomDomain™ hosts the zone and writes every record, now and later. Offered only where your application turns DNS hosting on; the domain check says `offered`, `offered_first`, `recommended` or `unavailable`. See [Managed DNS](/docs/dns/managed-dns). |

The server's pick runs in this order: sign in, one-click setup, secure sign-in,
API key, then the records by hand. DNS hosting is offered beside them by the
application's setting, and the console and the widget follow what the check says
within the ways each can show (see
[Rail truth](/docs/concepts/ownership-and-setup-types#rail-truth-what-to-actually-tell-the-user)).

All six end the same way: the desired records land in DNS (for DNS hosting, in the
zone CustomDomain™ hosts once its nameservers answer), the connection moves
`pending → propagating → live`, and the edge serves the domain.

The check names its pick as `recommended_rail`, and the widget opens that way as
its one card, with the others as rows under **Other ways to connect** (**Add the
records**, and **DNS hosting** when `rails.nameservers` says the application
offers it). It follows the pick within what it can show: it has no API token way,
so a pick of `api_key` opens the secure sign-in where the check offers it and the
records otherwise, and a pick it cannot show gives way to the next one in the
check's own order. A sign-in the customer cancels, or that fails, keeps the card;
the records screen has a **Back** to it.

## Resuming an abandoned setup

A setup that was started but not finished isn't lost. In the console, the
Domains list shows **Finish setup** on any connection that isn't `live` yet.
It reopens the guided flow at the right step, rehydrated from the existing
connection. Programmatically, the same replay is safe because
[`POST /v1/connections` is idempotent](/docs/connect-flow/create-a-connection#idempotency)
per application + domain.

For the fastest path with real `curl`, see the
[API quick start](/docs/getting-started/api). To let customers drive the flow
themselves, embed [the widget](/docs/widget-sdk/overview). What each rail needs
operationally is covered in [DNS providers](/docs/dns/providers).
