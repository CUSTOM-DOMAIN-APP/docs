Domain forwarding turns a connected domain into a redirect instead of a proxied
origin. Say a customer wants `oldbrand.example`, or a bare apex, to send
visitors somewhere else. The edge answers the request with an **HTTP 301 Moved
Permanently** and never contacts an origin.

## What it does

There are two forms, both resolved on the edge's hot path right after the
[ask gate](/docs/connect-flow/verify-and-go-live) approves the host:

- **Redirect to a target URL.** The connection carries a redirect target; every
  request for the domain 301s to that URL. The incoming request's **path and
  query are preserved**, so `https://old.example/a/b?x=1` lands on
  `https://new.example.com/a/b?x=1`.
- **Apex → www.** For a bare apex host (e.g. `example.com`), the edge 301s to the
  `www.` counterpart (`https://www.example.com/…`), again preserving path + query.
  A request already on `www.` is proxied normally, so there is no redirect loop.

The 301 comes from the edge, so the customer's origin never sees the request. No
certificate is needed on the origin side for the old hostname. Only the edge
certificate is needed, and it is issued automatically once the domain is
[live](/docs/connect-flow/verify-and-go-live#watch-propagation--live).

## From the console

Open the domain, then its **Settings** tab ([a domain's
settings](/docs/getting-started/console#domain-settings)). **Forwarding** is a
field. Type an `https://` address and **Save**, or **Clear** to stop forwarding.
**www redirect**, for a root domain, is a switch with its own **Save**. After a
save, the tab says what it did. For the www redirect, that is whether we wrote
the `www` record for you or you add it where you manage DNS. The record is
shown, with a link to the **DNS** tab. Members, admins and owners can change
them. A viewer can read them.

## Turn it on at the edge with the API [#enabling-it-with-the-api-edge-served]

Forwarding is part of edge serving and is set on the connection. The redirect
target (`redirect_to`) and the apex to www flag (`www_redirect`) are attributes
of the connection. Change them with `PATCH /v1/connections/{id}` ([API
reference](/docs/api-reference/connections/updateConnection)). You can also use
`POST /v1/connections/{id}/power`, and `POST /v1/connections/{id}/power:repower`
to change a connection that already serves through the edge. Leaving out
`application_url` there keeps the current origin:

```bash
curl -X PATCH https://api.customdomain.ai/v1/connections/<ID> \
  -H "Authorization: Bearer $CUSTOMDOMAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "redirect_to": "https://new.example.com" }'
```

Send `"redirect_to": ""` to clear a redirect. The edge picks up the intent within one ask-cache TTL, with no
redeploy. When neither is set, the domain is proxied to its origin as usual. Edge serving is included on the Edge, Scale and
Enterprise plans; on Starter and Pro these calls return `402` with the code
`plan_upgrade_required`.

- **The plan.** `redirect_to` needs edge serving, which is included on the Edge,
  Scale and Enterprise plans. On Starter and Pro, setting or changing it returns
  `402` with the code `plan_upgrade_required`. Clearing one never does.
  `www_redirect` is on every plan, and so is `client_label`. Where the
  deployment has edge serving off, `redirect_to` returns `503`.
- **Who may call it.** An API key of a member, admin or owner, or a token with
  the `app` scope for a connection of its own application. A viewer's key, an
  end user's widget token (even on its own connection) and a delegated agent
  token are refused with `403`. The target of a redirect decides where a
  domain's visitors go, so the platform that owns the domain decides it.
- **The address is checked.** `redirect_to` must be a plain `https://` address of a public domain. `400
  invalid_request` names the reason when it is not `https` (`http:`, `javascript:`, `data:` and an address with no
  scheme are all refused), when it holds a user name or password (`https://acme.com@evil.example`), when it is an
  IP address or a name that cannot be reached from the internet (`localhost`, `.local`, `.internal`, `.test`),
  or when it holds spaces, backslashes or hidden characters. The port is read as a number and stored once:
  `:443` is dropped, and `:0443` is the same port, so it is the domain itself when it names the domain. A
  target that names the domain on port 80 is the domain itself too, as the edge reads it.
  `422 redirect_target_not_allowed` is a domain another CustomDomain™ workspace has connected or claimed,
  whether or not it is serving yet: two workspaces could forward to each other and neither could see the circle.
  A domain your own workspace serves is yours to forward to, whoever else has a pending or failed claim on it.
  `422 redirect_loop` is an address that would send a visit round in a circle: the domain itself, or a chain
  through the `www` redirect and your other forwards that comes back to a host it went through (taking a forward
  off a domain whose `www` redirect is on counts: the visit then goes to the `www` name), or a chain of
  more than 8 forwards in a row (the title then says "too many forwards"). The answer names only the domains you
  can see, your workspace's and, for an `app` token, its own application's; any other reads "another domain".
  If a check cannot read who owns the address's domain, the answer is `500` and nothing is stored. The same
  checks apply to `redirect_to` on `/power` and `/power:repower`. An address equal to the one already set is not
  checked again.
- **Two requests at once.** Redirect changes of one workspace are made one at a
  time. Each is checked against the domains as they are when its turn comes. So
  two changes made together cannot make a circle between them: the second
  answers `422 redirect_loop`. A change that waits too long for its turn answers
  `503` with the code `redirects_busy` and a `Retry-After` header, and changes
  nothing. Send it again. A request writes only the settings it changes. A value
  it sends back as it read it is not a change, so a setting another request has
  changed since is not undone. `DELETE /v1/connections/{id}/power` clears the
  forward and the root path access through the same checks. On a domain whose
  `www` redirect is on, taking the forward off is refused (`422 redirect_loop`)
  when `www` forwards back to the root. A domain that is being removed answers
  `409` to all of these, also when the removal starts while the change waits.
- **The www redirect and its record.** `www_redirect` is for a root domain only
  (`422 www_redirect_apex_only` for a subdomain). Turning it on adds a `www`
  record to the records the domain needs. A zone CustomDomain™ hosts is
  rewritten at once. A domain whose records were written through a connected
  provider account is rewritten when `move_rewrite` is on. For any other domain,
  the response has `customer_action_required: true`,
  `connection.records_outdated` is sent, and the person adds the record. The
  domain stays live meanwhile. Turning it off also stops the edge answering for
  `www.` on that domain, unless that name is a connection of its own.
- **Sandbox.** A Sandbox domain takes `client_label` only; the two redirects answer `403
  sandbox_not_allowed`.
- **The audit log.** Every change is recorded as `connection.updated`. It holds
  the before and after of the fields that changed, and the member or key that
  made it (`widget:<application id>` for an `app` token). A domain that is being
  removed answers `409`. The redirects are stored before the name. If only
  `client_label` cannot be written, the answer is `500`, but the redirect change
  is stored and recorded. Sending the same body again writes the name.

## The redirect template the provider writes [#the-redirect-template-provider-written]

When the domain runs on a provider that implements the one-click (Domain
Connect) protocol, forwarding can instead be written **at the provider**. The
`redirect` service template (`serviceName: "Forward this domain"`) declares a
single `REDIR301` record on the apex (`@`) whose target is the `redirectTarget`
variable:

```json
{ "type": "REDIR301", "host": "@", "target": "%redirectTarget%", "ttl": 3600 }
```

`REDIR301` is a pseudo-record native to the Domain Connect protocol, like
`SPFM`. The provider's forwarding feature, not our edge, issues the 301 to
`redirectTarget` and keeps the path and query. A companion `apex-www` template
covers the apex to www case the same way.

**Only the one-click (Domain Connect) rail can apply the `redirect` template.**
The OAuth and API-token rails **refuse** any template carrying a `REDIR301` or
`REDIR302` record, with `forwarding_not_supported`. A redirect is HTTP behavior,
not a DNS record, and a provider's DNS API has no way to write one. On those
rails, serve the redirect from the edge instead (the section above), or set
forwarding by hand in the provider's own control panel. The `apex-www` template
is not affected. It writes an apex `A` record and a `www` CNAME, which those
rails can apply, and the edge issues the apex to www redirect.

## Widget forwarding path

The widget applies forwarding through the ordinary one-click setup rail, using the same
`POST /v1/connections/{id}/domainconnect:start` call it uses for connection
records, but naming the `redirect` template and passing the destination as a
variable:

```bash
curl -X POST https://api.customdomain.ai/v1/connections/<ID>/domainconnect:start \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -d '{"service_id":"redirect","vars":{"redirectTarget":"https://new.example.com"}}'
# → 200 { apply_url, service_id: "redirect", dc_provider }
```

`redirectTarget` must be an `http` or `https` URL, or a bare host, at a public
hostname. It cannot be an IP address, `localhost` or an internal name, and it
cannot hold a user name or password. Anything else answers `400 invalid_request`
naming it. The `redirect` template takes no other variable (see [Template
variables](/docs/connect-flow/verify-and-go-live#template-variables)).

The response's `apply_url` is opened in the provider popup. Once the customer
approves, the provider writes the `REDIR301` record, and the DNS check promotes
the connection to live. Choose this path when the domain stays on its current
provider. Choose the edge-served `redirect_to` and `www_redirect` above when the
domain is proxied through the edge.
