A provider account is a key for a DNS provider or registrar that the workspace
connects once. CustomDomain™ checks the key before keeping anything, keeps it
encrypted (`GRANT_ENCRYPTION_KEY`), and never returns it.

## Where an account's key comes from

An account holds a key that reached the workspace in one of three ways, which are
three of the six [ways to connect](/docs/concepts/glossary#ways-to-connect):

- **An API key** you paste, through `POST /v1/provider-accounts` or the console's
  **Remember this key** box. See [Provider setup](/docs/dns/provider-setup).
- **A provider sign-in that is kept**, where the deployment keeps that provider's
  sign-in. The hosted service does at some providers (see
  [Managed sign-ins](/docs/connect-flow/managed-connections#managed-sign-in-grants)).
  These are listed with the accounts, grouped by provider.
- **A secure sign-in** at a provider that offers no sign-in a third party can use,
  where our software makes a lasting API key after your customer signs in. See
  [Keys made at a secure sign-in](#keys-made-at-a-secure-sign-in), and
  [GoDaddy](/docs/dns/provider-setup#godaddy) and
  [Namecheap](/docs/dns/provider-setup#namecheap) for two of them.

One-click setup and adding the records by hand leave no account, since there is no
key to keep.

The key is checked by listing the provider's domains. A provider that cannot
list them is asked for one of the selected domains instead; with scope `all`,
name a domain the key manages in `check_domain`, or the call answers `400`
`check_domain_required`. A key is never kept unchecked.

## Access

- **Continuous**: kept until you revoke it. It keeps the records it wrote:
  putting back records that disappear, where the deployment has automatic
  repair on ([monitoring](/docs/connect-flow/monitoring)), removing records
  when a domain is [removed](/docs/connect-flow/offboarding), and re-applying
  them when you ask (`POST /v1/connections/{id}:reapply`, which answers
  `via: "provider_account"`). Whoever may manage the account also uses it to
  list the domains it reaches and connect more of them, and a
  [nameserver move](/docs/guides/nameserver-migration) may use it. Each of
  these is in the [audit log](#audit-log).
- **One time**: used to connect the domains you choose, then deleted. It works
  for an hour at most: past the hour every use is refused with `409` and the
  key is deleted, whether or not the hourly cleanup got to it first. The
  account stays as the record of what it connected.

Certificates renew without any DNS access, so both behave the same there.

### Credentials that are used once

Some providers' credentials are never kept, because they are an account login
or a token that expires within hours or cannot be limited: ALL-INKL (the KAS
login), Arsys (the Panel de Control password), Azure DNS and Google Cloud DNS
(access tokens that expire within an hour), Binary Lane (a token that reaches
the whole account), INWX, Loopia, Plesk and Subreg (logins), and Openprovider
(a token that expires after 48 hours). They get one time access only:
`"access": "continuous"` answers `422` `use_once_credential` when you connect
the account, switch its access or give it a new key, and a connect that names
no access gets one time access. The console offers them one time access only,
and says why.
Sign-ins get the same choice: `oauth:start` takes `"access": "continuous"` or
`"one_time"`; continuous is offered where the deployment can keep that
provider's sign-in.

## Defaults and limits

When you leave them out, `access` is `continuous` (`one_time` for a
[credential that is used once](#credentials-that-are-used-once)), and `scope`
is `selected` if you send `domains` and `all` if you do not. `POST /v1/provider-accounts/{id}/connect`
takes at most 200 domains per call (`400` beyond that; see [connect many domains at
once](#connect-many-domains-at-once)).

## Scope

All of the account's domains (`"scope": "all"`, including ones added later), or
a selected list (`"scope": "selected"`, `domains`) picked from the provider's
own list where it has one.

### What each kind of account allows

How far an account's scope can be widened depends on how its key was made
(`made_by.how`), and the server enforces it:

| Kind | Widening its domains or scope |
| --- | --- |
| **Pasted** (`pasted`): you made the key and pasted it | Any scope and any domains. Nothing is read at the provider; connecting a domain the key cannot write is what finds it. |
| **Made at a secure sign-in in the console** (`console_sign_in`) | Only to domains the key reaches. Each domain you add is read with the key before anything is stored. A domain it does not reach is refused, and nothing is stored. `all` needs the provider to list the key's domains. |
| **Made at your customer's own sign-in** (`widget_sign_in`) | Never widened, by anyone (`403`). It can be renamed, narrowed or removed. |

Narrowing and renaming ask the provider nothing, for every kind, with one
exception: a key made at a secure sign-in that goes from `all` back to `selected`
has each domain it names that the account does not already hold read first, at most
20 a call (`400` `too_many_domains_to_check` beyond), as explained below.

For a key made at a secure sign-in, `PATCH /v1/provider-accounts/{id}` reads each
domain it adds, by its zone, with the key. A call that names a domain the key
does not reach answers `422` `zone_not_reached` with those domains in `domains`,
and stores none of the call's domains, not even the ones that were reached:

```json
{ "code": "zone_not_reached", "title": "This key does not reach every domain you added.", "domains": ["other.example"] }
```

At most 20 new domains are read in a call (`400` `too_many_domains_to_check`
beyond that). A failure that says nothing about the key, such as a timeout or a
server error at the provider, answers `503` and stores nothing; try again. An
account that no longer holds its key answers `409`: renew it first. Setting
`scope` to `all` has no domain to read, so it needs the provider to list the
domains a key reaches and the key to list them now. For a provider that cannot,
it answers `422` `scope_all_needs_list`: add the domains one at a time instead.
A key the provider refuses answers `422` `ProviderAuthenticationError`.

The scope `all` is no way round the read of a domain. While a key made at a
sign-in is on `all`, a domain you name that the account does not already hold is
read with the key too, whether the call keeps `all` or goes back to `selected`.
The change is written on the account as it is after the reads, so a renewal that
landed meanwhile is kept; an account that lost its key meanwhile answers `409` and
nothing is written.

## Connect many domains at once

`POST /v1/provider-accounts/{id}/connect` connects up to 200 domains with the account's key in one call. Each entry
in `domains` is a name, or an object that puts that one domain into an application of its own:

```json
{
  "application_id": "app_web",
  "domains": [
    "www.example.com",
    { "domain": "shop.example.com", "application_id": "app_store" },
    "docs.example.com"
  ]
}
```

A domain goes into the first of these that names an application:

1. the application named for that domain;
2. the call's `application_id`, which you can leave out;
3. the application that already holds the domain in your workspace (its connection's own), so a domain you already
   serve is linked to the account where it lives, not connected a second time.

A domain none of those names answers `400`, and so does one that two applications hold or that the call names for two
different applications. A name written twice is one domain, and the 200 counts domains, not entries.

Everything below is checked before the first record is written, so a call that is refused changes nothing:

- **The caller may manage the account.** An admin, an owner or the member who connected it. Anyone else gets `403`
  before the body is read, so a member cannot use or widen a key they may not manage.
- **The key serves every application the call uses.** A key made at a secure sign-in serves its own application and the
  ones an admin shared it with (`application_ids`); any other application answers `403` ("this key is not shared with
  this application; an admin or an owner can share it"). An application that is not your workspace's answers `404`.
- **Every domain is inside the account's scope.** A domain outside it answers `400` and names the domains. A key made
  at a secure sign-in in the console is the one exception: when a read of the domain's zone (the part of a domain
  that your DNS provider holds, such as `example.com` for `shop.example.com`) works with that key, the domain is
  connected with no new sign-in and the zone joins the scope once a write there works. A call reads at most 20 such
  zones, once each, and answers `400` `too_many_domains_to_check` beyond that. To widen the scope on its own, use
  `PATCH /v1/provider-accounts/{id}`.

Each result in `results` names the `application_id` the domain went into, with its `status`: `connected`, `already`
or `failed`. A domain whose write fails does not stop the others. See the
[API reference](/docs/api-reference/provider-accounts/connectWithProviderAccount).

## More domains in the account

An account's key often reaches more domains at the provider than your workspace has connected. For whoever manages the
account, `GET /v1/provider-accounts/{id}` and the answer of a [secure sign-in's
keep](/docs/api-reference/provider-accounts/keepBrowserSessionAccount) carry `more_domains`: the domains the key
lists, minus the ones your workspace has connected. A console can ask "This IONOS account holds 11 more domains.
Connect them?" and send the list to the connect call above.

- A domain counts as connected when your workspace has a connection for it, or for a name under it, in any
  application. A failed connection and a test mode one count for nothing.
- The list is sorted. It is empty for a provider that cannot list the domains of a key (see [which providers list
  their domains](#which-providers-list-their-domains)).
- It can include domains outside the account's scope, such as a key made for one domain that reaches the whole
  account at the provider. The connect call refuses those until the scope covers them.
- Listing a key's domains is a use of the key, so only the account's manager gets it: it is left out for a viewer,
  for a member who did not connect the account, for a key your customer's sign-in made, and for an account with no
  usable key. The account list never carries it.
- The read changes nothing. If the provider refuses the key or the list fails, `more_domains` is left out and the
  account stays as it was; [Check now](#health-checks) is where a refused key is found. The provider's list is kept
  for a minute, so reading the account again does not call the provider again.

## Which providers list their domains

Where a provider has a list call for it, the key is checked by listing, the console's **Connect more
domains** shows the account's own list, and `POST /v1/provider-accounts/{id}/zones` returns it. These
providers list: Amazon Route 53, Azion, Binary Lane, Cloudflare, cPanel hosts and o2switch, DigitalOcean,
DirectAdmin, DNSimple, 101domain, Domeneshop, Epik, Exoscale, Gandi, Gcore, GoDaddy, Hetzner, hosting.de,
Hostinger, Huawei Cloud DNS, INWX, IONOS and united-domains, Joker.com, Loopia, Metaname, Mythic Beasts,
NameBright, Namecheap, Name.com, netcup, NS1, OVHcloud, Plesk, Porkbun, Scaleway, Spaceship, Subreg, Vercel,
webnames.ca, Websupport, WEDOS and Zone.ee. A provider that is not named here answers that it cannot list,
and you name one domain the key manages instead (see [scope](#scope)).

What each of the ten most recent lists holds, and what happens when a key may not:

| Provider | What the list holds | A key that may not list |
| --- | --- | --- |
| Porkbun | Active domains with API Access turned on. A domain without API Access is left out, because Porkbun would refuse a change to it. | Checked with a domain you name. |
| Hetzner | The project's primary zones. A secondary zone is left out: its records come from another nameserver and the API refuses to change them. | Checked with a domain you name. |
| DigitalOcean | Every domain in the account. | A token with custom scopes needs `domain:read`. Without it, the key is checked with a domain you name. |
| Name.com | Every domain in the account. | Checked with a domain you name. If two-step verification blocks API access, the key is refused instead, and Name.com's API Access setting has to be switched on. |
| Gandi | The domains of the token's personal organization, which is all Gandi's list call returns. | Checked with a domain you name, and also when the list comes back empty, because an empty list cannot be told from a token whose domains sit in another organization. |
| DNSimple | The zones of the account the key writes to: the only account an account token has, or the first account of a user token that reaches several. A secondary zone is left out, because DNSimple does not let you change its records. | A scoped token needs the right to read zones (`domains:*:read`). Without it, the key is checked with a domain you name. |
| OVHcloud | Every DNS zone the key may read. | The key needs the right GET on `/domain/zone`. A key made with rights on `/domain/zone/*`, and a key from a secure sign-in, which is limited to one zone, may not have it, and is checked with a domain you name. An invalid or expired key is refused instead. |
| Vercel | The domains of the team the key was installed on, or of your personal account for a token that names no team. | A token that may not list, or a personal token that finds no domain (it may be a team member's), is checked with a domain you name. |
| Spaceship | Domains that are registered or in their first grace period. A domain still being registered, in its second grace period or in redemption is left out. | A key needs the `domains:read` scope. Without it, the key is checked with a domain you name. A sign-in through Spaceship's MCP server cannot list. |
| Hostinger | Active domains. A domain that is pending, expired or suspended is left out. | Checked with a domain you name. |

A key that the provider refuses (a wrong, revoked or expired key) is never treated as "cannot list": the
call answers `422` `ProviderAuthenticationError` and the account is marked as needing a reconnect.

## Who can manage an account

Anyone whose role operates applications may connect a key, read the accounts and
rename one. Changing an account's access, scope or domains, listing the
domains its key reaches, connecting domains with it, giving it a new key,
[renewing it by signing in again](#renew-an-account-by-signing-in-again) and
[removing it](#remove-an-account) take an admin, an owner or the member who
connected it, because the key reaches zones the others were never given and
removing it deletes the key and detaches every domain that used it; anyone else
gets `403`. A key your customer's own sign-in made, which no member connected, is
managed by an admin or an owner alone. Each account says whether you may
(`can_manage`), and the console shows a member who did not connect an account no
buttons on it.

A viewer reads the accounts without what identifies your customer at their
provider: a [key made at a secure sign-in](#keys-made-at-a-secure-sign-in) shows
them no `agent_key.account` (the customer number) and no `agent_key.session_id`.

A delegated agent token reads them the way a viewer does, and less, with `domains:read`:
`GET /v1/provider-accounts` lists only the keys that serve the application its
grant is bound to, never a key a customer made at their own sign-in, with that
application's connections only, only the `domains` that no other application
of your workspace has connected, `can_manage` false and an empty `kept_access`.
`?application_id=` may only repeat the grant's own application (`403`
otherwise). Its answers also leave out whatever could name a person or another
application's domain:

- **Who made a key.** `made_by.by` and `created_by` are left out, and
  `made_by.how` stays.
- **The key's name.** `agent_key.name` is left out for every key: the name holds
  an application's name, and a key of the agent's own application can carry
  another application's after a share.
- **The provider's words about a failure.** `last_error` is left out for every
  key, because those words can name a domain of another application. `status`
  and `needs_you.reason` still say that the key needs attention.
- **The share list.** `application_ids` is always empty, since it names the
  workspace's other applications; `application_id` says the key serves the
  agent's own.
- **A key made for another application and shared with the agent's own.** Its
  `label` reads `<Provider> key` and it has no `application_id`, because the
  label the agent made it with (`<Provider> key for <domain>`) names the other
  application's domain. `?q=` searches only what the agent reads.

`?domain=` answers an empty `accounts` and `saved_access` for a zone in which
another application holds a domain (and the grant's own holds none), and when
the workspace's connections cannot be read. It reads a key at its provider only
for a zone the grant's own connections are in.

The agent reads `GET /v1/connections/{id}/saved-access` with `domains:read`
(with no `key_name` on any entry, and the same neutral label for a shared key)
and uses a key with `POST /v1/connections/{id}:use-saved-access` and
`domains:connect`, for a connection of that application; the account the use
answers is read the same way as the list. The audit log records the use as
`agent.acted` under the agent's grant once whenever the records were written,
the key linked or the write failed at the provider, whatever the answer; a use
refused before anything was sent, such as one with no records to write, leaves
no row.

The same limits hold when the agent reads a connection. On
`GET /v1/connections/{id}` the `credential` of a connection linked to a key
carries no `account`, no `session_id` and no `name`, and a `reach` through a key
made for another application reads `<Provider> key`. No connection answer to an
agent token carries `end_user_ref`, your id for the customer. An API key reads
all of it whole.

Sharing a key with another application is narrower still: only an admin or an
owner may, not the member who connected the key. See
[which applications may use it](#which-applications-may-use-it).

## Endpoints (API key)

| Call | Does |
| --- | --- |
| `POST /v1/provider-accounts` | Connect a key: `{ provider, credential: { token }, access, scope, domains?, check_domain? }`. Answers the provider's domains when it lists them. |
| `GET /v1/provider-accounts` | Every account with access, domains, last use and expiry, [what needs you](#what-needs-you) first, plus kept sign-ins and Domain Connect authorizations grouped by provider. `?owner=workspace` or `end_user`, `?q=`, `?limit=` and `?cursor=` filter, search and page the list; `end_user_keys` counts your customers' keys. |
| `PATCH /v1/provider-accounts/{id}` | Change label, access, scope or domains, or the applications the key is shared with (`application_ids`, admin or owner only). A domain taken out stays connected, without continuous access. What [each kind allows](#what-each-kind-of-account-allows) when it widens the account differs. |
| `POST /v1/provider-accounts/{id}/zones` | The domains the key reaches. Takes whoever may manage the account. |
| `GET /v1/provider-accounts/{id}` | One account with its domains. For its manager it also carries [`more_domains`](#more-domains-in-the-account). |
| `POST /v1/provider-accounts/{id}/connect` | [Connect domains](#connect-many-domains-at-once), each into its own application: `{ application_id?, domains }`, where a domain is a name or `{ domain, application_id }`. A domain is linked to the account once its records are written; a domain in a zone the key does not reach fails alone (`zone_not_reached`) and is not linked. |
| `POST /v1/provider-accounts/{id}/reconnect` | A new key: `{ credential: { token, params? }, access?, check_domain? }` for a pasted key, checked before it is kept (`params` replace the kept ones), or `{ method: "secure_sign_in", return_origin, consent_version }` to [renew a key made at a sign-in by signing in again](#renew-an-account-by-signing-in-again). |
| `POST /v1/provider-accounts/{id}:check` | [Check now](#health-checks): read the key against its provider and answer `{ account, result }`. Once a minute for an account. |
| `DELETE /v1/provider-accounts/{id}` | Revoke: the key is deleted; its domains stay connected. Answers [what that leaves](#remove-an-account): `used_by` and `revoke_url`. |
| `POST /v1/provider-accounts:sign-in` | Start a [secure sign-in that adds an account](#add-an-account-by-secure-sign-in), with no domain. The console only. |

A key the provider refuses marks the account `needs_reconnect` and each of its
domains records it on its timeline. A refusal that only concerns one zone (the
key works, but not for that domain) fails that domain and leaves the account
as it is. The console's **Connected accounts** page
shows all of this; *Remember this key* on the connect page keeps the key as a
continuous account.

## Keys made at a secure sign-in

When a [secure sign-in](/docs/guides/secure-sign-in#lasting-api-keys) makes a
lasting API key at a domain's DNS provider, CustomDomain™ keeps it as a provider
account of the workspace, checked and encrypted like any other, with continuous
access and the domain's zone as its scope. Such an account is different in five
ways:

- **It belongs to one application.** `application_id` names the application
  whose domain it was made for. Connecting another application's domain with it
  is refused with `403`, unless an admin
  [shared the key](#which-applications-may-use-it) with that application.
- **It can serve the application's other domains.** A key made at a sign in you
  or a teammate started in the console connects another domain of the same
  application with no second sign in and no second key: CustomDomain™ first
  reads that domain's records with the key, and only when the provider answers
  is the domain connected; its zone joins the key's scope once the records are
  written there. A domain in another account at the provider is refused with
  `400`, and needs its own sign-in. "Started in the console" means the
  console's own signed call: a sign-in your backend starts through the API, even
  one that names the console in its headers, makes a key that serves its one
  domain only. A key your customer's sign-in made in the widget serves only the
  domain they agreed to.
- **It says where it came from.** `origin` is `browser_agent`, and `agent_key`
  holds its record, never the key: the `name` it was made with (`CustomDomain`
  and your application's name), its `scopes` and `rights` (what it can do beyond
  DNS: `transfer`, `billing` or `account`), the provider's `account` identifier
  when the page showed one (never an email address, and not shown to a
  viewer), the `session_id` that made it (not shown to a viewer either), when it was checked (`verified_at`) and ends (`expires_at`), the last
  `notice`, the `reconnect_reason`, `reconnect_sent_at` and `renewed_at`,
  `old_key: "revoke_by_hand"` after a renewal, and the provider's `revoke_url`.
- **It is renewed by a sign-in, not a pasted key.** Before its end, or once the
  provider refuses it, the account is `needs_reconnect`. For a key your customer's
  sign-in made, your customer signs in again
  ([reconnecting](/docs/guides/secure-sign-in#reconnect)). For a key a member
  made at a sign-in in the console, a member who manages the account
  [signs in again](#renew-an-account-by-signing-in-again) from the account, and
  the account keeps its domains. In the console, **Connected accounts** shows it
  as **Made at sign in**.
- **Removing it deletes only our copy.** `DELETE /v1/provider-accounts/{id}`
  answers the provider's `revoke_url` and sends `credential.removed`: the key
  itself lives at the provider until it is revoked there.

## Add an account by secure sign-in

The console's **Connected accounts** can add an account without a pasted key: the person signs in to the provider
in a temporary browser, CustomDomain™ makes the API key itself, checks it by listing the domains it reaches, and
asks which of those domains the account may use. The account is kept only after that answer. Nothing is kept before
it, so a sign-in that is left alone or cancelled adds no account.

It is for the console only. `POST /v1/provider-accounts:sign-in` answers `201` with `{ session_id, popup_url }` to an
API key that carries the console's signed visitor forward, for an owner, an admin or a member (a viewer is refused
with `403`). The `X-CustomDomain-Client` header and the `Origin` alone start nothing, and a widget token, an end
user's token, a delegated agent token and the operator's key are refused with `403` `browser_account_unavailable`.
Your own backend's API call does not start one; add the key with `POST /v1/provider-accounts` instead.
[`GET /v1/providers`](/docs/api-reference/providers/listProviders) lists each company's `account_ways`, easiest
first: `secure_sign_in` where the deployment runs it for that company, then `api_key`.

Once the key is made, the member who started the sign-in reads it with `GET /v1/browser-sessions/{id}` (state
`key_ready`, the `zones` the key lists, what the key is, and when the ten minute wait ends) and confirms with
`POST /v1/browser-sessions/{id}:keep`:

```json
{ "scope": "selected", "domains": ["example.com"], "access": "continuous", "application_ids": [] }
```

- **`scope` is always named.** `all` of the account's domains, or `selected` ones, each a domain the key lists
  (`422` `domain_not_listed` otherwise). `access` is `continuous` (the default) or `one_time`; a credential that is
  used once is `one_time` only.
- **The account is the workspace's own.** `origin` is `browser_agent`, `made_by.how` is `console_sign_in`, and it is
  bound to the application the sign-in named, or serves every application when it named none.
  `application_ids` [shares the key](#which-applications-may-use-it) with other applications, for an admin or an
  owner only.
- **One key per provider account.** When the workspace already holds a continuous key for the same provider account
  and application, the new key is swapped into that account (`200`, `swapped: true`): the old key stays at the
  provider and the account says so (`old_key: "revoke_by_hand"`). The answer also names it, `replaced_key` with
  the `name` it was made with and the `page` where the provider lists and deletes keys, so you delete the right
  one; the two keys carry different names, because an account sign-in names its key to the second (two sign-ins
  for the same account in the same second would share one). The chosen
  domains join the account's scope and never narrow it. Every swap takes an admin, an owner or the member who
  connected the account, whether or not it widens the scope: another member's keep is `403` and the key still
  waits, so they can cancel the sign-in and be told which key to delete. GoDaddy is the exception for now: its
  second sign-in adds a second account.
- **A suspended workspace adds none.** While an operator has suspended the workspace, starting a sign-in and
  keeping its key are `403` `workspace_suspended`; the read and the cancel still work, so one under way can be
  abandoned and its key named.
- **An abandoned sign-in names its key.** `POST /v1/browser-sessions/{id}:cancel` with the API key, or the ten
  minutes passing, drops the key from our memory and answers `left_key`: the name it was made with and the provider's
  page that deletes it. The key itself lives at the provider until you delete it there.

Every call about the session is for the member who started it, in their workspace; another member's session, another
workspace's and a connect sign-in's all answer `404`. Every account made, swapped or shared is in the
[audit log](#audit-log) (`provider_account.created`, `.key_replaced` with the replaced key's name as `old_key_name`,
`.updated`, `.shared`).

## Renew an account by signing in again

A key made at a secure sign-in in the console is renewed the way it was made: by
signing in to the provider again. The account stays the same account. It keeps
its id, its domains, its scope, its access and the domains linked to it, and only
its key changes.

`POST /v1/provider-accounts/{id}/reconnect` takes `method`. The default,
`api_key`, is the paste for a key a person pasted. `secure_sign_in` starts the
same sign-in as [adding an account](#add-an-account-by-secure-sign-in), for the
account's own provider and application:

```json
{ "method": "secure_sign_in", "return_origin": "https://app.example.com", "consent_version": "cb-3" }
```

It answers `201` with `{ session_id, popup_url }`, and `GET /v1/browser-sessions/{id}`
names the account the session renews in `renews_account_id`. When the key is made
and checked, confirm it with `POST /v1/browser-sessions/{id}:keep` and an empty
body, `{}`: the new key goes into the same account (`200`, `swapped: true`, and
`replaced_key` names the old key so you delete it at the provider). The account is
`active` again, its [daily check](#health-checks) starts afresh, and a one time
account gets a new hour.

- **Who may.** The console's own signed call, for an admin, an owner or the member
  who connected the account. Another member and a viewer get `403`, and so does
  any caller that is not the console.
- **Which keys.** A key made at a sign-in in the console. A key you pasted is
  renewed by pasting a new one (`409`). A key your customer's own sign-in made is
  renewed by your customer, never from the console (`403`).
- **It must be the same provider account.** Where the provider names the account,
  the new key's account must be the same. Where it does not (IONOS), the new key
  must list every domain the account holds, or for an account of every domain,
  the domains linked to it. A key of another account answers `422`
  `different_account` and changes nothing; the key stays pending, and cancelling
  the sign-in names it so you can delete it at the provider. An account that holds
  no domain and has no account number gives nothing to compare, so it answers `422`
  `account_not_verifiable` the same way: remove the account and add it again with
  a new sign-in.
- **Nothing else changes.** A body that names `scope`, `domains`, `access` or
  `application_ids` is `400`: change those with `PATCH`.
- **Audited.** `provider_account.key_replaced`, with `via` `sign_in` and `renewed`
  true.

## Remove an account

`DELETE /v1/provider-accounts/{id}` deletes CustomDomain™'s copy of the key and
the account. It says what that leaves:

```json
{ "id": "pacct_...", "revoked": true, "used_by": 2, "domains_kept_connected": 2, "revoke_url": "https://..." }
```

- **`used_by`** is how many domains used the account. They stay connected and
  keep serving, without continuous access; each records `access_revoked` on its
  timeline. `domains_kept_connected` is the same number.
- **`revoke_url`** is the provider's page where the key itself is deleted, for a
  key you pasted as for one made at a sign-in. CustomDomain™ cannot revoke a key at
  the provider, so the key lives there until you delete it. The field is absent
  when the provider has no such page on file.

Removing an account takes whoever manages it: an admin, an owner or the member
who connected it, and for a key your customer's sign-in made, an admin or an owner.
Anyone else, a viewer included, gets `403`, and nothing is deleted or detached.

## What needs you

`GET /v1/provider-accounts` lists the accounts that need someone first, each
with `needs_you.reason`, then the most recently used, the never used last,
newest first:

| `needs_you.reason` | What it means | What to do |
| --- | --- | --- |
| `refused` | The provider refused the key. | Give the account a new key, or sign in again for a key made at a sign-in, or remove it. |
| `expired` | The key reached its end, or a one time key's hour passed with the key unused. | Sign in again, give it a new key, or remove it. |
| `check_failed` | The daily [health check](#health-checks) of the key failed three times in a row without the provider refusing it (a timeout, a server error, a domain the key no longer reads). The key may still work. | Call Check now (`POST /v1/provider-accounts/{id}:check`) to try it. If it keeps failing, check the provider's status and that the account still holds its domains. |
| `expiring` | A key made at a sign-in ends within 30 days (`until` says when). | Sign in again before then. |
| `one_time_window` | A one time key waits for its domains to be connected, until `until`. | Connect the domains now. |
| `no_domains` | A continuous key the workspace holds that no domain uses. | Connect domains with it, or remove it. |

An account that needs nothing has no `needs_you`.

## Health checks

A key that stops working should be found when it stops, not weeks later when
something happens to use it. Once a day CustomDomain™ reads each continuous
account's key with one cheap call: the provider's list of domains where it gives
one, else a read of one domain the account covers. The check writes nothing at
the provider, and it does not count as using the key, so **last used** does not
move.

Every account the check applies to answers `health`:

| `health.state` | What it means |
| --- | --- |
| `ok` | The last check worked. `checked_at` says when. |
| `failing` | The last check, or more, could not reach a verdict. `failures` counts them in a row. From the third the account is in [what needs you](#what-needs-you) as `check_failed`. |
| `refused` | The provider refused the key. The account is `needs_reconnect`. |
| `unchecked` | No check has run yet. A key connected before the checks began waits for its first one, within a day. |

A one time account, and an account that holds no key, has no `health`. A
viewer and a delegated agent token read it as a member does: it names no one and
no domain.

What a check finds:

- **The provider accepts the key.** The failures are forgotten and the next
  check is a day later, give or take two hours, so a thousand accounts do not
  all fall due at once.
- **The provider refuses the key.** The account becomes `needs_reconnect`, each
  domain it covers records it on its timeline, and the workspace gets one inbox
  item. A key made at a secure sign-in also asks your customer to sign in again.
  A refused key is not checked again until you give the account a new key or
  call Check now. When the provider refuses to list the domains, CustomDomain™
  reads one domain before it calls the key refused, so a key made without the
  right to list is not flagged.
- **Anything else goes wrong** (a timeout, a server error, a rate limit, or a
  domain the key cannot read, which can mean only that this domain is out of the
  key's reach). The check tries again after 1 hour, then 4, 12 and 24 hours, then
  every 48 hours, and from the third failure in a row the account is in [what
  needs you](#what-needs-you) as `check_failed`. The key stays active: a failing
  check does not stop repairs.

A key your customer's own sign-in made is never listed and is checked with one
read of a zone it already serves, because its account holds domains you were
never given.

Giving an account a new key, reconnecting it, or making a one time key continuous
starts its checks over, a day from then.

### Check now

`POST /v1/provider-accounts/{id}:check` runs the same check on request and
records what it finds the same way. It takes the workspace's API key and an
admin, an owner or the member who connected the account; a widget token or an
agent token is refused. It answers the account and a `result`:

```json
{ "account": { "id": "pacct_...", "status": "active", "health": { "state": "ok", "failures": 0 } }, "result": "ok" }
```

- `ok`: the provider accepted the key. A pasted key that the provider had
  refused and that works again returns to `active`, and the change is in the
  [audit log](#audit-log). A key made at a secure sign-in keeps its status,
  because it is renewed by signing in again.
- `refused`: the provider refused the key, and the account is now
  `needs_reconnect`.
- `unreachable`: the provider could not be asked, or answered with an error that
  is not a refusal. `message` says what. The failure counts toward the backoff.

An account's key can be checked once a minute: a second call answers `429`
`rate_limited` with `Retry-After: 60`. A key your customer's sign-in made answers
`403` (the daily check reads it, as above), a one time key `409`, and an account whose provider cannot list its
domains and which covers none answers `409` `nothing_to_check` (connect a domain
with it first).

An account that changed while its key was being checked (its key was replaced, or
someone edited it in that moment) also answers `409`. Nothing is recorded for it
and the minute is not used up, so call Check now again at once. A call that ends
after the provider was asked, because the connection dropped before the answer or
the answer was a `500`, does use up the minute.

## How a key was made and who added it

Every account says how its key was made and by whom, in `made_by`:

- `how` is `pasted` (a person pasted the key), `console_sign_in` (made at a
  [secure sign-in](/docs/guides/secure-sign-in) you or a teammate started in
  the console) or `widget_sign_in` (made at your customer's own sign-in, in the
  widget or one your backend started for them through the API).
- `by` is the member's e-mail, `a customer` for a key your customer's sign-in
  made (never their id), the API key's name for a key an API call pasted, or
  absent when it was not recorded. A delegated agent token's answer always
  leaves it out, because an agent has no need to know which person made a key;
  `how` stays.

`?owner=workspace` keeps the keys your workspace holds (pasted, or made at a
sign-in started in the console); `?owner=end_user` keeps the keys your
customers' own sign-ins made. `end_user_keys` counts those keys and the
customers they belong to (distinct `end_user_ref`), before `owner`, `q` and
paging apply, so a console can show them as one row. `?q=` keeps the accounts
whose label, scope domain or linked domain holds the text and, for a member,
whose `account_ref`, `agent_key.account` or `end_user_ref` does; a viewer never
matches those, as they are not shown one. `?limit=` (1 to 200) and `?cursor=`
(the previous answer's `next_cursor`) page the list; without `limit` the answer
holds every account. `?domain=` answers the resolver's order in full, so
`limit` and `cursor` with it are `400`.

## Who enforces the limit

A key is held to the account's scope either by the provider or by
CustomDomain™, and `enforced_by` says which:

- `provider`: the key itself reaches only the zones it was made for. A
  Cloudflare API token names its zones, Porkbun switches API access on per
  domain, and an IAM policy names the Route 53 hosted zones an access key may
  change.
- `customdomain`: the key reaches the whole account at the provider (GoDaddy,
  IONOS, Namecheap, Name.com and the rest), and CustomDomain™ uses it only for
  the domains in the scope. Narrowing the scope changes what CustomDomain™
  does with the key, not what the key could do.
## Which applications may use it

A key made at a secure sign-in belongs to one application (`application_id`) and
serves its domains alone. It serves another application of the workspace only
when an admin shares it, so a workspace with two applications can sign in once
for a provider account and use that key for both.

Send `application_ids` to `PATCH /v1/provider-accounts/{id}`: the whole list of
**other** applications that may use the key, besides its own.

```json
{ "application_ids": ["app_marketing"] }
```

- **Who may.** An admin or an owner. The member who connected the key manages it,
  and still gets `403` here. Anyone else gets `403` too.
- **Which keys.** A key bound to one application. A key your customer's own
  sign-in made is never shared (`403`): it acts only for that customer in their
  application. A key you pasted that is not bound to an application already
  serves every one, so naming an application answers `422`
  `serves_every_application`.
- **Which applications.** Each must belong to your workspace, or the call
  answers `404`. The key's own application always serves, so naming it, naming an
  application twice or sending a blank changes nothing. At most 100 per call.
- **It replaces the set.** Leave an application out to take the key back from it,
  and send `[]` to share with none. The answer's `application_ids` is the list
  now in force.
- **What a share allows.** The shared application's domains can use the key like
  its own: the saved-access list offers it for the second application's domains
  (and never for a third), `POST /v1/provider-accounts/{id}/connect` takes
  that application's id, a second secure sign-in for the same provider account
  from the shared application swaps its key into the shared account instead of
  adding a second one, and reconnecting a domain of the shared application renews
  the key in the same account.
- **What taking it back does.** The domains of that application that were using
  the key stay connected, without continuous access, and each records
  `access_revoked` with the reason `unshared` on its timeline.
- **Audited.** Each application shared writes `provider_account.shared` and each
  taken out `provider_account.unshared`, with the applications the key served
  before and after and the ones that changed.

## Whose key it is, and saved access

Every account says whose it is. `owner_kind` is `workspace` for a key your
workspace holds (one you pasted, or one made at a sign-in you or a teammate
started in the console) and `end_user` for a key your customer's own sign-in
made. A key made by a customer acts only for that customer, in the application
where they made it: you can narrow it or remove it, and you cannot use it, list
the domains it reaches or widen it. `account_ref` is the provider account the
key belongs to, and `end_user_ref` your id for the customer, when the sign-in
named one. A viewer sees neither.

**Saved access** answers "which kept key can act for this domain, for me" in one
place, so a second domain at the same provider does not start a second sign-in:

- `GET /v1/connections/{id}/saved-access` lists them, best first. A key is
  listed when it is at the domain's provider, kept (continuous) and still
  working, serves the connection's application, and you may use it. A key whose
  scope already holds the domain's zone is `ready`. A key made at a sign-in
  started in the console may also be listed with `ready: false`, after one read
  with it showed it reaches the zone; using it adds the zone to its scope. At
  most three such reads happen per call, and each answer is kept ten minutes.
  There is one entry per provider account.
- `POST /v1/connections/{id}:use-saved-access` with `{"account_id": "..."}`
  writes the domain's records with that key and links it once the write worked.
  A write that fails links nothing, leaves the key's scope as it was and
  records the failure on the domain (`error_code` and `error_message`):
  `502 saved_access_write_failed`, with the provider's words. A provider that
  writes one record set at a time can fail after the first, so the zone may
  hold some of the records even though the call failed. An account that
  cannot act for the domain is `409 saved_access_not_usable`.
- `rails.saved_access` on `POST /v1/domains:check` is the same list for an API
  key caller, and `recommended_rail` is then `saved_access`. An end user's
  widget token gets it only for that customer's own keys, under the rules in
  [A returning customer's own key](#a-returning-customers-own-key). An AI agent
  uses the same two routes through the
  [MCP tools](/docs/mcp/overview) `find-saved-access` and `use-saved-access`
  (and `list-provider-accounts` for the accounts): `discover-provider` reports
  `rails.savedAccess` and says so.
- `GET /v1/provider-accounts?provider=&domain=` keeps the accounts that can act
  for a domain.

A secure sign-in or a provider sign-in for a domain that a saved key can already
act for answers `409 saved_access_available` before anything starts. Send
`new_sign_in: true` to sign in with another account. Your customers' widget
sessions are not refused this way: a customer's own saved key is offered to them,
but the offer is not a refusal.

### A returning customer's own key

A key your customer made at their own secure sign-in is reused only for that
customer, in the application where they made it, and never for anyone else:
not for another customer, not for you or a teammate, and not for an AI agent.
When the customer comes back with another domain, `rails.saved_access` on the
check and `GET /v1/connections/{id}/saved-access` can offer them their own key
instead of a new sign-in, and only when all of this holds:

- the widget token is bound to the domain and was minted with your id for the
  customer (`end_user_ref`). A sample's `user_42` or `customer_123` does not
  count: it is a placeholder, so one customer could otherwise be offered
  another's key;
- the application allows it: `end_user_saved_access` is on (on by default; a
  test mode application never offers a key). Turn it off with
  `PATCH /v1/applications/{id}`; a console switch for it comes later;
- the customer can be told by email that their key was reused: the
  [end user notices](/docs/connect-flow/end-user-notices) feature is on, you
  gave their address when you minted the token (`end_user_email`) or the
  domain's connection holds one and names this customer (an address on a
  connection that names no customer does not count, because any customer's
  token could have set it), and the application's mail can be sent. Without
  the email, nothing is offered;
- the key was made at a sign-in started with a token minted with that same
  `end_user_ref` (any such token, not only the one asking now), and either its
  scope already holds the new domain's zone (`ready: true`) or one read with it
  shows it reaches that zone (`ready: false`);
- the key is not at GoDaddy. Reuse there is held until GoDaddy gives written
  permission ([why](/docs/dns/provider-setup#reuse-of-godaddy-keys-is-held-for-now)).

The entry names the provider and `from_domain`, a domain of theirs the key
already serves, and nothing else about the key: no key name, no application,
and the neutral label `<Provider> key` in place of any name a member gave the
account. Any miss leaves the customer on the usual sign-in. For now it is
an offer only: a customer's token cannot yet write a domain's records with the
key (`409 saved_access_not_usable`), and the sign-in is not refused. The tap of
consent for each domain, and the email after each use, come with that step.

A second secure sign-in for a provider account you already hold a key for, from
the application the key belongs to or one it is shared with, does not add a
second row. Its key is swapped into the existing account, and the
domain's zone joins that account's scope. The key it replaces still lives at the
provider unless it was the same key, so the account shows `old_key:
"revoke_by_hand"` with the provider's `revoke_url`; CustomDomain™ never revokes
a key itself. If the write that follows the sign-in fails, the account keeps the
new key (and `old_key`), the zone leaves its scope again unless the account
covered it before, and the domain records the failure; an account other domains
use is never removed for one failed write. GoDaddy is the exception for now: each
sign-in there keeps its own key ([why and what it means](/docs/dns/provider-setup#reuse-of-godaddy-keys-is-held-for-now)).

## DNS hosting uses an account at the registrar

[DNS hosting](/docs/dns/managed-dns) changes a domain's nameservers at its
registrar. Where the workspace keeps an account at that registrar, a
[nameserver move](/docs/guides/nameserver-migration#how-the-nameservers-change) can
use its key to make the change, so nobody signs in again: only for the domains the
account is given for ([scope](#scope)), and a key made at a secure sign-in only for
domains of the application it was made for. Each use is in the
[audit log](#audit-log) as `credential.used_for_nameservers`. Without such an
account the move goes through a secure sign-in at the registrar, or the person sets
the nameservers by hand. An account at the company that runs the domain's DNS,
when it is not the registrar, is never used for the change.

## Audit log

Every change to a provider account, and every use of its key beyond the records
it wrote, is in the workspace's audit log (`GET /v1/audit`, and the console's
**Activity** page), with who did it as the server knows them, never the key:

| Event | When |
| --- | --- |
| `provider_account.created` | A key is kept: pasted, or made at a secure sign-in. |
| `provider_account.updated` | Its label, access, scope or domains change, with the values before and after. Also when Check now finds that a refused pasted key works again and returns it to `active` (`status` before and after, `via: check_now`). |
| `provider_account.domain_added` | A key made at a sign-in in the console starts serving another domain's zone. |
| `provider_account.relinked` | A domain the application already had now uses this account. |
| `provider_account.key_replaced` | It gets a new key: pasted, or made when someone signed in again. |
| `provider_account.shared` | An admin or an owner lets another application use the key. Names the applications it serves before and after, and the ones just shared (`application_ids`). |
| `provider_account.unshared` | An admin or an owner takes that back. Same fields. |
| `provider_account.removed` | Our copy is deleted: revoked, its last domain removed, or the write after a sign-in failed. |
| `agent.acted` | An agent changed a domain's DNS under its grant: it used a saved key for a domain (`used a saved key`), re-applied a domain's records (`re-applied a domain's records`) or moved a domain's nameservers, or back (`moved a domain's nameservers`, `moved a domain's nameservers back`). The row is `agent:<grant id>` in the actor. |
| `credential.used_for_nameservers` | A [nameserver move](/docs/guides/nameserver-migration), or a move back, uses its key. |
