title: Apply records & go live
description: The three automatic rails, the manual fallback, propagation to live, and cert issuance.
---

Once a connection exists, get its [desired records](/docs/connect-flow/create-a-connection#response)
into the customer's DNS via one of the four
[rails](/docs/connect-flow/overview#the-four-rails). All of them move the
connection `pending → propagating → live`.

## Rail C: OAuth into the provider (flagship)

```bash
curl -X POST http://localhost:8080/v1/connections/<ID>/oauth:start \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"return_origin":"https://app.acme.example"}'
# → { "authorize_url": "https://<provider>/authorize?...", "provider": "cloudflare",
#      "flow": "oauth2", "callback_origin": "<this API's public origin>" }
```

The widget opens `authorize_url` in a popup. The provider redirects the customer
to `GET /v1/connect/oauth/callback`, which consumes the HMAC-signed single-use
`state`, exchanges the code, writes the records with the **one-time** access
token (discarded immediately, never stored, unless the deployment keeps
[managed sign-in grants](/docs/connect-flow/managed-connections#managed-sign-in-grants)),
and returns an HTML page that postMessages `{ type: "customdomain:oauth", payload }`
to the vetted `return_origin`. The connection is now `propagating`. `flow` says
which kind of sign-in the popup runs: `oauth2`, `vercel_integration` (the
CustomDomain™ integration install), `porkbun_handoff` (Porkbun's key approval),
`ovh_consent` or `mcp_oauth` (sign-in through the provider's MCP server, not
switched on for any provider on the hosted service yet).

## Rail A: provider-hosted one-click setup

```bash
curl -X POST http://localhost:8080/v1/connections/<ID>/domainconnect:start \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"return_origin":"https://app.acme.example"}'
# → { "apply_url": "https://<provider>/domainconnect/...", "service_id": "...", "dc_provider": "..." }
```

Redirect the customer to `apply_url`; their provider applies the signed template.
Both the synchronous redirect and the asynchronous variant are supported.
`service_id` may be omitted when a single/default template is loaded.

The synchronous `apply_url` carries a signed `redirect_uri` back to
`GET /v1/connect/dc/return/{state}`. Every template we publish allows that
return since version 2 of the templates was merged into the public Domain
Connect template repository on 2026-09-29. After the customer approves or
cancels, the provider sends the browser to the return page, which records any
error the provider reports on the connection, starts the DNS check at once,
posts the same `{ type: "customdomain:oauth", payload }` message as the OAuth
callback to the `return_origin` you passed (it must be on the server's
allowlist), and closes the window. A return that reports success is never
taken as proof: only public DNS promotes the connection.

## Rail B: API token (BYO)

The customer supplies a **scoped** provider credential; it writes the records,
and through the API it is discarded afterwards unless the request asks to
[remember it](/docs/dns/provider-setup#remembering-a-key-optional) (in the
console the remember box starts ticked). In the console, multi-part credentials
are collected as separate labeled fields (GoDaddy: one Personal Access Token;
Namecheap: username and API key; Route 53: access key ID and secret access key,
or an access role instead) and joined into `credential.token` for you; see
[Provider setup](/docs/dns/provider-setup) for each provider's exact steps.
Calling the API directly:

```bash
curl -X POST http://localhost:8080/v1/connections/<ID>/apply \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "cloudflare",
    "zone": "customer.com",
    "credential": { "token": "<scoped-provider-token>" },
    "records": [ { "type": "CNAME", "host": "app", "value": "edge.customdomain.ai", "ttl": 3600 } ]
  }'
```

`SPFM` records are merged into any existing SPF TXT at write time (never
clobbered); mark a record `essential: true` to fail the apply if it can't be
written.

## Bulk connect: more domains on one account

After a Rail B apply, one provider key can connect the **other** domains on that
same account in a single step. In the console this is the **"Connect more
domains"** panel: it lists the account's other zones and lets you **Select all**
or pick a subset, then connects them without re-entering the key.

Listing is supported for **Cloudflare, GoDaddy, Amazon Route 53, Namecheap,
IONOS, united-domains, Epik, NameBright and cPanel hosts (including
o2switch)**. Other providers can't enumerate an account's domains (or would
need a broader key than the records do), so they degrade to connecting one
domain at a time.

Two control-plane endpoints back it:

```bash
# 1. List the other zones on the account (credential passed once, not persisted)
curl -X POST http://localhost:8080/v1/providers/cloudflare/zones:list \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"credential":{"token":"<scoped-provider-token>"}}'
# → { "provider": "cloudflare", "zones": ["acme.com", "beta.com"] }
# A provider that can't list returns 422 { "error": "list_not_supported", … }

# 2. Create connections for the selected domains (idempotent, up to 200)
curl -X POST http://localhost:8080/v1/connections:bulk \
  -H "Authorization: Bearer <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"domains":["beta.com","gamma.com"]}'
# → { "results": [
#      { "domain": "beta.com",  "connection_id": "con_…", "status": "connected" },
#      { "domain": "gamma.com", "connection_id": "con_…", "status": "already" }
#    ] }
```

Each result carries a **per-domain `status`**: `connected` (a new connection),
`already` (one already existed; the call is idempotent, so re-running is safe),
or `failed` (that domain errored; the batch continues and reports its `message`).
Each new connection then applies records and goes live on its own rail exactly
like a single connect.

## Manual

If no automatic rail is available, show the records from
`GET /v1/connections/{id}/records` for the customer to add by hand. Nothing else
is required: the poller watches for them.

## Watch propagation → live

The control-plane's background poller resolves each desired record against
public DNS and, when they all match their intended values, flips the connection
to `live`. When the public resolver does not show a record yet (it may still
remember the name as missing, from a lookup before the record existed, or hold
the old value), the check asks the zone's own nameservers instead: every one of
them that answers must serve the record, so a provider still copying the change
between its nameservers is not counted as done. On that transition the edge issues the TLS certificate
on the next handshake and a `connection.live` [webhook](/docs/webhooks/overview)
fires (exactly once). Treat webhooks as the primary signal and **poll
`GET /v1/connections/{id}` as the fallback**: delivery is durable but can lag
(the outbox retries for up to six hours).

Timing, honestly:

- **A write is checked at once.** When a rail writes the records (a sign-in, an
  API key apply, a one-click return or an async callback), the connection is
  due on the poller's next pass, and the poller looks every five seconds. A
  record the provider serves right away is usually verified within seconds.
- **Checks back off with age.** Counted from when the connection was created
  (or last re-entered verification): every 5 seconds for the first 5 minutes,
  every 30 seconds until 15 minutes, every 2 minutes until an hour, then every
  15 minutes.
- A **`pending`** connection (records not yet seen) never fails on its own.
  After 72 hours it stays `pending` with `error_code: setup_incomplete` and is
  re-checked every six hours, forever. The moment the records appear it goes
  live.
- A **`propagating`** connection (a rail wrote the records) that never resolves
  within 24 hours becomes `failed` with `error_code: propagation_timeout` and
  fires `connection.failed` (the event carries `error_code` / `error_message`).
- **`failed` is not terminal.** `POST /v1/connections/{id}:recheck` revives it
  (fresh window, diagnosis cleared); re-`POST /v1/connections` for the same
  domain revives the newest failed row and returns `200`; and real traffic
  arriving at the edge for a failed host re-enters it into verification
  automatically. Only a manual disconnect removes a connection.

Where a rail can complete today on the hosted service: one-click setup
completes at NameSilo, Glauca Digital and Domain Chief (the providers measured
to serve our template catalog); GoDaddy, IONOS, Cloudflare and Vercel have not
onboarded it, so they are never offered one-click. Sign-in runs at Cloudflare,
DigitalOcean, DNSimple, Linode, Netlify, Vercel (the integration install) and
WordPress.com, and Porkbun's key approval runs too; each credential is used
once and never stored. Google Cloud DNS's sign-in, OVHcloud's consent and the
sign-ins through a provider's MCP server are built but not switched on yet.
Read `rails` on the pre-flight rather than memorizing this list; see
[Rail truth](/docs/concepts/ownership-and-setup-types#rail-truth-what-to-actually-tell-the-user).
