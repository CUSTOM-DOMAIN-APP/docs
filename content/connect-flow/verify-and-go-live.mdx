Once a connection exists, get its [desired
records](/docs/connect-flow/create-a-connection#response) into the customer's
DNS. Use one of the six [ways to
connect](/docs/connect-flow/overview#the-four-rails): sign in with the provider
(Rail C below), one-click setup (Rail A), [secure sign-in](#secure-sign-in), an
API key (Rail B), [add the records](#manual) by hand, or [DNS
hosting](#dns-hosting). All of them move the connection `pending → propagating →
live`.

## Rail C, the flagship: OAuth into the provider [#rail-c-oauth-into-the-provider-flagship]

```bash
curl -X POST https://api.customdomain.ai/v1/connections/<ID>/oauth:start \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"return_origin":"https://app.acme.example"}'
# → { "authorize_url": "https://<provider>/authorize?...", "provider": "cloudflare",
#      "flow": "oauth2", "managed": false, "access": "one_time",
#      "callback_origin": "<this API's public origin>" }
```

The body also takes `provider` and `region` where a provider needs them. It
takes `access` (`continuous` or `one_time`) and `purpose` (`"remove"`, to sign
in once more to take records off). `managed` and `access` in the response say
whether the sign-in will be kept (`continuous`) or discarded after this use
(`one_time`). A removal sign-in is never kept and echoes `purpose`. Without
`access`, a sign-in is kept wherever the deployment keeps that provider's
grants. The hosted service keeps them for Cloudflare, DigitalOcean, DNSimple,
Linode, Netlify, Porkbun, Vercel and WordPress.com. There the answer above reads
`"managed": true, "access": "continuous"`. The example shows a deployment that
keeps none.

The widget opens `authorize_url` in a popup. The provider redirects the customer
to `GET /v1/connect/oauth/callback`. That route consumes the HMAC-signed
single-use `state` and exchanges the code. It writes the records with the access
token, which is discarded at once unless the sign-in is kept as a [managed
sign-in grant](/docs/connect-flow/managed-connections#managed-sign-in-grants).
It then returns an HTML page that postMessages `{ type: "customdomain:oauth",
payload }` to the vetted `return_origin`. The connection is now `propagating`.
`flow` says which kind of sign-in the popup runs. It is one of `oauth2`,
`vercel_integration` (the CustomDomain™ integration install), `porkbun_handoff`
(Porkbun's key approval), `ovh_consent` or `mcp_oauth`. `mcp_oauth` is sign-in
through the provider's MCP server, switched on for Dynadot and Unstoppable
Domains on the hosted service.

## Rail A: provider-hosted one-click setup

```bash
curl -X POST https://api.customdomain.ai/v1/connections/<ID>/domainconnect:start \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"return_origin":"https://app.acme.example"}'
# → { "apply_url": "https://<provider>/domainconnect/...", "service_id": "...", "dc_provider": "..." }
```

Redirect the customer to `apply_url`; their provider applies the signed template.
Both the synchronous redirect and the asynchronous variant are supported.
`service_id` may be omitted when a single/default template is loaded.

### Template variables

`vars` takes the template's caller-supplied variables, and only those.
`email-full` takes `mxHost`, `spfInclude`, `dkimSelector`, `dkimTarget` and
`dmarcRua`. `email-mx`, `email-spf`, `email-dkim` and `email-dmarc` each take
their part of that set. `redirect` takes `redirectTarget`. The partner template
`clickfunnels` takes its partner's values. Every other template takes none. The
edge address (`edgeIp`, `edgeIp6`) always comes from the platform's own
configuration, on every path. That includes a kept one-click authorization's
re-apply. Naming one in `vars`, or a variable the template does not take,
answers `400 invalid_request`. Each value must have its variable's shape, or the
answer is `400 invalid_request` with `details` naming it:

| Variable | Accepted value |
| --- | --- |
| `mxHost`, `spfInclude`, `dkimTarget` | A fully qualified public hostname, such as `mx.example.com`: not an IP address, `localhost` or a name that resolves only inside a network (such as one ending in `.local`, `.internal`, `.lan` or `.corp`). |
| `dkimSelector` | One DNS label: up to 63 letters, digits, hyphens or underscores, with no dots. |
| `dmarcRua` | One email address at a public domain, such as `dmarc@example.com`. A `mailto:` prefix is accepted and dropped; `;`, `,` and other DMARC tags are refused. |
| `redirectTarget` | An `http` or `https` URL, or a bare host, whose host is a public hostname, with no user name or password, spaces, quotes or angle brackets. |

On the synchronous redirect, some templates take caller values (email,
forwarding). Their records are kept as awaiting the DNS provider until public
DNS shows them. Until then nothing else writes them. That covers a kept
sign-in's re-apply, a zone CustomDomain™ hosts, and the zone a nameserver move
builds. The same variable rules apply to `POST
/v1/templates/{serviceId}/apply-url`, which answers `404` for an unknown
template.

The synchronous `apply_url` carries a signed `redirect_uri` back to `GET
/v1/connect/dc/return/{state}`. Every template we publish allows that return.
That has been true since version 2 of the templates was merged into the public
Domain Connect template repository on 2026-09-29. After the customer approves or
cancels, the provider sends the browser to the return page. The page records any
error the provider reports on the connection and starts the DNS check at once.
It posts the same `{ type: "customdomain:oauth", payload }` message as the OAuth
callback to the `return_origin` you passed, which must be on the server's
allowlist. Then it closes the window. A return that reports success is never
taken as proof. Only public DNS promotes the connection.

## Rail B: bring your own API token [#rail-b-api-token-byo]

The customer supplies a **scoped** provider credential. It writes the records
and is discarded afterwards. To keep a key, connect it as a [provider
account](/docs/connect-flow/provider-accounts). In the console, the [remember
box](/docs/dns/provider-setup#remembering-a-key-optional) starts ticked and does
that for you. The console collects multi-part credentials as separate labeled
fields and joins them into `credential.token` for you. For example, GoDaddy
takes one Personal Access Token. Namecheap takes a username and API key. Route
53 takes an access key ID and secret access key, or an access role instead. See
[Provider setup](/docs/dns/provider-setup) for each provider's exact steps.
Calling the API directly:

```bash
curl -X POST https://api.customdomain.ai/v1/connections/<ID>/apply \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "cloudflare",
    "zone": "customer.com",
    "credential": { "token": "<scoped-provider-token>" },
    "records": [ { "type": "CNAME", "host": "app", "value": "edge.customdomain.ai", "ttl": 3600 } ]
  }'
```

`SPFM` records are merged into any existing SPF TXT at write time, never
overwritten. Mark a record `essential: true` to fail the apply if it can't be
written.

## Bulk connect: more domains on one account

After a Rail B apply, one provider key can connect the **other** domains on that
same account in a single step. In the console, this is the **"Connect more
domains"** panel. It lists the account's other zones and lets you **Select all**
or pick a subset. Then it connects them without asking for the key again.

Listing works for providers whose keys can read the whole account. These include
Cloudflare, GoDaddy, Amazon Route 53, Namecheap, IONOS, NS1, Scaleway, cPanel
hosts, Porkbun, Hetzner, DigitalOcean, Name.com, Gandi, DNSimple, OVHcloud,
Vercel, Spaceship and Hostinger, and many other API providers. The [full
list](/docs/connect-flow/provider-accounts#which-providers-list-their-domains)
is with provider accounts. Some providers can't list an account's domains, or
would need a broader key than the records do. They answer `list_not_supported`,
and you connect one domain at a time.

Two control-plane endpoints back it:

```bash
# 1. List the other zones on the account (credential passed once, not persisted)
curl -X POST https://api.customdomain.ai/v1/providers/cloudflare/zones:list \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"credential":{"token":"<scoped-provider-token>"}}'
# → { "provider": "cloudflare", "zones": ["acme.com", "beta.com"] }
# A provider that can't list returns 422 { "error": "list_not_supported", … }
# Needs a widget JWT or an API key; an empty credential.token is a 400.

# 2. Create connections for the selected domains (idempotent, up to 200),
#    optionally under a client's name
curl -X POST https://api.customdomain.ai/v1/connections:bulk \
  -H "Authorization: Bearer <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"domains":["beta.com","gamma.com"],"end_user_ref":"Acme Co"}'
# → { "results": [
#      { "domain": "beta.com",  "connection_id": "con_…", "status": "connected" },
#      { "domain": "gamma.com", "connection_id": "con_…", "status": "already" }
#    ] }
```

Each result carries a **per-domain `status`**. `connected` is a new connection.
`already` means one already existed. The call is idempotent, so running it again
is safe. `failed` means that domain errored. The batch continues and reports its
`message`. Each new connection then applies records and goes live on its own
rail, exactly like a single connect.

The call takes a widget token with the `app` scope or your workspace's API key.
With a key, the connections are created on the key's application, or on
`application_id` when that names another application of the same workspace.

`client_label` is the name of the client the whole list is for, up to 200
characters, such as an agency's client. Characters that draw nothing are
dropped, and a name with nothing left stores no name. It is stored on every
connection the call creates. The Domains page shows it, filters by it and
includes it in an export. A person can rename or clear it later in the domain's
**Settings** tab, or with `PATCH /v1/connections/{id}` ([change a domain's
settings](/docs/api-reference/connections/updateConnection)). `end_user_ref` is
a different field. It is your own id for the customer the domains belong to, up
to 256 characters. It is set when a connection is created and never changed
afterwards, because it ties a customer's widget token and saved access to the
connection. A domain that already exists keeps its name and id, and comes back
as `already`.

A workspace that has not subscribed yet connects its first ten domains without a
card, or the number an operator set. The rest of a list come back `failed` with
the reason, one by one, until its trial starts.

## Secure sign-in

Some providers offer no sign-in a third party can use. For those, the customer
signs in to the provider in a temporary browser. `POST
/v1/connections/{id}/browser:start` starts the session, and the widget or the
console opens it. A person is always there, so an API key or an agent cannot
start one. Where the provider allows it, our software makes a lasting API key on
the provider's own API page. The domain then goes on as an API key connection
(Rail B), with the key kept as a [provider
account](/docs/connect-flow/provider-accounts#keys-made-at-a-secure-sign-in).
Otherwise the changes are made on the provider's DNS page once the customer
approves them. See [Secure sign-in](/docs/guides/secure-sign-in).

## DNS hosting

The sixth way writes no record into the provider's DNS. The domain's owner
changes its nameservers once, where the domain was bought. CustomDomain™ then
hosts the zone and writes every record in it. Use `POST
/v1/connections/{id}/managed-dns`, and `POST
/v1/connections/{id}/nameservers:migrate` for the move. Your application decides
whether its customers are offered it. See [Managed DNS](/docs/dns/managed-dns)
and the [nameserver migration guide](/docs/guides/nameserver-migration).

## Manual

If no automatic rail is available, show the records from
`GET /v1/connections/{id}/records` for the customer to add by hand. Nothing else
is required: the poller watches for them.

## Watch propagation to live [#watch-propagation--live]

A background check resolves each desired record against public DNS. When they
all match their intended values, it flips the connection to `live`. The public
resolver may not show a record yet. It may still remember the name as missing
from an earlier lookup, or hold the old value. Then the check asks the zone's
own nameservers instead. Every one of them that answers must serve the record,
so a provider still copying the change between its nameservers is not counted as
done. On that change, the edge issues the TLS certificate on the next handshake,
and a `connection.live` [webhook](/docs/webhooks/overview) fires exactly once.
Treat webhooks as the main signal and **poll `GET /v1/connections/{id}` as the
fallback**. Delivery is durable but can lag: retries run for up to six hours.

Timing, honestly:

- **A write is checked at once.** When a rail writes the records (a sign-in, an
  API key apply, a one-click return or an async callback), the connection is due
  on the next check. Checks run every five seconds. A record the provider serves
  right away is usually verified within seconds.
- **Checks back off with age.** Counted from when the connection was created, or
  last re-entered verification: every 5 seconds for the first 5 minutes, every
  30 seconds until 15 minutes, every 2 minutes until an hour, then every 15
  minutes.
- A **`pending`** connection (records not yet seen) never fails on its own.
  After 72 hours it stays `pending` with `error_code: setup_incomplete` and is
  re-checked every six hours, forever. The moment the records appear it goes
  live.
- A **`propagating`** connection (a rail wrote the records) that never resolves
  within 24 hours becomes `failed` with `error_code: propagation_timeout`. It
  fires `connection.failed`, and the event carries `error_code` and
  `error_message`.
- **`failed` is not terminal.** `POST /v1/connections/{id}:recheck` revives it
  with a fresh window and the diagnosis cleared. Posting `POST /v1/connections`
  again for the same domain revives the newest failed row and returns `200`.
  Real traffic arriving at the edge for a failed host also puts it back into
  verification. Only a manual disconnect removes a connection.

Here is where each rail can complete today on the hosted service. One-click
setup completes at NameSilo, Glauca Digital and Domain Chief, the providers
measured to serve our template catalog. GoDaddy, IONOS, Cloudflare and Vercel
have not onboarded it, so they are never offered one-click. Sign-in runs at
Cloudflare, DigitalOcean, DNSimple, Linode, Netlify, Vercel (the integration
install) and WordPress.com, and Porkbun's key approval runs too. Each of these
is kept, encrypted, unless the person chooses one-time use. Sign in with Azure
DNS and the sign-ins through Dynadot's and Unstoppable Domains' MCP servers run
as well, and each of those is used once. Sign in with Google Cloud runs for
Google Cloud DNS. OVHcloud's consent and the other MCP server sign-ins are built
but not switched on yet. Secure sign-in runs at Namecheap, GoDaddy, IONOS,
Name.com, Squarespace, Hover, Spaceship and Hostinger, for the workspaces it is
switched on for. Read `rails` on the pre-flight instead of memorizing this list.
See [Rail
truth](/docs/concepts/ownership-and-setup-types#rail-truth-what-to-actually-tell-the-user).
