CustomDomain™ ships a **Model Context Protocol (MCP) server** so an AI agent
can search for, connect and manage domains through the same control plane `/v1`
API, without ever handling DNS records itself. It runs as a separate process
(`services/mcp`) and wraps the control plane; it adds no business logic of its
own.

The hosted endpoint is live at **`https://mcp.customdomain.ai/mcp`** (Streamable
HTTP). The console's **MCP server** page (under **More**, once you switch it on
in **Settings → Features**) has the endpoint, a connection test and copy and
paste setup for Claude Code, Claude Desktop, Codex, Cursor, VS Code, ChatGPT and any
other client. The welcome has an optional step that does the same for the agent
you pick, and says when it has signed in (see
[MCP: drive it from an agent](/docs/getting-started/mcp#set-up-an-agent-from-the-welcome)). The [agent skill](/docs/agents/skills) teaches an agent the safe
way to use the tools below.

The server reports itself as `customdomain-mcp`, version `0.6.0` (protocol
revision `2025-06-18`), and advertises only the `tools` capability.

## Tools

The server registers **twenty tools**, in a fixed order. None of them takes DNS
records as input. Records always come from the control plane, so an agent can
never inject them. Each tool needs one scope (see below).

The scope is checked twice. A delegated agent token must carry the tool's scope,
or the call is refused before it runs; the control plane checks the same scope
again on the route the tool calls. An API key or a client credentials token holds
no scopes: the control plane authorizes each call.

> **`generate-domain-suggestions` is deterministic, not AI.** Candidates are
> keyword joins plus a few common affixes (`get`, `try`, `use`, `my`, `…app`,
> `…hq`), expanded across TLDs by the registrar search and filtered to what is
> actually available. No LLM is involved: the same keywords always produce the
> same candidates, which keeps the tool predictable and testable.

> **`create-domain-order` is fail closed, and off on the hosted service.** The
> server places a paid order only after the integrator's purchase authorization
> callback approves it (see
> [Purchase authorization callback](#purchase-authorization-callback)). If no
> callback is configured, every purchase is denied, and the hosted service
> configures none: every call there answers `success: false` with the status and
> the `error` `rejected`, and nothing reaches the control plane. Behind the
> callback, the order goes to the control plane's direct purchase route, which has
> its own switch, `SELL_DIRECT_PURCHASE_ENABLED`, also off on the hosted service
> (`service_unavailable`), and which refuses API keys. So purchases through MCP
> are off there; buying a domain is live through the console's money safe
> checkout. See [Buying a domain](/docs/sell/buying-a-domain).

## Purchase authorization callback

Before every paid order, `create-domain-order` asks an endpoint the integrator
runs whether this purchase may go ahead. The deployment configures it with
`MCP_PURCHASE_AUTHZ_URL`, `MCP_PURCHASE_AUTHZ_USER` and
`MCP_PURCHASE_AUTHZ_PASSWORD`. With no URL set, every purchase is denied; the
hosted service sets none today.

The server sends a `POST` with a JSON body that carries only the domain, and
HTTP Basic auth with the configured user and password. The shapes below are
illustrative; the field names are exact.

```http
POST /authorize-purchase HTTP/1.1
Authorization: Basic <base64 of user:password>
Content-Type: application/json
Accept: application/json

{ "domain": "example.com" }
```

What the server does with your answer:

| Your answer | Result |
| --- | --- |
| `200` | Authorized, unless the body says `"authorized": false`. The body may carry the registrant contact and records (below). |
| `200` with `"authorized": false` | Denied. Your `reason` becomes the tool's `message`. |
| `401` | Denied. |
| Any other status | Denied. |
| A network error, or no answer within 10 seconds | Denied. |

A denial answers `success: false` with the status and the `error` `rejected`.
Nothing is ordered and nothing is charged.

An approval's body looks like this:

```json
{
  "authorized": true,
  "reason": "approved",
  "buyer": { "name": "Ada Lovelace", "email": "ada@example.com", "country": "GB" },
  "dnsRecords": [
    { "type": "CNAME", "host": "www", "value": "app.example.net", "ttl": 3600, "priority": 0 }
  ]
}
```

- `buyer` is the registrant contact. The agent never supplies one, so it has to
  come from you. **`buyer.email` is required**: an approval without it (including
  a `200` with no body, or a body that is not JSON) answers the status and the
  `error` `buyer_required`, and nothing is ordered.
- `dnsRecords` (each `{ type, host, value, ttl, priority }`) optionally seeds the
  new domain's DNS. They come from you, never from the agent.
- The order is sent with an idempotency key made from the domain and
  `buyer.email`, so a retried call for the same buyer and domain does not
  register it twice.

## Scopes

| Scope | Lets an agent |
| --- | --- |
| `domains:read` | Look, and change nothing: availability, suggestions, connection, certificate, order and nameserver move status, diagnosis, provider discovery, listings, billing standing. |
| `domains:connect` | Set a domain up: connect, re-apply, recheck, forward and email setup, and move its nameservers or move them back. A recheck can move a failed connection back into verification, so it is here and not in read. |
| `domains:disconnect` | Take a connected domain offline. Its own scope, so a grant that may set domains up cannot also remove them. A grant approved before this scope existed does not carry it: the person approves the agent again to add it. |
| `domains:purchase` | Register a domain. Spends money, and the grant needs a saved card and a monthly spend cap. |

The discovery documents list them in that order: look, change, remove, spend.
See [Agent access](/docs/agents/overview) for how a person approves them.

## What a call answers

A success is the tool's JSON object. A failure is an `isError: true` result with
one shape, whichever tool made it:

```json
{ "success": false, "error": "billing_required", "message": "An active subscription is needed to connect new domains.", "details": "..." }
```

`error` is the control plane's own code when it sent one (`billing_required`,
`quota_exceeded`, `confirmation_required`, `confirmation_mismatch`, `forbidden`,
`not_found`, `conflict`, `service_unavailable` and so on), else the tool's
fallback code: `search_failed`, `suggest_failed`, `order_failed`,
`connect_failed`, `status_failed`, `reapply_failed`, `disconnect_failed`,
`discover_failed`, `forward_failed`, `add_email_failed`, `list_failed`,
`certificate_failed`, `recheck_failed`, `diagnose_failed`, `billing_failed`,
`orders_failed`, `nameservers_failed` (the three nameserver tools), or
`tool_failed` for anything else. `create-domain-order`
reports the status that stopped it, such as `rejected` or `buyer_required`.
`details` is there only when there is one; for `billing_required` it says where
to fix it. Branch on `error`. After a `billing_required` failure,
`check-billing-status` says why.

Three refusals happen before a tool runs:

- A call with a missing or malformed argument (for example no `confirm` on
  `disconnect-domain`, a `confirm_domain` on `create-domain-order` that does
  not repeat `domain`, or an `add-email` or `forward-domain` value of the wrong
  shape, such as an IP address for `mxHost`) gets the JSON-RPC error `-32602`,
  which names the argument. An unknown tool is `-32601`.
- A token without the tool's scope gets the JSON-RPC error `-32003`,
  `insufficient_scope`, which names the scope it needed.
- A caller over its tool call limit gets `rate_limited` with
  `retryAfterSeconds`, and the call never reaches the control plane. The limit is
  5 calls a second with bursts of 20 (`MCP_TENANT_RPS`, `MCP_TENANT_BURST`; 0
  turns it off). For API keys it is counted per credential: each API key, and
  each `/token` JWT, has its own bucket, so a workspace with several keys has
  several. A delegated agent token counts against its workspace, whose agents
  share one bucket, and the `CLIENT_ID:CLIENT_SECRET` form against its
  application.

On the `http` transport, a credential that is missing, invalid, expired or
revoked is answered with HTTP `401` rather than a failure inside a `200`, so the
client knows to sign in again or use another credential. The answer carries the
challenge
`WWW-Authenticate: Bearer realm="mcp", error="invalid_token", resource_metadata="https://mcp.customdomain.ai/.well-known/oauth-protected-resource"`
and the OAuth error body `{ "error": "invalid_token", "error_description": "..." }`:

- **An API key or a `/token` JWT** is checked with the control plane when it
  arrives, so a revoked or expired one is refused on `initialize` and
  `tools/list` as well as on a tool call. The server reuses that answer for a
  short while (60 seconds for a good credential, 30 for a refused one), and a
  credential revoked within that time is refused by the next tool call it makes:
  the request is answered `401` instead of a result. A check that fails for
  another reason (the control plane cannot be reached) lets the request through.
- **A delegated agent token** is verified locally: an expired one, a bad
  signature or a token issued for another audience is refused at once. A token
  whose grant was revoked still verifies, so `initialize` and `tools/list`
  answer, but its first tool call that reaches the control plane is answered
  `401`.
- **A `CLIENT_ID:CLIENT_SECRET` pair** the control plane refuses is `401` at once
  (see [Authentication](#authentication) for its limit).

The `stdio` transport has no HTTP status: there a refused credential is a failed
tool result with the `error` `unauthorized`.

A request a browser sends from a web page is refused before any of this, unless
the page's origin is the server's own or one its operator lists
(`MCP_ALLOWED_ORIGINS`): it gets HTTP `403` with the JSON-RPC error `-32000`
(`origin not allowed`) and no id. A client that sends no `Origin` header, which
is every desktop, command line and server MCP client, is not affected.

Text a third party wrote (domain names, DNS record values, provider and registrar
names, error text) is data, never instructions. A DNS value is cut at 256
characters and an error text at 600, and the cut is marked `[truncated]`.

## Transports

The server binary (`cmd/mcp`) speaks two transports, selected with `-transport`:

- **`stdio`** (default): line delimited JSON-RPC on stdin and stdout, one message
  per line. This is what a locally launched host (or `mcp-remote`) uses when it
  runs the server as a subprocess. It authenticates with a single static
  control plane credential (`-bearer`, or the `CUSTOMDOMAIN_API_TOKEN` environment
  variable, with the older `JUSTEASY_API_TOKEN` as a fallback).
- **`http`**: a Streamable HTTP style endpoint. These are all of its routes:

  | Route | Purpose |
  | --- | --- |
  | `POST /mcp` | The MCP JSON-RPC endpoint. **Requires `Authorization: Bearer`** (unless started with `-insecure` for local development). |
  | `POST /token` | OAuth 2.0 **client credentials** grant: exchange `client_id` and `client_secret` for a short lived Bearer. Limited per caller IP address (see [Authentication](#authentication)). |
  | `GET /healthz` | Liveness. Answers `200` with `ok`. |
  | `GET /.well-known/oauth-protected-resource` | RFC 9728 protected resource metadata, also served at `/.well-known/oauth-protected-resource/mcp`. The `401` from `/mcp` points here. It names the control plane (`https://api.customdomain.ai`) first as the authorization server, then this server, and lists the four scopes. |
  | `GET /.well-known/oauth-authorization-server` | RFC 8414 authorization server metadata for `/token` (the `client_credentials` grant). The authorization code flow for delegated agents belongs to the control plane, not to this server: see [Agent access](/docs/agents/overview). |
  | `GET /.well-known/agent/mcp.json` | The agent capability manifest: protocol, transport, endpoint, auth and the live tool list. |

  The three `/.well-known/` documents are public, cacheable for an hour and open
  to any origin.

The hosted server is at `https://mcp.customdomain.ai` (the MCP endpoint is
`POST https://mcp.customdomain.ai/mcp`).

## Authentication

`POST /token` proxies the control plane's `POST /v1/tokens` with the `app`
scope: it exchanges an application's `client_id` and `client_secret` (also
accepted as `application_id`) for a widget JWT that acts as the whole
application. Credentials may be sent as HTTP Basic auth, form fields, or a JSON
body; the only supported `grant_type` is `client_credentials`.

```bash
# Mint a short lived Bearer
curl -X POST https://mcp.customdomain.ai/token \
  -u "<APPLICATION_ID>:<CLIENT_SECRET>" \
  -d "grant_type=client_credentials"
# → { "access_token": "eyJ…", "token_type": "Bearer", "expires_in": 900 }
```

`expires_in` is what is left of the token's life, in seconds: 900 (15 minutes,
the control plane's `JUSTEASY_TOKEN_TTL`) for a new token. The server keeps the
token it minted for a client id and secret and hands the same one back, with the
seconds it has left, until a minute before it expires; the next request after
that mints a new one. Mint again when it runs out.

`POST /token` is limited per caller IP address: one request a second, with
bursts of 10. Over the limit the answer is `429` with
`{ "error": "rate_limited" }` and a `Retry-After` header in seconds. Each
exchange carries the caller's address to the control plane, so the control
plane's own limit on minting tokens counts each caller, not the MCP server as a
whole.

`POST /mcp` accepts **three** Bearer forms, so hosts that cannot run the token
dance still authenticate:

1. a JWT minted by `/token`,
2. a console API key (`cd_live_…` / `cd_test_…`, or an older `sk_live_…` /
   `sk_test_…` key, which keeps working),
3. the `mcp-remote` shortcut `CLIENT_ID:CLIENT_SECRET`, which the server exchanges
   for a JWT on the fly and reuses like `/token` does, until a minute before it
   expires. A pair the control plane refuses is `401`. Refused pairs are limited
   per caller IP address: 10, then one more every 10 seconds. Past that, a pair
   the server has not already exchanged gets `429 rate_limited` with
   `Retry-After`, and no exchange is tried; a pair it already holds a token for
   keeps working.

For these **integrator** credentials the MCP server does not validate tokens
cryptographically: it forwards the caller's credential to the control plane,
which is the authority and rejects bad credentials on every wrapped call. It
also asks the control plane about an API key or a `/token` JWT when it arrives
(`GET /v1/billing/standing`, a read every credential may make), so a refused one
gets HTTP `401` before any tool runs (see
[What a call answers](#what-a-call-answers)). Every route a tool calls takes all
three credentials; purchases stay closed to API keys.

**Delegated agent tokens are the exception.** When a person grants an AI agent
access, the agent presents a short lived **ES256** token that the MCP verifies
**locally** against the control plane JWKS (no per request callback) and
enforces the tool's required scope on, so a read only grant can never reach a
connect, disconnect or purchase tool. The token must name this server's endpoint
as its audience (`aud`, RFC 8707), `https://mcp.customdomain.ai/mcp` by default;
a token for another audience is refused with `401 invalid_token`. The control
plane checks every tool call's token again, its grant included, so a token whose
grant was revoked is refused with `401` too. A client that
follows the `401` to the protected resource metadata needs no key: it signs the
person in at the control plane and receives a delegated agent token. See
[Agent access](/docs/agents/overview) for the human first consent flow.

```bash
# Call a tool
curl -X POST https://mcp.customdomain.ai/mcp \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"search-domain-availability","arguments":{"domain":"example.com"}}}'
```

| Flag / env | Purpose |
| --- | --- |
| `-api` / `MCP_API_BASE` | Control plane base URL (default `https://api.customdomain.ai`). |
| `-addr` / `MCP_ADDR` | HTTP listen address (default `:8080`). |
| `-public-base` / `MCP_PUBLIC_BASE` | Public origin used in the discovery documents and as the base of the token audience (default `https://mcp.customdomain.ai`). |
| `-auth-server` / `MCP_AUTH_SERVER` | Public origin of the control plane that issues agent tokens, named first in the protected resource metadata (default `https://api.customdomain.ai`). It must equal the issuer that server reports. |
| `-agent-jwks-url` / `MCP_AGENT_JWKS_URL` | The control plane's JWKS. Empty leaves delegated agent tokens off. |
| `-tenant-rps` / `MCP_TENANT_RPS`, `-tenant-burst` / `MCP_TENANT_BURST` | Tool calls per second (default 5) and burst (default 20) for each caller: each API key or `/token` JWT, each workspace for agent tokens (see [What a call answers](#what-a-call-answers)). 0 turns the limit off. |
| `-link-base` / `MCP_LINK_BASE` | Console URL prefix for guided DNS fallback links. |
| `-preferred-registrar` / `MCP_PREFERRED_REGISTRAR` | Registrar tried first during order resolution. |
| `-purchase-authz-url/-user/-pass` / `MCP_PURCHASE_AUTHZ_*` | The fail closed [purchase authorization callback](#purchase-authorization-callback). Unset means purchases are denied. |
| `JUSTEASY_MCP_USAGE_KEY` | Turns on usage recording to the control plane (`CUSTOMDOMAIN_MCP_USAGE_KEY` is read first; `MCP_USAGE_INGEST_KEY` still works as a fallback). Unset leaves it off. |
| `-allowed-origins` / `MCP_ALLOWED_ORIGINS` | Browser origins (`scheme://host[:port]`, comma separated) allowed to call `/mcp` besides the `-public-base` origin. A request from any other `Origin` gets `403`; one with no `Origin` is unaffected. There is no wildcard, and an entry that is not an origin stops the server at start. |
| `-insecure` / `MCP_INSECURE=1` | Serve `/mcp` without Bearer auth. **Local development only:** the server refuses to start with it unless `-addr` is a loopback address (such as `127.0.0.1:8080` or `localhost:8080`), and never when `SENTRY_ENVIRONMENT` says production. |
