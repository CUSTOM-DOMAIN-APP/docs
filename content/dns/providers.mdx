title: DNS providers
description: Which DNS providers connect in one click, which take an API key, and which take a few records by hand.
---

When a customer enters a domain, we look up its nameservers to see who hosts its
DNS, then offer the easiest way in that works at that provider, in this order:

1. **Sign in with the provider** (OAuth) or **approve access at the provider**:
   one click, nothing to paste, and the one-time token is never stored.
2. **One-click setup** (Domain Connect): the provider applies our signed
   template after the customer approves it on the provider's site, then sends
   the customer back.
3. **An access role** (Amazon Route 53): the customer lets our AWS account
   change the zone, with no secret to paste.
4. **An API key**: the customer creates a scoped credential at the provider and
   pastes it; we write the records for them.
5. **Add the records by hand**: the exact rows to copy, with provider-specific
   steps and a link to the provider's DNS page. This works at every provider.

CustomDomain™ knows more than 150 DNS hosts, registrars and domain platforms,
among them every one of the 100 largest registrars (by domains under
management in ICANN's registry reports for May 2026), and names most of them
from the domain's nameservers. Knowing a provider is not the same as writing
its records: most registrars give no third party a way to change DNS, so for
them the fifth way, with that provider's own steps, is the way in. The tables
below are what the hosted service offers as of 2026-09-29.

The console and the widget read the same verdict from
`POST /v1/domains:check` (its `rails` block and `recommended_rail`), so they
never disagree about what to show. `GET /v1/providers` lists every adapter and
`GET /v1/providers/census` routes every known provider to its mode.

Root domains (`acme.com` rather than `www.acme.com`) depend on what the provider
can hold at the zone apex; see [Root domains](/docs/dns/root-domains). For
records only you know (SES DKIM, a verification `TXT`), see
[Bring your own records](/docs/dns/bring-your-own-records).

## One click, nothing to paste

| Provider | How it connects | Notes |
| --- | --- | --- |
| Cloudflare | **Sign in with Cloudflare** | A root CNAME is fine: Cloudflare flattens it. |
| DigitalOcean, DNSimple, Linode (Akamai Cloud), Netlify, WordPress.com | **Sign in with the provider** | Netlify writes need the domain on Netlify DNS. |
| Vercel | **Install CustomDomain™ on Vercel** | The sign-in is our Vercel integration: install it on the Vercel team that owns the domain. |
| Porkbun | **Approve access at Porkbun** | Porkbun adds an API key named for CustomDomain™ to the account. Porkbun only lets the API change domains that have API Access turned on. |
| NameSilo, Glauca Digital, Domain Chief | **One-click setup** (Domain Connect) | These providers serve our templates. |
| Amazon Route 53 | **Access role** (recommended) | Create a role in your AWS account that lets us change this zone; nothing secret to paste. An IAM access key works too. |

Sign-in and approval tokens are used once to write the records and are never
stored, which also means we cannot repair those records later without asking
again. (A deployment can keep them as encrypted grants instead; see
[Managed connections](/docs/connect-flow/managed-connections#managed-sign-in-grants).)

A self-hosted deployment offers each sign-in once it has registered an app with
that provider; see
[Signing in with the provider](/docs/dns/provider-setup#signing-in-with-the-provider).

### Built, but not switched on yet

These sign-ins exist in the product but are not offered on the hosted service
today, so none of them appears in the console or the widget:

- **Sign in with Google Cloud** (Google Cloud DNS): the customer signs in with
  the Google account that can edit the domain's public Cloud DNS zone, and we
  find the Google Cloud project that holds it. It is switched on once its
  Google client is configured, and until Google verifies the app only the test
  users listed in its Google Auth Platform can sign in. Until then, Google
  Cloud DNS connects with a project ID and an access token.
- **Sign in with Azure DNS** (Azure DNS): the customer signs in with a Microsoft
  account that can list and edit the domain's zone, and we find the Azure
  subscription and resource group that hold its public zone. Until the app has
  a verified publisher, users in other organizations see an unverified
  publisher warning, and an organization that limits user consent needs an
  admin to approve it. Azure DNS can also connect with a subscription ID, a
  resource group and an access token.
- **Grant access at OVHcloud**: a consent page limited to the domain's zone,
  which needs an OVHcloud application for each region a deployment serves. The
  hosted service has none, so OVHcloud connects with an application key.
- **Sign in through the provider's MCP server** (Hostinger, Namecheap,
  Spaceship, Unstoppable Domains and XServer Domain): the provider's own MCP
  server signs the customer in and its DNS tools write the records. Each one
  is switched on only after the provider approves CustomDomain™ and a live test
  passes. Until then Hostinger, Namecheap and Spaceship connect with an API key
  (Namecheap only for accounts that qualify), and Unstoppable Domains and
  XServer Domain take the records by hand.

### Speaks one-click setup, but has not onboarded our templates

GoDaddy, IONOS, Aruba and Squarespace answer Domain Connect discovery but have
not onboarded our templates, so the console does not offer a one-click button
that would end on the provider's error page. Cloudflare and Vercel answer too
and serve none of our templates, and WordPress.com has not onboarded them
either; for those three, the sign-in is the one-click path. Until each provider
onboards the templates, GoDaddy and IONOS connect with an API key, and Aruba
and Squarespace take the records by hand.

### Using a provider token through the API

The BYO-token rail writes a connection's records with the customer's own
credential:

```bash
curl -X POST http://localhost:8080/v1/connections/<ID>/apply \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "cloudflare",
    "credential": { "token": "<scoped-provider-token>" }
  }'
```

`credential.token` carries every part of the credential in one string. The
console builds it from the separate fields; through the API you send it
yourself:

| `provider` | `credential.token` |
| --- | --- |
| `godaddy` | the Personal Access Token (a classic `key:secret` pair still works) |
| `namecheap` | `apiUser:apiKey`, optionally `:userName` and `:clientIp` |
| `route53` | `accessKeyId:secretAccessKey`, plus `:sessionToken` for temporary keys |
| `alidns` | `accessKeyId:accessKeySecret`, plus `:securityToken` for STS credentials |
| `allinkl` | `login:password`, plus `:otp` with two-factor login |
| `arsys` | `hostingDomain:apiPassword` |
| `azuredns` | `subscriptionId:resourceGroup:accessToken` |

## Domains bought through a site builder or shop

Site builders, shops and email suites often sell the domain inside their own
product, and then the records go in on that product's DNS screen. Twenty
platforms where people buy or keep a domain (mostly those, plus
DomainDiscount24 and Just Host) are recognized with their own steps:

- **With nameservers of their own**, named from the nameservers: Microsoft
  365, Fastmail, Turbify, SITE123, BigCommerce, Jimdo and DomainDiscount24
  (which registers domains bought when signing up for Google Workspace), plus
  Just Host, whose zones are named Bluehost because Just Host now sends its
  customers there.
- **On another provider's nameservers**, offered in the widget's provider list
  with their steps: Canva, Strikingly, Webnode, Lovable, Bolt, HighLevel,
  Kajabi, Elementor, Tumblr, Square Online, Yola and Odoo Online.

Where a platform keeps its domains on another provider's nameservers,
detection would name that provider, whose sign-in or API key cannot reach a
zone held in the platform's account. So when the root also points at an
address only that platform hands out, detection names the platform instead and
shows its steps: a Shopify store on Google Cloud DNS's nameservers, a Tumblr
domain on WordPress.com's, and a Canva domain on OpenSRS's shared DNS. The
domain is then connected by adding the records in the platform's own settings.

## Where keys are kept

Sign-ins and one-click setup store nothing, unless the connection is made
[managed](/docs/connect-flow/managed-connections). An API key is used for the
write and kept only when the customer leaves **Remember this key** ticked in the
console (through the API, only when the request sets `remember`). A kept key is
encrypted with AES-256-GCM, scoped to one workspace and provider, used only
server-side, and revocable any time under **Settings, Connected provider
accounts**. Account passwords and short-lived tokens (ALL-INKL.COM, Arsys,
Google Cloud DNS, Azure DNS, Openprovider) are never kept. See
[Remembering a key](/docs/dns/provider-setup#remembering-a-key-optional).

## One-click setup (Rail A)

One-click setup uses the provider-hosted Domain Connect protocol and is
redirect-based: the customer is sent to their provider, which applies a signed
template and returns. There is no server-to-server token. Discovery is via
`TXT _domainconnect.<domain>` and the provider's settings endpoint. Both the
synchronous redirect and the asynchronous variant are supported
(`POST /v1/connections/{id}/domainconnect:start`). The button is only offered
for providers that serve our templates.

Every template we publish names our return domains (`syncRedirectDomain`:
`api.customdomain.ai`, `app.customdomain.ai` and `customdomain.ai`), since
version 2 of the templates was merged into the public Domain Connect template
repository on 2026-09-29. So a synchronous apply always carries a signed
return link: after the customer approves (or cancels) at the provider, the
provider sends the browser back to us, the window closes, and the widget or
console that opened it learns the result. The records still count only once
public DNS shows them; a return that says "done" is never taken as proof.
