To connect a domain with an API key, the customer (or you, on their behalf)
creates a credential at the DNS provider. In the console each part of it is a
**separate labeled field** (Namecheap asks for *API username* and *API key*,
OVHcloud for a region and three keys), next to a link to the page where it is
created and numbered steps, so nobody has to know a wire format. Calling the API
directly, you send the parts joined into one `credential.token` with the matching
`provider` key; the formats are listed in
[DNS providers](/docs/dns/providers#using-a-provider-token-through-the-api).

Where a provider offers it, signing in with the provider, approving access at the
provider, one-click setup or a Route 53 access role needs no key at all; see
[DNS providers](/docs/dns/providers).

> Give every credential the least it needs: permission to read and edit DNS
> records on the zone. Never reuse an account-wide admin key.

## Our server's address, for allowlists

Some providers only answer API calls from addresses on a list. On the hosted
service, DNS writes come from **`34.192.32.132`**. It must be allowed at
Namecheap, Dynadot, Epik, NameBright, Internet.bs, Combell, Vultr and WEDOS, at Subreg if it
refuses the address, and on any IP restriction you set at ClouDNS, NameSilo, TransIP,
GleSYS, Openprovider, NS1, Scaleway or Exoscale (an IAM policy with an IP condition at the
last two). A Plesk or DirectAdmin server must accept calls from it too, since a host can
limit its API to listed addresses and a firewall may block the rest. Moniker takes
the address once, when its support team issues the key, rather than through a self-serve
list. A self-hosted deployment uses its own address (the control plane's
`CONNECT_CLIENT_IP`).

## Cloud DNS

These take a credential created by someone with admin access to the cloud
account. No approval of our service is needed.

### Amazon Route 53 (`route53`)

- **Recommended: an access role.** The console offers it first for Route 53: you
  create a role in your AWS account that lets us change the zone's records, so
  there is no secret to paste, and you can delete the role any time.
- **Or an IAM access key.** In the
  [IAM console](https://console.aws.amazon.com/iam/home#/security_credentials),
  use a user allowed `route53:ListHostedZonesByName`, plus
  `route53:ListResourceRecordSets` and `route53:ChangeResourceRecordSets` on the
  hosted zone, create an access key, and paste the **Access key ID** and
  **Secret access key**. Temporary credentials (keys starting with `ASIA`) also
  need the **Session token**.

### Google Cloud DNS (`gcpdns`)

Open [Cloud Shell](https://console.cloud.google.com/?cloudshell=true) in the
project that holds the zone, signed in with the DNS Administrator role, run
`gcloud auth print-access-token`, and paste the token with the project ID. The
token expires within an hour, so it is used once and never kept.

On the hosted service, use the project ID and access token above. The Google
Cloud DNS sign-in is not offered to anyone there until Google verifies the app.

A self-hosted deployment that registers its own Google client gets **Sign in
with Google Cloud**, which skips all of the above: sign in with the Google
account that can edit the zone, and we find the project that holds it among the
projects that account can see. The zone must be a public Cloud DNS zone (a
private zone is never used) in a project that account can edit, and there must
be only one such zone for the domain; otherwise the sign-in says which account
you used and what to change. While that client is in Google's Testing status,
only the test users listed in its Google Auth Platform can sign in, and its
refresh tokens expire after seven days.

### Azure DNS (`azuredns`)

Open [Azure Cloud Shell](https://shell.azure.com/) as someone with **DNS Zone
Contributor** on the zone's resource group, run
`az account get-access-token --resource https://management.azure.com/ --query accessToken -o tsv`,
and paste the token with the subscription ID and resource group. The token
expires within about an hour, so it is used once and never kept.

**Sign in with Azure DNS** skips all of the above: sign in
with the Microsoft account that manages the zone, and we find the subscription
and resource group that hold it among the subscriptions that account can list
zones in. The zone must be a public Azure DNS zone (a private zone is never
used), there must be only one such zone for the domain, and the account needs
the Reader role on its subscription and a role that can edit the zone (DNS Zone
Contributor); only the directory the account signs in to is searched. Azure
also requires multifactor authentication for the change, and an organization
that limits user consent needs an admin to approve CustomDomain™ once. When a
check fails, the sign-in says which account you used and what to change.

## GoDaddy

GoDaddy's API documentation grants domain management access to any account that
holds at least one domain (or is on a plan with management access) and
recommends Personal Access Tokens; the older key and secret pairs (`sso-key`) are
deprecated for the Domains API. Create a token with only
`domains.domain:read` and `domains.dns:update` and a short expiration. GoDaddy's
one-click setup (Domain Connect) is waiting on GoDaddy to onboard our templates,
and GoDaddy has no sign-in for third parties, so a token or adding the records by
hand are the ways in today. Root domains need A records: GoDaddy has no ALIAS.

## Namecheap

- Namecheap only turns the API on for accounts with **20 or more domains**, a
  **balance of $50** or more, or **$50 spent in the last 2 years**.
- Switch API access on under **Profile**, **Tools**, **Namecheap API Access**
  and copy the API key. Your API username is your Namecheap username.
- **Whitelist `34.192.32.132`**: Namecheap rejects every request from an
  address that is not on the list.
- Domains on Namecheap **hosting** nameservers are edited in cPanel's Zone
  Editor, not through this API; add those records by hand.
- Namecheap's API replaces the whole zone on each write. The adapter reads the
  zone and writes it back with only our records changed.

## Remembering a key (optional)

A provider key is used to write the records. In the console, **Remember this
key for my *&lt;provider&gt;* account** starts ticked: untick it to use the key
once and have it forgotten. Through the API, `POST /v1/connections/{id}/apply`
never keeps a key; connect it as a
[provider account](/docs/connect-flow/provider-accounts) to keep it.

A remembered key becomes a continuous
[provider account](/docs/connect-flow/provider-accounts) for all of that
account's domains, checked against the provider before it is kept. It is:

- **sealed at rest**: encrypted with AES-256-GCM under the control plane's
  `GRANT_ENCRYPTION_KEY`;
- **server-side only**: the plaintext never leaves the server; the browser only
  ever sees the account's details (provider, a label, its domains and last use);
- **one-click reusable**: the next time you connect a domain at that provider,
  **Use saved key** applies the records without re-entering anything, and the
  key puts records back if they disappear (where automatic repair is on) and
  removes them when the domain is removed;
- **revocable any time**: open the account on the console's **Connected
  accounts** page and choose **Revoke**; the key is deleted and its domains stay
  connected.

A deployment without `GRANT_ENCRYPTION_KEY` cannot keep provider accounts, so
its console keeps the key itself (AES-256-GCM under `WEB_SECRET_KEY`, one per
workspace and provider), only to connect more domains. Keys saved that way are
listed under **Keys to move** on the Connected accounts page until you move
them to an account.

Credentials that are passwords or expire within hours are never kept, whatever
the request asks: ALL-INKL.COM KAS logins, Arsys API passwords, INWX, Subreg,
Loopia and Plesk logins, Google Cloud DNS and Azure DNS access tokens, and
Openprovider tokens. A Binary Lane token is never kept either, because it cannot
be limited to DNS. See
[Ownership & setup types](/docs/concepts/ownership-and-setup-types#optional-credential-reuse)
and [Security](/docs/security/overview#provider-credentials).

## Connecting more domains on the same account

For providers whose API can list an account's domains, among them **Cloudflare,
GoDaddy, Amazon Route 53, Namecheap, IONOS, united-domains, Epik, NameBright and
cPanel hosts (including o2switch)**, one key can connect the *other* domains on that account in a single step. After the first apply, the
console offers **Connect more domains**, lists the account's other zones, and
lets you **Select all** or pick a subset, with no need to re-enter the key. See
[Bulk connect](/docs/connect-flow/verify-and-go-live#bulk-connect-more-domains-on-one-account).

## Signing in with the provider

Signing in with the provider needs an OAuth app **registered with that provider
under your company's identity**, which is a business step, not code. The hosted
service has one for Cloudflare, DigitalOcean, DNSimple, Azure DNS
(**Sign in with Azure DNS**; users in other organizations see an unverified
publisher warning until the app has a verified publisher), Linode, Netlify,
Vercel (the CustomDomain™ integration) and WordPress.com. It offers Porkbun's **Approve access at Porkbun**, which needs no
registration, and the sign-in through Dynadot's and Unstoppable Domains' own
MCP servers.

Built, but not yet switched on for the hosted service:

- **Sign in with Google Cloud**, held until Google verifies the app. Connect
  Google Cloud DNS with a project ID and an access token meanwhile.
- **Grant access at OVHcloud**, which needs an OVHcloud application for each
  region served.
- **Sign in through the provider's MCP server** for Hostinger, Namecheap,
  Spaceship, XServer Domain and Muumuu Domain. A deployment switches each one
  on by listing it in `MCP_SIGNIN_PROVIDERS`; the hosted service lists only
  Dynadot and Unstoppable Domains, and adds the others once the provider
  approves CustomDomain™ and a live test passes.

Until a sign-in is on, API keys, one-click setup and adding records by hand
cover the same providers.

A self-hosted deployment switches a sign-in on with the app's credentials:
`OAUTH_<PROVIDER>_CLIENT_ID` and `OAUTH_<PROVIDER>_CLIENT_SECRET` (for Google
Cloud DNS, `OAUTH_GCPDNS_CLIENT_ID` and `OAUTH_GCPDNS_CLIENT_SECRET`), an
OVHcloud application key and secret per region, or an entry in
`MCP_SIGNIN_PROVIDERS` for an MCP server sign-in. Porkbun's approval needs
none of these. Every sign-in also needs `OAUTH_STATE_KEY` and the page origins
allowed to receive its result, `OAUTH_ALLOWED_RETURN_ORIGINS`.

A sign-in is used once and dropped unless the deployment lists the provider in
`OAUTH_MANAGED_PROVIDERS` and sets `GRANT_ENCRYPTION_KEY`. The hosted service
keeps sign-ins at Cloudflare, DigitalOcean, DNSimple, Linode, Netlify, Porkbun,
Vercel and WordPress.com by default, encrypted, and the console's **Keep this
sign-in** box lets you use one once instead. See
[Managed sign-in grants](/docs/connect-flow/managed-connections#managed-sign-in-grants).
