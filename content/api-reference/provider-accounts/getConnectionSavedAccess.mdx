      - content: >-
          The saved access resolver's answer for the connection's domain: the
          workspace's kept provider keys that may write its records for the
          caller, best first, with no sign in and no new key. The same answer is
          `rails.saved_access` on `POST /domains:check`, and the console's
          Connect page offers it first. Its rules, in order: the key is at the
          domain's provider (`?provider=` asks about another than the one
          detected), kept (`continuous`) and still working (a key that is only
          nearing its end counts); an API key caller gets the workspace's keys
          that serve the connection's application and that it may use (an admin,
          an owner or the key's maker), never a key an end user's own sign in
          made; a key whose scope holds the domain's zone is `ready`; otherwise
          a key made at a secure sign in a member started in the console may be
          offered with `ready: false`, after one read with it showed it reaches
          the zone (at most 3 reads a call, each answer kept 10 minutes), and
          using it adds the zone to its scope. One entry per provider account.

          An end user's widget token (scope `connect`) gets that end user's own
          keys, and only theirs, when all of these hold: the token is bound to
          the connection's domain and was minted with the end user's
          `end_user_ref` (not one of the install samples' `user_42` and
          `customer_123`); the application allows it (`end_user_saved_access` on
          the application, never in test mode); the e-mail that tells the end
          user their key was reused can be sent (the `end_user_contact` flag is
          on, an address was given for the token at mint or is held for the
          domain's connection, and the application's end user mail has a live
          sender); and the key is the end user's own, in this application, made
          at a sign in that same token vouched for, and not held at GoDaddy for
          now. Any other widget token gets an empty list, and a token bound to
          no domain, or to another end user than the connection's, is refused
          with `403` `token_not_bound` or `token_wrong_end_user`, as
          `browser:start` refuses it. An end user's entry carries `from_domain`,
          the newest domain of theirs the key already serves, the neutral label
          `<Provider> key` and no `key_name` or `application_id`. It only offers
          the key: `POST /connections/{id}:use-saved-access` and the `409`
          `saved_access_available` of the sign in routes do not apply to an end
          user's token yet.

          A delegated agent token reads it with `domains:read` (the MCP's
          `find-saved-access`), for a connection of the application its grant is
          bound to (another application's is `404`). It gets the workspace's
          keys that serve that application, never a key an end user's own sign
          in made, and a token without `domains:read` is `403`. No entry carries
          a `key_name` for it (the name holds an application's name, and a key
          of the grant's own application can carry another application's after a
          share). A key made for another application and shared with the grant's
          own one reads as `<Provider> key`, with no `application_id`: the label
          the agent made it with names the other application's domain.
