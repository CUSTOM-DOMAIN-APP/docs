      - content: >-
          Changes the settings of a domain a person edits after it is set up:
          `client_label` (the name of the client it is for), `www_redirect` (a
          root domain's redirect to `www`) and `redirect_to` (forward every visit
          to another site). Send only what changes. A body that changes nothing
          answers `200` and writes nothing.

          **Who may call it.** A server side credential only: an API key of a
          member who may change domains (member, admin or owner; a viewer's key is
          `403`), or an `app`-scoped token for a connection of its own
          application. An end user's `connect`-scoped widget token is refused
          `403`, its own connection included, and so is a delegated agent token:
          the name, the `www` redirect and above all the forward decide where the
          domain's visitors go, so the platform that owns the domain decides, not
          the person connecting it or an agent acting for them. A connection of
          another workspace answers `404`.

          A test mode domain takes `client_label` only (`403`
          `sandbox_not_allowed` for the redirects).

          **The www redirect** changes the records the domain needs. A zone we
          host is rewritten at once; a domain whose records were written through a
          connected provider account is rewritten when `move_rewrite` is on; any
          other domain is reported with `connection.records_outdated` and the
          answer's `customer_action_required` is `true` when a record was added. A
          live domain stays live while that record is missing.

          **Forwarding** is held to one validator, the same one `POST
          /connections/{id}/power` and `/power:repower` use for their
          `redirect_to`: see `redirect_to` in the body. A value equal to the one
          stored is not checked again.

          Every change is recorded in the audit log as `connection.updated`, with
          the before and after of the fields that changed.
