      - content: >-
          Read-only feature detection. Returns the provider, the chosen
          `setup_type`, whether automatic setup is possible, whether the
          OAuth-into-provider and one-click setup rails are available,
          capability flags (`ns_support`, `wildcard_support`,
          `cname_flattening`, `spf_override_support`, `caa_support`),
          social-login support, any `record_conflicts` observed in public
          DNS (records the automatic write would replace), and any
          `advisories` (warnings that replace nothing, such as a CAA record
          that blocks Let's Encrypt). Within /v1 a `caa-blocks-letsencrypt`
          advisory is also listed in `record_conflicts`, as before `advisories`
          existed; it never counts toward `will_fallback_to_manual`, and new
          clients should read it from `advisories`. Unknown providers degrade to `setup_type: manual`.


          Apex pre-flight: `apex_supported` reports whether the provider can
          host a CNAME-like record at the zone root, and `apex_message` is
          returned when this particular target needs one the provider cannot
          host, so an apex connection that would be refused at apply time is
          refused here instead, before any connection is created.


          The answer is for one application (where its domains point:
          `target_mode` and the apex strategy). A widget JWT checks for its own
          application. An API key checks for `application_id`, which must be an
          application in the key's tenant (404 otherwise), or for the key's own
          application when it is omitted.


          A delegated agent token needs `domains:read` or `domains:connect` and
          checks for its own application; naming another application is a `403`.
