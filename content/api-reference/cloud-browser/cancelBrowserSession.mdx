          Idempotent: a session that is already over answers its own state. During
          `applying` it stops at the next change boundary, never inside a change. A
          `navigator.sendBeacon` cannot set headers, so this route (and `:event`) also
          accepts the token in the body, as `{"token": "..."}` with a content type of
          `text/plain` or JSON.


          The member who started an account sign in may also cancel it with an API
          key, on the console's signed visitor forward, in any state before its end:
          this is how a sign in is abandoned at the list of domains. The key the
          session made, if any, is dropped and named as `left_key` (the name it was
          made with and the provider's page that deletes it); the answer carries it.
          While a keep step is storing the key it is `409` `browser_wrong_state`. The
          identity rules are those of the read above, and an API key without the
          console's forward is read as the popup's (`401`).
