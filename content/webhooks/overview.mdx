Register HTTPS endpoints to receive signed events as connections progress and as
monitored domains drift.

## Register an endpoint

```bash
curl -X POST https://api.customdomain.ai/v1/webhooks \
  -H "Authorization: Bearer <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://api.acme.example/webhooks/cd","events":["connection.live","domain.record_missing"]}'
# → { "id": "whk_…", "url": "...", "events": [...], "secret": "whsec_…", "created_at": "..." }
```

Register from your server with an API key (or an app-scoped widget token). A
widget token minted by `POST /v1/tokens` has `connect` scope and is rejected
with 403. The `url` must be a public `https` URL; `localhost` and private or
link-local addresses are refused.

The `secret` (`whsec_…`) is returned **once**. Store it to verify signatures. An
empty `events` array subscribes to all events; `"*"` also matches all.

Manage endpoints: `GET /v1/webhooks` lists them (secrets omitted; tenant-wide
with an API key, app-scoped with a widget JWT; `?app_id=` narrows to one
application) and `DELETE /v1/webhooks/{id}` removes one (204). The tenant-wide list
leaves out a [test mode](/docs/guides/test-mode) application's endpoints unless
`?app_id=` names it, so a test endpoint is never mistaken for a live one.

## Event catalog

| Event | Fires when |
| --- | --- |
| `connection.created` | A connection is created. |
| `connection.applied` | Records were written through a rail (`data.via` = `automatic` for OAuth, `async` for one-click setup, unset for API-token apply). |
| `connection.live` | Every desired record resolved; the connection is `live`. |
| `connection.failed` | A `propagating` connection's records never appeared within 24h. |
| `connection.records.updated` | A [managed](/docs/connect-flow/managed-connections) connection was re-applied (`POST /v1/connections/{id}:reapply`); its desired records were re-written and the connection re-verified. |
| `connection.reapply.failed` | A managed re-apply push failed; if the stored grant was revoked, the connection is flagged for re-consent. |
| `connection.disconnected` | A domain was [removed](/docs/connect-flow/offboarding). `removal` says what happened to its DNS records: `choice`, `outcome` (`removed`, `partly_removed`, `kept`, `manual`, `in_use`, `not_needed`, `failed`), `via`, and the records `removed`, `restored`, `left_in_place` and `failed`, plus any `manual_steps`. |
| `connection.records_outdated` | A non-managed connection's applied records were computed against a superseded edge target; the envelope carries a `connect_link` to re-run setup. |
| `certificate.issued` | The edge issued the first certificate for a domain. |
| `certificate.renewed` | The edge renewed a domain's certificate. |
| `certificate.failed` | Issuing or renewing failed (once per failure episode); the edge keeps retrying. |
| `certificate.expiring` | A certificate that has not renewed expires in 14, 7 or 3 days, or expired. The certificate events carry a `certificate` object (`status`, `issuer`, `issued_at`, `expires_at`, `days_left`, `error`). See [Certificates](/docs/connect-flow/certificates). |
| `domain.record_missing` | [Monitoring](/docs/connect-flow/monitoring) confirmed a record disappeared or was repointed. `drift` carries `record_type`, `verdict` (`record_missing` or `record_changed`), `expected`, `observed` and `action` (`auto_fixed`, `fix_failed` or `action_required`). |
| `domain.record_restored` | A previously missing record is observed again. |
| `domain.purchased` | A [domain purchase](/docs/sell/buying-a-domain) completed: the domain is registered (and only then is the card captured). |
| `purchase.error` | A purchase failed; the card authorization was released. |
| `purchase.confirmation.expired` | A pending purchase's checkout session timed out unpaid; the buyer never confirmed. Release the cart. |
| `secure_status` | A certificate's provisioning status changed (`secure_status` on the envelope). Sent only where the deployment has Secure on (`SECURE_ENABLED`). |
| `power_status` | A reverse-proxy host's provisioning status changed (`power_status` on the envelope). |

When the connection carries a recorded diagnosis at emit time, the envelope also includes `error_code` and `error_message` (for example `propagation_timeout`, `access_denied`, `ProviderAuthenticationError`, or `setup_incomplete` on a stalled pending connection), so a receiver need not fetch the connection to learn why.

That table is the **complete** vocabulary: it is exactly the set the platform can
emit, and the `events` enum in the [OpenAPI spec](/v1/openapi.json) matches it.
An unknown event string is still accepted at registration, but it can never be
delivered, so subscribe only to the events above.

> **Status:** the drift events (`domain.record_missing` / `domain.record_restored`)
> are produced by the hourly Monitor sweep, which **delivers** them only where
> `MONITOR_ALERTS_ENABLED=1`. With the flag off (the hosted default) the sweep
> still runs in shadow mode but no drift webhooks are sent. `domain.purchased`
> (and `purchase.error`) require the Sell purchase path, which is live on the
> hosted service (gated by `SELL_PURCHASE_ENABLED`).

## Payload envelope

Deliveries are a flat JSON object:

```json
{
  "id": "evt_…",
  "type": "connection.live",
  "user_id": "tenant-or-end-user-ref",
  "domain": "app.customer.com",
  "subdomain": "app",
  "provider": "cloudflare",
  "setup_type": "automatic",
  "propagation_status": "success",
  "data": {
    "records_propagated": [ { "type": "CNAME", "host": "app.customer.com", "value": "edge.customdomain.ai" } ],
    "records_non_propagated": []
  },
  "created_at": "2026-07-07T12:00:00Z"
}
```

`propagation_status` is `pending`, `success`, or `timeout`. On propagation
events, `data` carries the per-record propagated / non-propagated arrays. Fields
that don't apply to an event are omitted.

Additional conditional fields ride connection events:

- `user_id`: the connection's `end_user_ref`, echoed so integrators can
  associate lifecycle events with the originating tenant or end user. Omitted
  when the connection was created without an `end_user_ref`.
- `updated_objects`: the records a write actually created or changed. Present on
  `connection.applied` and `connection.records.updated` only; the events that just
  observe a connection never claim to have written anything.
- `redirection_status`: `pending`, `success` or `failed` for the apex↔www
  redirect, and present only on connections created with `www_redirect: true`.
- `connection_id`: the connection the event is about, on connection,
  certificate and drift events.
- `sandbox`: `true` on an event from a [test mode](/docs/guides/test-mode)
  application, whose domain is a simulated `.test` name. Real events carry no
  `sandbox` field. Test mode events are signed and delivered like any other, so
  you can test your receiver end to end, and a receiver that writes to a real
  customer's account should check the field and skip them.

## Delivery & retries

- A delivery succeeds on any `2xx`. Respond within 15 seconds.
- Network errors, `5xx` and `429` are retried with exponential backoff
  (about 30 seconds, then doubling, capped at 6 hours between tries), up to 12
  attempts in total. Any other `4xx` is treated as a permanent failure and is
  not retried.
- Inspect outcomes: `GET /v1/webhook-deliveries` returns the 100 most recent
  settled deliveries (`attempts`, `status_code`, `delivered`, `error`; filter
  with `?app_id=` and `?type=`). The log keeps the last 50 per application.
  A delivery that is still being retried appears once it succeeds or is given
  up on.

Endpoints should be **idempotent**: the same event can arrive more than once on
retry. Deduplicate on the envelope `id`, or on `domain` + `type`.
