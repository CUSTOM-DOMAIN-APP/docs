A **connection** is one customer domain being set up under an application. Its
`id` doubles as the `jobId` the widget and webhooks report. Every connection
carries a **desired record set** and a **status**. The desired record set is the
list of records that point the domain at the edge, and it is the one source of
truth for them.

## The connection lifecycle

The status machine is deliberately small:

```
                 apply a way (sign in / one-click / secure sign-in / API key)
  pending ─────────────────────────────────────────────▶ propagating ──▶ live
     │                                                          │
     └──────────── manual: records seen in public DNS ─────────┘        │
                                                                        │
                        propagating > 24h with records unseen ──▶ failed
                                                                        │
                    :recheck / re-create / edge traffic ──▶ pending ◀───┘
```

| Status | Meaning |
| --- | --- |
| `pending` | Created; records not yet seen. Checked every five seconds at first, backing off to every 15 minutes; after 72 hours it stays `pending` with `error_code: setup_incomplete` and is re-checked every six hours. **Never fails on its own.** |
| `propagating` | Records were written (by a rail) and are being checked against public DNS. |
| `live` | Every desired record resolves to its intended value (see the note under Propagation to live on which types are value-checked). Re-applying records to a live connection moves it back to `propagating`. The edge serves TLS for the host (only when the record set includes an edge record; an email-only set is verified but never served). |
| `failed` | A `propagating` connection's records never resolved within 24 hours (`propagation_timeout`). Only the poller sets it. **Not terminal.** See Retrying. |

There is no separate ownership step. **The way to connect proves control.** A
sign-in with the provider, a one-click setup, a secure sign-in to the account
that holds the domain, or a scoped API key each shows the customer controls the
zone. With DNS hosting, the owner changes the domain's nameservers at its
registrar. When records are added by hand, we wait for them to appear. A
`pending` connection has no deadline. After 72 hours it is checked less often,
with the diagnosis `setup_incomplete`.

## Retrying

`failed` is a diagnosis, not an end. Three things move a failed connection back
to `pending`, with a fresh window and a cleared diagnosis:

- `POST /v1/connections/{id}:recheck`, which is *Resume* or *Check now* in the console.
- `POST /v1/connections` again for the same domain. It returns the revived row with `200`.
- Real traffic reaching the edge for the host.

Until then you can still read the diagnosis in `error_code` and `error_message`,
and on the webhook events.

## The authoritative record set

`GET /v1/connections/{id}/records` returns the one record set everything uses.
The widget shows it, the provider sign-in writes it, and our checks verify it.
Before anything is applied, it holds the default edge record:
`CNAME <host>` to `edge.customdomain.ai`, TTL 3600, or your own edge target. Once
a way to connect writes records, it returns the stored set instead.

## Propagation to live [#propagation--live]

We check every `pending` and `propagating` connection against public DNS, and we
check values, not just names:

- A CNAME must resolve to the expected target.
- An A or AAAA record must contain the exact address.
- A TXT record must contain the expected value.

`MX`, `SPFM`, `SRV` and `CAA` records are written but their values are not
checked, so they count as found. We look for connections due a check every five
seconds. A young connection is due every
5 seconds for its first 5 minutes, then every 30 seconds until 15 minutes,
every 2 minutes until an hour, and every 15 minutes after that; a rail's write
makes it due at once. When the public resolver does not show a record yet
(it may still remember the name as missing, or hold the old value), the check
asks the zone's own nameservers, and every one that answers must serve the
value, so a fresh write is usually verified within seconds.
When all records resolve, the connection moves to `live` and `connection.live`
fires exactly once, never twice.

## Error codes

A connection that hits a problem keeps its status and records the cause in
`error_code` / `error_message`, which also ride the webhook events. A rail that
refuses or fails a write does not mark the connection `failed`. Codes you can
see on a connection:

| `error_code` | Meaning |
| --- | --- |
| `setup_incomplete` | Still `pending` after 72 hours; re-checked every six hours |
| `propagation_timeout` | `propagating` for over 24 hours with records unseen (status `failed`) |
| `dns_write_failed` | The provider rejected the write of the records |
| `apex_not_supported` | The provider cannot serve a root domain for this connection |
| `forwarding_not_supported` | The provider cannot realize the requested forwarding |
| `spf_merge_failed` | An `SPFM` merge would exceed 10 lookup mechanisms or 255 characters |
| `domain_already_connected` | Another account already serves this domain; the connection is not promoted to `live` |

## Idempotency and tenancy [#idempotency--tenancy]

`POST /v1/connections` is idempotent per application + domain: if the app already
has a non-failed connection for the domain, that connection is replayed (`200`)
instead of a duplicate being created (a widget token for a domain another
customer connected gets `403 token_wrong_end_user` instead, see
[Idempotency](/docs/connect-flow/create-a-connection#idempotency)). Every object is tenant-scoped: an API
key sees all its tenant's connections; a widget JWT sees only its
application's. Cross-tenant ids return `404`, never another tenant's data.

## Drift

After a domain goes live, we keep checking its records against live DNS (see
[events](/docs/webhooks/overview#event-catalog)). If a record disappears or
points somewhere else, `domain.record_missing` fires. When it comes back,
`domain.record_restored` fires, so you can tell the customer.
`POST /v1/monitor:check`, and the SDK's `checkRecords`, run the same check on
demand.
