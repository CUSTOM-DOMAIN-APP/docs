CustomDomain™'s default `docker-compose.yml` / `docker-compose.prod.yml` stack runs
with **zero third-party egress**. The cloud observability integrations documented
here are strictly opt-in: each is a no-op until you set its environment variable,
and every one can be re-pointed at a backend you host yourself.

> The cloud observability integrations (Sentry errors, OTLP tracing → Grafana Cloud via a Grafana Alloy forwarder, PostHog analytics) are opt-in and no-op when their env vars are unset; the default docker-compose.yml/.prod.yml stack makes zero calls to any of them. A self-hoster gets zero third-party egress by default, or can point OTEL_EXPORTER_OTLP_ENDPOINT / the /metrics scrape at their own backend. There is no forced SaaS dependency; the Apache-2.0 "run the whole thing yourself" guarantee is preserved.

## Environment variables

Every variable in this section is optional. Leaving one unset disables the
corresponding integration: the service starts and runs normally, it just emits
no telemetry to that destination.

| Variable | When unset | What it does |
|----------|------------|--------------|
| `SENTRY_DSN` | Sentry not initialized | Error reporting for the Go services (control-plane, edge, MCP). |
| `SENTRY_ENVIRONMENT` | events unlabeled | Environment label (e.g. `development`, `production`); only read when `SENTRY_DSN` is set. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | no OTLP export | OTLP/HTTP endpoint the Go services export traces (and metrics) to. |
| `METRICS_ADDR` | endpoint off | Serves the control-plane Prometheus `/metrics` on a separate internal port. |
| `EDGE_METRICS` | endpoint off | Set to `1` to expose `/metrics` on the edge's internal health port (`:8081`). |
| `APP_SENTRY_DSN` | console error reporting off | Error reporting for the console, in the browser and on the server. Passed to the app container as `NEXT_PUBLIC_SENTRY_DSN` (build time) and `SENTRY_DSN` (runtime). |
| `NEXT_PUBLIC_POSTHOG_KEY` | analytics off | PostHog project key for product analytics in the console. Baked in at build time. |
| `NEXT_PUBLIC_POSTHOG_HOST` | `https://us.posthog.com` | PostHog UI host (`https://eu.posthog.com` for an EU project); only used when the key is set. |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog ingestion host the console's same origin `/ingest` proxy forwards to (`https://eu.i.posthog.com` for an EU project). |

These keys also appear, commented out, in the `.env.example` file at the root of your self-hosted checkout.

### Error monitoring (Sentry)

Set `SENTRY_DSN` to your Sentry project DSN to enable error and exception
reporting in the three Go services. When it is unset, the Sentry client is never
initialized and the services make no calls to Sentry. `SENTRY_ENVIRONMENT` labels
the events (for example `production`). Tracing is **not** sent to Sentry: the
Sentry `TracesSampleRate` is `0`; distributed tracing stays on OpenTelemetry (see
below). The DSN can point at Sentry's SaaS or at a self-hosted Sentry instance.

The console (`apps/app`) reports its own errors too, in the browser and on the
server. Set `APP_SENTRY_DSN` in the host's `infra/.env`; `docker-compose.prod.yml`
passes it to the app as `NEXT_PUBLIC_SENTRY_DSN` (a build argument, baked into the
browser bundle, so rebuild the app image after changing it) and as `SENTRY_DSN`
(read at runtime by the server). Unset, nothing is initialized and nothing is
sent. It is errors only: no tracing, no session replay, no cookies, no request
bodies and no user, and the query string and fragment are cut from every URL.
Browser events go to the console's own origin at `/monitoring`, which the server
forwards to Sentry, so the Content-Security-Policy needs no Sentry host and ad
blockers do not drop them. That tunnel understands Sentry Cloud DSNs; for a
self-hosted Sentry the DSN's origin is added to `connect-src` instead.
`SENTRY_ENVIRONMENT` labels the console's events as well (default `production`).
Source maps are not uploaded, so browser stack traces are minified.

### Traces and metrics (OpenTelemetry / Prometheus)

`OTEL_EXPORTER_OTLP_ENDPOINT` is the OTLP/HTTP endpoint the Go services export to.
In CustomDomain™'s hosted stack this points at the Grafana Alloy forwarder
(`http://alloy:4318`), which fans telemetry out to Grafana Cloud. A self-hoster can
point it at **any** OTLP-compatible collector they run (Grafana Alloy, the
OpenTelemetry Collector, Tempo, or Jaeger), or leave it unset for no export.

`METRICS_ADDR` serves the control-plane's Prometheus `/metrics` endpoint on a
separate internal port (for example `:9090`). Keep it on the compose network or
loopback only, never the public API port. `EDGE_METRICS=1` exposes `/metrics` on
the edge's internal health port. Scrape either with your own Prometheus-compatible
collector.

### Per-domain traffic

The edge counts, per connected domain, requests by status class, bytes sent,
origin response time and approximate visitors, and posts the counts to your own
control plane once a minute (`/internal/traffic`, authenticated with
`EDGE_ASK_SECRET`). Nothing leaves your deployment and no client IP address is
stored. It is on by default; set `EDGE_TRAFFIC=off` on the edge to switch it off.

### Visitor addresses (`IP_RETENTION_DAYS`)

The control plane records the IP address and country of the request behind each
domain lookup (a search, check, price, connect or purchase, from the console, the
widget, the API, the MCP server or an agent), each connect widget funnel step and
each audit event, and the console records the address of each sign in. They are for
security, abuse prevention and support, and nothing sends them to a third party. They
are kept without an end date (`IP_RETENTION_DAYS` defaults to `0`). Set a whole number of
days from 1 up and, after that many days, the address is set to NULL and the row stays,
with its country (anything else is `0`). The control plane's hourly lifecycle sweep does
this for its tables and the console's daily upkeep for its own; set the same value on
both (the production compose file forwards it to both). Sign in events are kept without
an end date too unless `SIGN_IN_RETENTION_DAYS` sets a window on the console.

Cloudflare's headers are believed only when the request really came through Cloudflare.
The console's server passes the visitor to the control plane in a signed header, keyed by
`JUSTEASY_PROVISION_SECRET`, so that value must be the same on both: without it the control
plane records the console's own address for console traffic. A deployment that is not
behind Cloudflare records the address of the connection as its proxy saw it, with no
country.

### Domain intel (`DOMAIN_INTEL_ENABLED`, `DOMAIN_INTEL_HTTP`)

The control plane can collect public facts about the domains people enter (a search,
check, price, connect or purchase, and the company domain of a sign up address) and say
whether each domain's website is alive: live, parked, redirecting, erroring, with no
website, or unreachable. It is **off by default**.

- `DOMAIN_INTEL_ENABLED=true` starts a background worker. It finds new domains by
  polling the tables the control plane already keeps, reads their public DNS records
  through public resolvers, and stores the result (apply migration `0067` first).
- `DOMAIN_INTEL_HTTP=true` also lets it make one request for each domain's home page
  (HTTPS, then HTTP, with up to five redirects) from your server, as `CustomDomainBot`.
  It does nothing without the first switch. The request only reaches public addresses
  on ports 80 and 443, sends no cookies or credentials, and keeps only the page title.

A domain is checked at most once a day however many people entered it, and one
workspace can add at most 200 new domains a day (counted in Redis when `REDIS_URL` is
set, otherwise per process). Set both variables back to `false` to stop; what was
collected stays in the `domain_intel` table. `GET /internal/admin/domains/intel` (the
management key) reads it. If you turn this on, say so in your own privacy policy: the
requests come from your server's address and name `CustomDomainBot`.

### Product analytics (PostHog)

`NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST` and `POSTHOG_HOST`
configure product analytics in the console. The key and the UI host are
`NEXT_PUBLIC_*`, so they are exposed to the browser, so never put a secret in them.
Point the hosts at PostHog Cloud or at your own self-hosted PostHog instance. When
the key is unset, no analytics are sent and the console makes no call to PostHog.

The browser SDK is wired in. Events go through the console's own origin at
`/ingest`. They are sent while analytics is on, which is the default for a
visitor who has not chosen (the consent banner offers Confirm and Change), and
never when the browser sends Global Privacy Control or Do Not Track; turning
analytics off stops them at once. What is sent is narrow on
purpose: the product events the console emits, clicks on buttons and links (no
text and no attributes) and page views, plus session recording for signed in
people (described below). Every URL is cut to its path before it is sent,
nothing is sent from the password reset, email verification, invite, shared view
and email preferences pages, and a signed in person is identified by their
account id only, never an email or a name.

The key and the two hosts are baked into the app image, so rebuild it after
changing them, and take all three from the same PostHog project and region: a
mismatch drops events without an error.

Opt out, not opt in. Until the visitor chooses, analytics and marketing are on,
and the banner at the bottom of the page asks them to Confirm that or Change it.
Nothing is stored until they do. A stored choice always wins, and so does a
browser that sends Global Privacy Control or Do Not Track (those visitors are
never asked and nothing optional runs). A "no" given under an earlier version of
the choice is kept. In a new browser the default waits until the console has
asked the signed in account (a saved "no" is read first), or for a couple of
seconds if it cannot. If you self host with an analytics key set and want visitors
to be asked before anything runs, this build has no switch for that: the default
lives in `assumedChoice()` in `apps/app/src/lib/consent.ts`, and the banner's
words in `apps/app/src/components/legal/replay-copy.ts`. Earlier releases sent
nothing until a visitor accepted the banner, so check this against your own
privacy notice before you upgrade.

#### Session recording

With the key set, the console also records how people use it, as a replay of
the screen: clicks, scrolling and page views. It records only while analytics
is allowed: on for a visitor who has not chosen, off once they turn it off, and
never when the browser sends Global Privacy Control or Do Not Track.

- The public pages a visitor sees before they have an account (the home page,
  the docs, the free tools and the sign up form) are recorded without anyone
  signed in, under PostHog's anonymous id. When the visitor signs up, the
  identify call links that id to the account, so the journey from the first page
  to the console reads as one recording.
- The console and the welcome intake are recorded only once PostHog knows who
  is signed in, so those recordings carry the account id as their distinct id
  and nothing else.
- Every field a person types into is replaced with asterisks in the recording,
  so what they type is not recorded. The one exception is a field that asks for
  a domain name (the welcome intake and Connect a domain), marked
  `data-replay-show`: its value is shown, so you can see which domain someone
  tried. A password, email or phone field is never shown, whatever its markup.
  The recording does show what the page displays, such as the names of domains
  and DNS records.
- Nothing is recorded on the sign in, password reset, email verification,
  invitation, shared view, email preferences, Domain Connect return, agent
  consent and billing pages, or on the API keys, webhooks, MCP, agent access and
  security settings pages, and nothing outside the public pages, the console and
  the welcome intake is recorded at all. Anything that shows an API key, a token
  or a signing secret is also blanked wherever it appears.
- Browser console output, request and response contents, network timing and
  frames from other origins (such as Stripe's card form) are never recorded, and
  every URL in a recording is cut to its path.
- Recording stops at once when the visitor withdraws the choice, signs out or
  opens one of those pages, and starts again when they leave it.

The PostHog project decides whether recording happens at all: turn on Session
replay in the project settings, with Mask all inputs on and console logs and
network capture off, and set the retention there. CustomDomain™'s hosted console
keeps recordings for 30 days. Switching Session replay off in the project stops
all recording without a rebuild, because the console only starts a recording the
project allows. The recorder script loads through the same `/ingest` proxy as the
rest of PostHog, and the content security policy adds `blob:` to `worker-src` for
its compression worker when the key is set; nothing else changes.

A visitor turns recording off in Cookie settings (Settings, then Privacy) by
switching Analytics off, or by sending Global Privacy Control or Do Not Track.
Recording became part of the Analytics choice in version 2 of the cookie choice,
so a "yes" given before is asked again, once, the first time they open the
console after an upgrade to this release; a "no" is kept.

## Running the Grafana Alloy overlay

The base stack does not run Grafana Alloy. CustomDomain™ ships an out-of-band
overlay (`infra/docker-compose.alloy.yml`, driven by `infra/config.alloy`) that
runs one Alloy forwarder to collect OTLP traces, metrics, and logs and ship them to
Grafana Cloud. Before you enable it, read the caveat below.

> infra/config.alloy is pre-wired to CustomDomain™'s own Grafana Cloud tenant (hardcoded basic-auth user ids + prod-us-east ingest endpoints); a self-hoster who runs docker-compose.alloy.yml as-is points THEIR logs/metrics/traces at CustomDomain™'s tenant. The Alloy path is NOT a simple env-var repoint: config.alloy must be replaced/re-pointed at the self-hoster's own Grafana stack, with their own GRAFANA_CLOUD_TOKEN set in the host's infra/.env (the overlay reads it from the compose project's env by substitution; this page previously named a separate infra/observability.env, which the overlay stopped using several releases ago and which has never been committed here). No credential ships in this repo. The default no-overlay zero-egress claim for the base stack remains true.

## Shared cookies and analytics beacons

Two optional variables control how the console's cookie choice and anonymous
visitor id are shared with your other sites.

| Variable | When unset | What it does |
|----------|------------|--------------|
| `NEXT_PUBLIC_CONSENT_COOKIE_DOMAIN` | derived from the host | Scope of the cookie choice (`cd_consent`) and the anonymous visitor id (`cd_anon`). On a customdomain.ai host they are shared with `Domain=.customdomain.ai`; anywhere else they stay host-only. Set `host` to force host-only, or a parent domain of your console host (for example `example.com`) to share them with your marketing site. Baked in at build time. |
| `ANALYTICS_BEACON_ORIGINS` | CustomDomain™'s own sites | Comma-separated origins allowed to send first-party analytics events to the console's `/api/e` collector from another site, with credentials. Other origins are refused. Read at runtime. |

The collector never stores an IP address or user agent. Events from another
origin keep only the page path, the referrer (origin and path), UTM tags and a
short list of allowed properties.

## Sign-in holds (`OAUTH_HOLD_PROVIDERS`)

A DNS provider sign-in is offered once its app credentials are set; see
[Signing in with the provider](/docs/dns/provider-setup#signing-in-with-the-provider).
This variable withholds a sign-in that is otherwise configured.

| Variable | When unset | What it does |
|----------|------------|--------------|
| `OAUTH_HOLD_PROVIDERS` | nothing is held | Comma-separated provider ids (for example `gcpdns`) whose sign-in is not offered to anyone, even when the provider's `OAUTH_<PROVIDER>_CLIENT_ID` and `OAUTH_<PROVIDER>_CLIENT_SECRET` are set. Empty or `none` also holds nothing. The provider still connects with an API key or access token. |

The hosted service holds `gcpdns` until Google verifies the app.

## Push notifications

The console's bell (the in-app inbox) needs no configuration. Push, a
notification from the browser that arrives with the console closed, needs a
VAPID key pair, and is off until you set one.

Generate a pair with `scripts/generate-vapid-keys`, then set:

| Variable | Where | What it does |
|----------|-------|--------------|
| `VAPID_PRIVATE_KEY` | control plane | The private key that signs each push. A secret: keep it out of git and out of logs. |
| `VAPID_PUBLIC_KEY` | control plane | The public half of the same pair. The production compose also bakes it into the console image (as `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, which the browser needs to subscribe), so set it once and rebuild the image after changing it. Empty hides the push controls. |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | console, at build time | Only when you build the console without that compose (`next dev`, your own image): the same value as `VAPID_PUBLIC_KEY`. |
| `VAPID_SUBJECT` | control plane | A `mailto:` or `https:` contact the push services can reach. Empty uses `mailto:support@customdomain.ai`. |

With both keys empty, push stays off and the bell works. If the pair is mistyped
or the two halves do not match, the control plane logs the reason at startup and
leaves push off instead of failing each message. Changing the pair later makes
every device's subscription invalid, and each person turns notifications on again.
See [Notifications](/docs/guides/notifications) for what people see.
