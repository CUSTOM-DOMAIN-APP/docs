CustomDomain™ doesn't yet cut numbered releases. The hosted service is
continuously updated, and the API is versioned separately (below).

## API versioning policy

The public API is versioned by URI major (`/v1`) and is **additive-only within a
version**: new optional fields and endpoints can appear, but existing fields
never change meaning or disappear without a new major version. See the
[API reference](/docs/api-reference) for the current surface.

## Notable milestones

- **November 2, 2026: the console after two review sessions, and a quieter secure sign-in.**
  - **Navigation.** The console has one menu. The Classic or New choice under **Settings → General** is gone and every
    workspace is on the grouped menu. **Settings → Notifications** now holds your own switches with **What we send**
    under them, and **Settings → General** shows the console's version with the time it was built. See
    [Navigation](/docs/getting-started/console#navigation).
  - **Secure sign-in.** A plan that only adds records is approved by the sign-in window itself, with no Review screen:
    your customer sees "Getting things ready", then "Making the changes", then Done. Review still appears when a record
    is replaced or removed, when the plan changed, or after an approval that failed. The window no longer mentions an
    API or a key. At Squarespace, the code it emails before a DNS change now waits for your customer instead of failing
    the run. See [When your customer approves a change](/docs/guides/secure-sign-in#review).
  - **Widget.** **Try it live** leads with **Open the widget**. **Install** has **Get your API key** and **Hand it to
    your coding agent**, a prompt that never contains a secret. The Design preview adds the screens **Instructions
    sent**, **Email setup** and **Remove a domain**. See [Install the widget](/docs/getting-started/console#install).
  - **Domains.** The attention banner is gone (the **Needs attention** filter shows its count), each row says who
    added the domain, and a domain waiting on DNS reads **Checking DNS**, **Records found** or **Not finished**.
  - **Analytics.** **Most common stopping point** now names the real last step instead of "Closed the widget".
    **Traffic** says what a request is and counts the pages the edge writes itself in **Data sent to visitors**; our own
    domain checks are not counted. **Providers** shows started, connected, rate and top reason stuck, plus **Time to go
    live** and **How domains connect**. The API adds `top_stuck`, `top_stuck_count`, `median_seconds_to_live` and
    `time_to_live` to [`GET /v1/analytics/connect`](/docs/api-reference/analytics/getConnectAnalytics). See
    [Analytics](/docs/getting-started/console#analytics).
  - **Sign in and sign up.** Passkey, Google and GitHub are one row of icon buttons, and Google One Tap shows where
    Google sign in is set up. On sign up it waits for the Terms box. See
    [Sign up and verify](/docs/getting-started/console#1-sign-up-and-verify).
- **November 2, 2026: the account's sheet in the console, and who may change an account.** Opening a connected account
  shows one sheet: rename it, change which domains its key may configure, choose which applications may use it,
  connect more of its domains, renew it by signing in again, remove it, and run Check now. Only an admin, an owner or
  the member who connected the account can do these, and the control plane enforces the same rule (a customer's key:
  admins and owners only). A name is 1 to 80 characters with no control or invisible characters. Check now and
  connecting more domains are recorded in the audit log (`provider_account.checked` and
  `provider_account.domains_connected`) under whoever made the call. See
  [The account's sheet in the console](/docs/connect-flow/provider-accounts#the-accounts-sheet-in-the-console) and
  [Who can manage an account](/docs/connect-flow/provider-accounts#who-can-manage-an-account).
- **November 2, 2026: Overview follows the application you picked, and you can bring the setup list back.** With the
  new menu (**Settings → General → Navigation**) and two or more applications, picking one in the switcher makes
  **Overview** count only its domains and show only its widget figures. Its links to pages that narrow by application keep it: a count,
  **View all**, the source links and a platform's **Keys and webhooks** shortcut open the same application's list, so the
  number you click is the number you land on (the widget, your team and your connected accounts open as they are). The
  **Usage** card and the setup list are still the whole workspace's. **Dismiss** on the setup list hides it
  for you on every device; **Help → Show the setup list** brings it back and it stays through a reload. See
  [Console](/docs/getting-started/console#navigation).
- **November 2, 2026: checks at a DNS provider have an hourly limit for each workspace.** A workspace can now make 60
  reads an hour at DNS providers to find out what a key reaches: the list of a key's domains, the read of a new domain's
  zone when a key made at a secure sign-in is widened or connects a domain outside its scope, Check now, and the reads
  that find which saved key can act for a domain. When the hour's reads are spent, those calls answer `429`
  `reach_quota` with a `Retry-After` of the seconds until the hour ends, read nothing, change nothing and spend nothing
  from the hour (a call that needs several reads takes them all or none, so a smaller call that fits is still answered);
  finding saved keys simply offers fewer until the hour turns, and using a saved key by name
  (`POST /v1/connections/{id}:use-saved-access`) that was not read for that reason answers `429` too, not
  `409 saved_access_not_usable`. An answer kept from a read in the last ten minutes costs nothing, and
  the daily health check of every kept key is outside the limit, so it is never held back. Self-hosters set it with
  `REACH_CHECKS_PER_TENANT_HOUR` (`0` turns it off). See
  [Checks at the provider have an hourly limit](/docs/connect-flow/provider-accounts#checks-at-the-provider-have-an-hourly-limit).
- **November 2, 2026: "Host its DNS instead" starts one domain's DNS hosting from the console, and a waiting move has its buttons.**
  On a domain's page, **Change** then **Host its DNS instead** (and a line on the connect page) opens a sheet that
  lists only the ways that would work for that domain: a saved account at the registrar that you may use, **Secure
  sign-in**, or **Change it yourself**. When the move cannot start, such as the plan's limit of hosted domains or a
  registrar that keeps its own nameservers, the sheet says why and has nothing to start. A move that waits for the
  registrar sign-in now shows **Sign in at** the registrar on the domain's DNS tab, a move that stopped before the
  registrar changed shows **Try again**, which starts the same move again (the same way, and the same saved account),
  and one that stopped after shows **Move back** first. The API gains
  `GET /v1/connections/{id}/nameservers:offer`, which says what a start would accept; an agent token reads it too, and
  sees that it may not start a move while the application's DNS hosting is off, or that its grant lacks
  `domains:connect`. A move uses only a saved account its caller may use: a member's key may use the accounts they
  connected and the ones an admin or an owner connected, never another member's (`403 forbidden`, before any move
  exists), for a start, a resume and a move back, whether the call names the account or the start picks one. An app
  scoped token uses none (it moves by hand, by the secure sign-in or with a key it sends), skipping the zone check on
  a resume takes someone who may use the account the move was started with, and the DNS host account of an
  application's setting is chosen under the same rule (a member may still change only the mode and keep the account
  the application has). A move back whose answer the registrar lost and that could not be read back leaves the move
  stopped, so a later check does not send the new nameservers again. A failed
  move's `next_action` for `retry` now carries the move's `path` and, for `api`, its `provider_account_id`. See
  [Start one domain's move](/docs/guides/nameserver-migration#start-one-domain) and the
  [console guide](/docs/getting-started/console#how-we-reach-a-domain).
- **November 2, 2026: a domain's client name, www redirect and forwarding can be changed after setup.** On a
  domain's **Settings** tab, **Who it is for**, **www redirect** and **Forwarding** are now fields, each with its own

  `www_redirect` and `redirect_to`; `POST /v1/connections`, `POST /v1/connections:bulk` and the account connect take
  `client_label`; and `redirect_to` on `POST /v1/connections/{id}/power` and `power:repower` is held to the same
  checks (an `http://` address is now refused). `end_user_ref` is not the client's name: it stays your id for the end
  user and is still set once. A client's name written before this is shown as that id until a name is given. See
  [A domain's settings](/docs/getting-started/console#domain-settings) and
  [forwarding](/docs/connect-flow/forwarding#from-the-console).

- **November 1, 2026: stored secrets can be bound to their workspace and record, and the encryption key can be rotated.**
  The control plane can now seal provider keys, sign-in grants, MCP sign-in client secrets, webhook signing secrets and
  SMTP passwords in a v2 format: the value is tied to its workspace and record, so a copy of it placed in another
  workspace's record does not open, and it names the key it was sealed under, so a key can be added, made current and
  retired without a gap. With none of the new settings set, the control plane writes and reads exactly what it did
  before: `GRANT_ENCRYPTION_KEY` works as before and `GRANT_ENCRYPTION_WRITE` defaults to the old format (it only
  counts, at start, how many stored secrets are in each format). The new settings `GRANT_ENCRYPTION_KEYS`,
  `GRANT_ENCRYPTION_WRITE`, `GRANT_ENCRYPTION_READ_V1` and `WEBHOOK_ENCRYPTION_KEYS` take effect only when you set
  them, and a combination that cannot work is refused at start instead of guessed: a key list with no
  `GRANT_ENCRYPTION_KEY` must also set `GRANT_ENCRYPTION_WRITE=v2`, and a valid list beside an unusable
  `GRANT_ENCRYPTION_KEY` stops the start. A `credctl` tool in the control plane image
  (`status`, `verify`, `rewrap`) moves stored secrets between formats and keys and checks them. See
  [Encryption keys](/docs/security/overview#encryption-keys-self-hosted).

- **November 1, 2026: a second secure sign-in uses the key we stored, where the provider's page still lists its row.** When
  your customer signs in again at a provider whose key page lists each key with its name and account (Name.com's
  token table), CustomDomain™ now looks for the row of the key it made the first time: its exact name and its exact

- **November 1, 2026: one customer's widget token never gets, reads or changes another customer's connection, zone or nameserver move.**
  Two customers (end users) of one application, each with a widget token for their own domain, could reach each other's
  connection. `POST /v1/connections` for a domain the application already had answered the existing connection, so a
  token for another customer's exact domain was handed that connection's id, and the managed DNS and nameserver
  routes then read that customer's whole zone, wrote records into it, and resumed, confirmed or rolled back their
  nameserver move. Now `POST /v1/connections` answers a widget token whose `end_user_ref` is not the existing
  connection's, or that has none while the connection names one, `403 token_wrong_end_user` and shows nothing of
  it (a failed connection is not revived for it either). A connection that names no customer, your API key, an `app`
  scope token, a delegated agent token and the customer's own repeat call are answered as before. Every managed DNS route
  and every nameserver route (`GET`, `:migrate`, `:rollback`) answers `403 token_wrong_end_user` for a connection that
  names another customer; a zone that holds another customer's connection (or one you made with your API key for
  another name) answers `409` "the DNS of acme.com is already hosted by CustomDomain™ for someone else"; a nameserver
  move whose connection was removed is never taken over by a customer's call, and only your API key resumes it.
  Every other route that takes a connection's id now answers the same `403 token_wrong_end_user` to another customer's
  token before it reads or changes anything: the connection read and its records, certificate, diagnosis, SSL and Power
  reads; applying records, starting a sign in, Domain Connect or the Route 53 role; and `DELETE
  /v1/connections/{id}/grant`, `:reapply` and `:recheck`. An id handed out while the bug was live no longer reads or
  writes anything for another customer. Removing a domain and reading its monitoring, services or timeline keep their
  rule and answer `403 forbidden`. For managed DNS and nameserver moves a connection you made with your API key (it
  names no customer) is a token's only when its domain is one the token is bound to, so a token with an `end_user_ref`
  and no `domain` owns none of those, and a token with neither counts only the domain of the connection the call is
  about. Share links keep working: the person who opens a link acts as the end user who shared it (your API key shares
  as the customer of your connection for the one domain the link names). One rule governs a link: its token owns exactly
  what the token that made it owned, and may touch only the shared domains. A link made by a token that names no
  customer and is bound to no domain counts only the one connection a call is about as its own, so a zone that links
  several of the shared domains is not its own; a link made by a token that names a customer and is bound to no domain
  owns none of your connections that name no customer, and reaches only the domain it was made for, not the customer's
  others. A widget token can share only a domain whose connection it owns by the rules above (`403
  token_wrong_end_user` and no link otherwise; a domain with no connection yet can be shared), so a customer's token
  that is bound to no domain cannot share your connection's domain to itself and read its zone. A link is a credential
  to set that one domain up and nothing more: it cannot remove the domain (`DELETE`, `:disconnect` and the sign-in to
  remove answer `403 forbidden`), cannot set the customer's contact address on any connection, cannot start a sign-in
  in reconnect mode to renew the customer's key, is never offered the customer's kept keys, and a key made at a sign-in
  it starts is not the customer's own and never replaces a key the customer already keeps. A sign-in in reconnect mode
  on a key the customer's own sign-in made is refused with `403 forbidden` before it starts unless it is that
  customer's own session (a reconnect link on a connection that names no customer, an API key without the console's
  signed forward, the console), and a reconnect link whose key was replaced by another, or whose connection is gone,
  answers `404` like an expired link instead of opening the plain flow.

  **Compatibility.** A widget token with no `end_user_ref` that acts on a connection that names a customer now gets
  `403 token_wrong_end_user` on the repeat `POST /v1/connections`, `:recheck`, `:reapply`, `DELETE .../grant`, the
  connection reads and writes above, and every managed DNS and nameserver move route, where it got `200`. That includes a
  connection the same token created by sending `end_user_ref` in the request body. If you create connections with an
  `end_user_ref`, mint each widget token with the same `end_user_ref` and the `domain` it is for. Share links keep
  working, with two changes: a share link can no longer remove a connection that names no customer (it could before),
  and links made before this release stop working (opening one answers `404` like an expired link and spends it, which
  the console words as "invalid or expired, ask for a fresh link"), so ask for a new one. See
  [Idempotency](/docs/connect-flow/create-a-connection#idempotency),
