CustomDomain™ doesn't yet cut numbered releases. The hosted service is
continuously updated, and the API is versioned separately (below).

## API versioning policy

The public API is versioned by URI major (`/v1`) and is **additive-only within a
version**: new optional fields and endpoints can appear, but existing fields
never change meaning or disappear without a new major version. See the
[API reference](/docs/api-reference) for the current surface.

## Notable milestones

- **Four more API key rails.** Huawei Cloud DNS, WEDOS, Moniker and Zone.ee: paste a key or a
  login and the records are written for you. Moniker was by hand until now. A root domain on any
  of them gets A records. See [Provider setup](/docs/dns/provider-setup).
- **101domain and Mythic Beasts, and netcup's CloudDNS tab.** Paste a 101domain API key or a
  Mythic Beasts key ID and secret and the records are written for you; a root domain on either
  gets A records. netcup customers whose domain moved to the CloudDNS tab now connect the same
  way as everyone else on netcup, with the API key alone. Muumuu Domain (ムームードメイン) gets a
  sign in through its own MCP server, built and not switched on yet; until then its records are
  added by hand on ムームーDNS. See [Provider setup](/docs/dns/provider-setup).
- **Seven more API key rails.** Domeneshop, Scaleway, INWX, Gcore, Subreg, Loopia and hosting.de:
  paste a key or a login and the records are written for you. Scaleway, INWX and Subreg were by
  hand until now. The INWX, Subreg and Loopia logins are used once and never stored, and Subreg may
  ask you to allow `34.192.32.132` in its API settings. A root domain on any of them gets A records.
  See [Provider setup](/docs/dns/provider-setup).
- **The Privacy Policy now describes domain checks.** When you enter a domain, or sign up
  with an address at your company's own domain, we check from our own servers whether that
  domain responds on the public internet, to help you connect it: we read its public DNS
  records and make one ordinary request for its home page, as CustomDomainBot. We keep what the
  domain publicly answers (its DNS records, the status, where it redirects, the page title and
  the page size), never the page itself, cookies or credentials, and check each domain at most
  once a day. [What CustomDomainBot does](/docs/security/domain-checks), and how to ask us to
  stop.
- **Your first domain is free.** A new workspace connects its first domain without adding a card,
  so you can see it go live before deciding anything. Once it is live, the console offers the
  14 day free trial once (skip it and it stays skipped), and a card is needed to connect more
  domains or create API keys. Domains that are already connected keep working either way.
- **Get notified in your browser.** After you sign up, the Overview offers once to send a notification to this
  browser when a domain goes live or needs attention. It only appears in browsers that support it, and you can
  change it any time under Settings, Notifications. The sign in page now reads "Connect custom domains, without the
  friction".

- **Billing shows how you paid, and checkout opens with your email.** A workspace that paid with Link,
  Apple Pay or Google Pay now shows that on the Billing page instead of "No card on file". Checkout fills
  in the email you signed up with, so it goes straight to your payment details. Apple Pay and Google Pay
  are offered at checkout on devices that support them.
- **The Privacy Policy now says what we log about domain searches and IP addresses.** When you
  search for, check, price, connect or buy a domain (in the console, the widget, the API, our MCP
  server or through an agent), we record the domain that was typed, what happened and the IP
  address and country of the request, and we keep the IP address of each sign in and of each
  account or workspace change. We use it for security, abuse prevention and support, and each
  address is kept for as long as your account exists. Nothing is sent to our analytics tool.
- **Session recording, only with your consent.** If you allow analytics, we now record how you use
  the console (clicks, scrolling and page views, never what you type) so we can improve it. Fields
  you type into show as asterisks, keys, tokens and signing secrets are blanked, and the sign in,
  billing and agent access pages are never recorded. Recordings are kept 30 days, and you can turn
  them off any time under Settings, Privacy, or by sending Global Privacy Control or Do Not Track.
  Because analytics now includes recording, everyone is asked about cookies once more.

- **Signing in with Google or GitHub checks your email address.** If Google or GitHub has not
  confirmed your email, you land on *Check your email* and the link we send finishes the sign in.
  An account that already uses an address can be opened by Google or GitHub only once they have
  confirmed it: until then, sign in with your password, then add Google or GitHub under Settings,
  Security. If you were invited by email, signing up from the invite link works as before.

- **Add Google or GitHub after you sign up with a password.** Once the welcome is done, the
  Overview offers once to add Google and GitHub as more ways to sign in: Add Google, Add GitHub
  or Not now. It connects only an account that uses the same email address as yours, an answer is
  remembered on every device, and accounts that came in with Google or GitHub are not asked. The
  same buttons are under Settings, Security.

- **Sign in with Azure DNS.** Azure DNS connects through a Microsoft sign-in where a
  deployment has set it up: we find the Azure subscription and resource group that hold
  the domain's public zone, so there is no subscription ID, resource group or access
  token to paste, and a failure says which Microsoft account was used and what to
  change. Azure requires multifactor authentication for the change, and until the app
  has a verified publisher, users in other organizations see an unverified publisher
  warning and an organization that limits user consent needs an admin to approve it.
  The API key way stays beside it.

- **Two more API key rails.** Combell (including combell.nl accounts) and Wix: paste a
  key and the records are written for you. Combell's API comes with Reseller Hosting and
  needs `34.192.32.132` on the account's IP restrictions; a Wix key must be made by the
  account owner and works for domains on Wix's nameservers. See
  [Provider setup](/docs/dns/provider-setup).
- **Two more API key rails.** NS1 (IBM NS1 Connect) and netcup: paste a key and the
  records are written for you. NS1 needs the DNS permission Manage zones, writes an
  ALIAS at the root and leaves records it steers with filters alone; netcup needs a
  customer number, an API key and the API password, works on its own nameservers and
  does not change domains on CloudDNS. See [Provider setup](/docs/dns/provider-setup).
- **Long console pages became short summaries with views.** A domain opens to its status,
  the one thing to do and five facts, with DNS, Certificate, Edge, Traffic and History as
  tabs. Settings, Analytics, API and SDK, an application, Billing, Team and Monitor work the
  same way, and a row opens a side panel for its detail instead of a longer page. The
  connect step opens the recommended way and keeps the others one click away. Every old
  address and in page link still lands on the right view, and the back button returns to
  where you were.
- **Sign up asks you to agree to the Terms.** The sign up page has a box for the Terms
  of Service and Privacy Policy, and none of the ways of creating an account (email,
  Google, GitHub) goes on until it is ticked. If you already have an account you are
  asked once, the next time you open the console, and again only when the Terms change.
  We keep the version you agreed to and when, and nothing else with it. API keys and the
  widget are not affected.
- **The card moves from sign-up to the moment you need it.** Signing up no longer
  asks for a card at every sign-in. The setup flow is offered once, skipping it
  sticks, and you can look around, check domains and design your widget without
  one. A card (which starts your 14 day free trial, with nothing charged until
  it ends) is asked for when you create an API key, create an application or
  connect your first domain, with a link that brings you back to where you were.
  Keys and applications you already have keep working.
- **Checkout on the page, in the console's own look.** Starting a free trial,
  subscribing to a plan, buying a domain and saving a card for an agent no longer
  open a pop-up with Stripe's own page in it. The checkout takes the place of
  what you were looking at (the plan list, the search results, the permissions
  under the agent's name), with a way back. The order, the promotion code, the
  total and the buttons are part of the console, in light and dark, on a phone
  and on a computer; a trial says when the first charge happens, and a domain
  says that your card is held, not charged, until it is yours. Only the card
  fields are Stripe's, in a frame, so card details still never reach
  CustomDomain™. If Stripe cannot offer this checkout, the console shows
  Stripe's own, on the page, in its place.
- **If checkout cannot load, there is a way on.** When something stops the
  payment form from loading (a blocker, a network that does not reach Stripe, a
  page left open across an update), the page now says so and Start again opens
  Stripe's own checkout on the page, instead of a dead end. We are told when it
  happens, with Stripe's error code and never what you typed. A promotion code
  cannot be changed while a payment is going through, and Deny stays available
  while you add a card for an agent. If you run your own deployment: the control
  plane should go live before the console, and an older one is asked again
  without the new field so checkout keeps working while you update it; setting
  `CHECKOUT_UI_MODE` to `embedded` switches the console back to Stripe's own
  checkout with a container restart and no rebuild.
- **The welcome says what email and agents mean here, and offers names you can
  buy.** Setting up email means adding the sending and receiving records (MX, SPF,
  DKIM and DMARC) for the provider you choose; we do not host mailboxes. Running an
  AI agent means giving it access over MCP or an API key so it can search for,
  buy and connect domains. When the domain you type is not registered, the welcome
  lists names close to it that you can buy, with the first year price, and the
  search opens with the name already filled in. If you manage domains for clients,
  the welcome asks whose domain it is and words the next steps to match.
- **Your logo sits properly in the connect widget.** With a logo set, the widget
  no longer stacks it over the stock globe tile: the logo stands alone in the
  header, a little larger (32 pixels tall by default, still adjustable in the
  widget designer) and with more room above it, on every screen. A logo you
  supply for the domain icon slot still shows.
- **Notifications, in the console and on your phone.** A bell at the top of the
  console holds your latest notifications and counts the ones you have not
  opened: a domain going live, a domain that needs attention, DNS records that
  changed or were put back, certificate problems, billing, purchases, agents
  and DNS providers that need reconnecting. They go to owners and admins. Turn
  on push under **Settings → Notifications** and the same notifications arrive
  on your phone or computer even with the console closed. A domain waiting for
  DNS offers **Get a ping when it is live**, so you can close the tab. You
  choose, for each kind, whether it reaches the bell, push, both or neither;
  the routine ones (agent actions, a customer using the widget, a teammate
  joining) are in the bell only until you want more. Your browser asks before
  anything is turned on, each device is listed and removable, and signing out
  takes a browser off the list. The emails you already get are unchanged. See
  [Notifications](/docs/guides/notifications).
- **A welcome that starts from what you want.** The first thing the console asks
  is what you want to use your domain for: a website, email, an AI agent, a white
  label, subdomains, letting your customers connect their own domains, or managing
  domains. Each answer gets only the steps it needs, with what we could work out
  (your company, your website, your logo and brand color) filled in for you to
  confirm. You can see your brand on the real widget as you set it, connect your
  domain with the real connect flow, and finish on what you now have instead of a
  settings page. Your place is saved, so you can leave and come back, and you can
  change what you are doing any time from the checklist.
- **Design the widget, one look for each application.** **Widget → Design**
  now shows the widget itself, running on example data, instead of a sketch of
  it. Step through every screen (enter the domain, detect the provider, sign in,
  apply, connected, and the rest), look at light and dark, a computer and a
  phone, and see each change in the open widget as you make it. The header is
  balanced around your logo, a logo can have its own version for dark mode, one
  brand color brings its hover, text and dark mode shades, and one corner radius
  reaches every corner. New options: the name in the first heading, the logo's
  size, background and text colors, a font, the pop-up's width and shadow, the
  close button, the progress steps, and which options the widget offers (set up
  manually, an AI assistant, email the instructions, hosted DNS). Each
  application keeps its own look, with a workspace default behind it. Nothing in
  the preview is sent anywhere. In the SDK, `whiteLabel` takes `logoDark` and
  `logoPlate`.
- **Removing a domain, certificates, monitoring and connected accounts.**
  Removing a domain now asks what to do with the DNS records CustomDomain™
  added: remove them (putting back what each replaced) or keep them. When the
  access used to connect was not kept, one more sign-in or key does it, or the
  exact steps are listed. Each domain's certificate, its renewal and its
  history are visible, with alerts before an unrenewed certificate expires.
  Monitoring checks every live domain each hour, confirms drift before acting,
  and says what it found and what it did; each domain shows whether records
  CustomDomain™ wrote are put back automatically when they disappear. Each
  domain lists the services it uses. Provider keys and kept sign-ins are
  managed in **Connected accounts**, with one time or continuous access for
  some or all domains; an admin, an owner or the person who connected an
  account manages it. New on the API: [removal](/docs/connect-flow/offboarding),
  [certificates](/docs/connect-flow/certificates),
  [monitoring and services](/docs/connect-flow/monitoring) and
  [provider accounts](/docs/connect-flow/provider-accounts); in the SDK,
  `removeDomain()`.
- **Traffic for every domain.** Each domain the edge serves shows its
  requests by the kind of answer, bandwidth, server errors, how fast its
  origin answered and approximate visitors, and **Analytics** shows the
  workspace's edge traffic with the busiest domains. A domain connected for
  DNS only says why it has no figures instead of showing zeros. No visitor's
  IP address is stored. New on the API: `GET /v1/connections/{id}/traffic`
  and `GET /v1/traffic`.
- **Starter replaces the Free plan.** Starter is $10 a month for 10 domains a
  year, and every new workspace starts with a 14 day free trial (the card is
  added at checkout and charged when the trial ends). Workspaces that were on
  Free get 14 days from their first sign-in to choose a plan and are not
  charged before those days end; after that, new connections pause until a plan
  is chosen, while connected domains keep working. Billing is now managed by a
  workspace's owners **and admins**, with promotion codes, plan changes, card
  updates and invoices in the console. See
  [Plans & quotas](/docs/billing/plans-and-quotas).
- **Every domain opens, whatever its application.** A domain of an
  application other than the one the console is switched to used to read
  "Domain not found", and its actions failed the same way. The console now
  acts on every domain in your workspace, and a domain that isn't live says
  what happened and what to do next. On the API, a tenant API key reaches the
  apply rails, provider sign-in, one-click setup and the Route 53 access role
  for a connection of any application in its tenant, and
  `POST /v1/domains:check` and `POST /v1/sharing/connect` take an
  `application_id`.
- **A page for each application.** Its domains, API keys, widget and where its
  domains point, with rename and delete. `DELETE /v1/applications/{id}` is
  new; it is refused for the default application and while an application
  still has domains.
- **Viewers stay read only.** A viewer can no longer mint widget tokens, buy a
  domain, connect a provider account's other domains or list the domains a
  provider key manages, in any application: those need a member, admin or owner,
  and a viewer who tries gets a 403. The **Applications** pages tell viewers the
  same and hide what they cannot use. On the **API & SDK** page, the key your
  console itself uses is labeled "This console" and has no Revoke button,
  because revoking it would cut the console off from your workspace; a
  teammate's key is marked "Team member" and warns before it is revoked.
- **The 100 largest registrars, and the platforms that sell domains.** More
  than 150 DNS hosts, registrars and domain platforms are now known by name,
  among them all of the 100 largest registrars, and the widget has step by
  step instructions for 125 of them. Twenty platforms where people buy or
  keep a domain are recognized too, mostly site builders, shops and email
  suites (Microsoft 365, BigCommerce, Canva, Tumblr, Kajabi and more).
  Detection also names the platform in three cases where it keeps its domains
  on another provider's nameservers: a Shopify store on Google Cloud DNS, a
  Tumblr domain on WordPress.com and a Canva domain on OpenSRS's shared DNS now
  get that platform's steps instead of a sign-in that could never reach the
  zone. See
  [DNS providers](/docs/dns/providers#domains-bought-through-a-site-builder-or-shop).
- **Records written for you verify in seconds.** A write through a sign-in,
  one-click setup or an API key is checked within five seconds, a new
  connection is checked every five seconds for its first five minutes, and
  when public DNS still has an old or missing
  answer we ask the zone's own nameservers (every one that answers must serve
  the record). If the wait passes a minute, the widget now says it is unusual
  and that closing the window is safe, because the domain connects on its
  own. See
  [Apply records & go live](/docs/connect-flow/verify-and-go-live#watch-propagation--live).
- **One-click setup brings people back.** Version 2 of our Domain Connect
  templates was merged into the public template repository on 2026-09-29, and
  every template now names our return domains. A one-click apply carries a
  signed return link, so after approving at the provider the customer lands
  back in the widget or the console, which learns the result at once, instead
  of being left on the provider's page. NameSilo, Glauca Digital and Domain
  Chief serve our templates. See
  [One-click setup](/docs/dns/providers#one-click-setup-rail-a).
- **Three more API key rails.** Tencent Cloud DNSPod (China and International
  sites), Infomaniak and Internet.bs: paste a key and the records are written
  for you. A DNSPod key is best created for a CAM sub-user limited to DNS
  records, and Internet.bs needs `34.192.32.132` on the account's API
  allowlist. See [Provider setup](/docs/dns/provider-setup).
- **Sign in with Google Cloud.** Google Cloud DNS connects through a Google
  sign-in: we find the Google Cloud project that holds the domain's public
  zone, so there is no project ID or access token to paste, and a failure says
  which Google account was used and what to change. Until Google finishes
  reviewing the app's Cloud DNS permissions, Google shows an "unverified app"
  notice before its approval screen. A project ID and an access token still
  work too.
- **Sign in through a registrar's MCP server, built and not switched on
  yet.** Hostinger, Namecheap, Spaceship, Unstoppable Domains and XServer
  Domain run MCP servers with their own sign-in and DNS tools, and the
  control plane can now sign in through them (`flow: mcp_oauth` on
  `oauth:start`). None is switched on: each waits for the provider to approve
  CustomDomain™ and for a live test. Until then Hostinger and Spaceship
  connect with an API key, Namecheap with an API key only for accounts it has
  opened its API to (20 or more domains, a $50 balance or $50 spent in two
  years, with our server's address on the account's whitelist), and
  Unstoppable Domains and XServer Domain by adding the records by hand.
- **More ways to connect without pasting a key.** Vercel connects through the
  CustomDomain™ integration install, Porkbun through "Approve access at
  Porkbun", and Akamai Cloud (Linode) and DigitalOcean through sign-in.
  OVHcloud's consent page per region (Europe, Canada, US) is there for
  deployments that register OVHcloud applications; the hosted service has
  not. Deployments can keep a sign-in as an encrypted grant
  (`OAUTH_MANAGED_PROVIDERS`) so the connection stays managed and can be
  re-applied.
- **Route 53 without access keys.** A customer can create a limited IAM role in
  their own AWS account from our template instead of pasting an access key.
- **Seven new API key rails.** United Domains, Epik, NameBright, ALL-INKL.COM,
  cPanel hosts (including O2switch) and Arsys.
- **One-click only where it works.** Domain Connect is offered only after the
  provider's own API confirms it serves the exact template, and the button
  appears by itself once a provider onboards it.
- **Provider fixes.** Hetzner moved to the Hetzner Console API, Hostinger to its
  new API host, Name.com to its Core API and Openprovider to `/v1`; Namecheap,
  Dynadot, Porkbun, deSEC, Constellix and a dozen others follow each provider's
  current documentation.
- **Safer agent approvals.** The screen where you approve an AI agent now
  shows where its access would go and whether that address is a known
  assistant, a program on your computer, or unverified, and blocks agents that
  pretend to be Claude, ChatGPT or another brand. Agents can identify
  themselves with a published client metadata document instead of registering,
  and their refresh tokens now rotate on every use. See
  [The OAuth flow](/docs/agents/oauth-flow).
- **Provider logos.** The widget, the console and the DNS instruction emails
  show the logo of your customer's DNS provider wherever they name it, and the
  logo of the service a record still points to ("still points to Squarespace").
- **CustomDomain™, one word.** The product now reads CustomDomain™ everywhere:
  the console, the widget, emails and these docs. Nothing in the API changed
  name.
- **New API key prefix.** New keys start with `cd_live_` or `cd_test_`. Keys
  that start with `sk_live_` or `sk_test_` keep working; there is nothing to
  rotate. See [API keys](/docs/authentication/overview).
- **Hand the DNS step to an AI assistant.** On the manual step, the widget
  offers one ready prompt with the exact records for the customer's provider,
  and opens it in ChatGPT, Claude, Perplexity or Grok (Gemini and Copilot get
  it on the clipboard). The prompt holds no link or credential.
- **Send the records to whoever manages DNS.** The widget emails the
  instructions, with an optional note, to the person who can make the change,
  and the console's domain page does the same for your teammates, inviting
  them to your workspace if you are an admin.
- **Nameserver hosting, rolling out.** Where a provider offers no automatic
  setup, the widget can offer to host the domain's DNS: the owner changes the
  nameservers once and every record after that is written for them. See
  [Managed DNS](/docs/dns/managed-dns).
- **Upload a logo.** Widget branding takes an uploaded logo as well as a URL;
  any common image format is turned into a clean PNG sized for the widget.
- **See where each domain came from.** Connections carry `created_via`
  (`widget`, `console`, `api`, `agent` or `mcp`), and the console's Domains
  page filters by it.
- **A calmer, clearer widget.** The manual step now leads with a link to the
  provider's DNS panel and shows each record's live status; the widget moves
  smoothly between steps, fills the screen on phones and respects reduced
  motion.

- **The widget tells people exactly what is wrong.** While a customer adds
  records by hand, the widget reads public DNS for each one and shows found,
  not found yet, or what answers instead ("Still points to Squarespace"), and
  catches the common mistakes: the full hostname typed into the Name field,
  Cloudflare's proxy turned on, a leftover IPv6 record. The same check is on
  every domain's page in the console and at
  `GET /v1/connections/{id}/diagnose`.
- **Root domains are a choice, not a trap.** Typing `acme.com` now asks
  whether to connect the root and `www` (recommended), the root alone, or a
  subdomain, and says how that provider points a root. `domains:check`
  reports it up front as `apex_strategy`.
- **Sessions no longer expire mid-setup.** Pass `getToken` and the widget
  refreshes its token on its own; without it, the widget says the user can
  close the window and the domain still connects.
- **Widget analytics.** The console's Analytics page (and
  `GET /v1/analytics/connect`) shows where customers drop off in the connect
  flow, by DNS provider and by root versus subdomain.
- **Point domains at your own infrastructure.** A connection target
  (`PUT /v1/applications/{id}/connect-target`) sends customer domains to your
  own hostname and addresses on every plan. See
  [Where domains point](/docs/connect-flow/routing).
- **Least-privilege widget tokens.** Tokens now carry a scope; the default
  `connect` scope runs the connect flow and nothing else. See
  [Widget tokens](/docs/authentication/widget-tokens#scopes).
- **A simpler console.** New accounts get a short welcome, a tour and a setup
  checklist. The navigation now centers on domains, analytics, the widget,
  the API and routing; everything else is a feature you switch on in
  Settings.
- **Re-check is honest on live domains.** A re-check on a domain connected
  from the console or the widget verified an empty record set and reported
  drift on a healthy domain; it now verifies the domain's actual records. The
  connect flow also shows the right refusal for a hosting platform's
  subdomain (`www.name.vercel.app`) instead of "register it at your
  registrar", and GoDaddy's one-click status reads "hasn't onboarded our
  template" rather than "not offered".
- **Wix, Hover, Bluehost and friends are named.** A domain at a
  manual-only host is identified from its nameservers and shown with that
  provider's DNS panel link, instead of "we couldn't detect your DNS host".
- **Domain-purchase orders are listable and stale quotes expire.** `GET
  /v1/sell/orders` returns your application's orders; unpaid quotes older
  than a day become `expired` (with `purchase.confirmation.expired`).
- **"Unregistered" only when it's true.** The pre-flight reports
  `registered: false` only on an NXDOMAIN answer; a transient resolver failure
  omits the field and reports `detection_error: resolver` instead.
- **Webhooks say why.** `connection.failed` (and any lifecycle event on a
  connection with a recorded diagnosis) now carries `error_code` and
  `error_message`. Connections also expose `retried_at`.
- **Widget tells the host why it fell back.** A new `customdomain:fallback`
  event carries the reason (no sign-in or one-click at this provider, too
  many conflicting records, unsupported or unknown provider) and the message
  the user saw.
- **Widget recovers a failed connection in place.** The records stay on
  screen with the reason; *I've added them, verify* re-enters verification
  (`:recheck`). Re-sending an identical record set after a write returns 200.
  A stalled connection keeps its real diagnosis instead of a generic one.
- **`www` works with the root redirect.** A root connection with
  `www_redirect` now serves `www.<root>` too (the edge redirects the root
  there); previously `www` was refused at the edge and never got a
  certificate.
- **Rail truth on the pre-flight.** `POST /v1/domains:check` now returns
  `rails` (per rail: available, and one machine reason when not), the server's
  `recommended_rail`, `end_user_automatic`, a `blocked_reason` for domains no
  rail can connect, a `dashboard_url` into the provider's DNS panel, and the
  observed `nameservers`. One-click setup is advertised only where the
  provider is measured to serve our template (never merely because it
  answered discovery), and `domainconnect:start` refuses what the check did
  not advertise, naming the provider. Hosting-platform subdomains
  (`*.vercel.app` and friends) are refused on create with `platform_subdomain`
  instead of waiting for DNS that can never appear. The console shows "What
  works at GoDaddy" from this block and links to the DNS panel; the widget
  explains *why* one-click isn't available and offers the panel link on the
  manual screen; the SDK exposes the same fields in camelCase.
- **Clearer setup, honest by provider.** The connect flow now shows what your
  DNS provider can actually do before you choose a path, explains provider
  errors in plain words, never pretends one-click setup worked before you
  approved it, and offers "Check now" plus a fallback after a few minutes of
  waiting. A domain that's live but shows nothing tells you to set where it
  points. The overview explains the three ways to use CustomDomain™ (your own
  domain · your customers' domains via the widget · API/agents).
- **Email-only domains are never served.** Connections whose records are only
  mail (MX/SPF/DKIM) can't be approved at the edge; a domain pointed at us
  before it's active gets a clear page instead of a raw error.
- **Late DNS no longer fails a connection.** A `pending` connection now waits
  as long as it takes (re-checked every six hours after the first three days)
  and connects the moment the records appear. If your domain already points at
  us when a connection had failed, real traffic re-enters it into verification
  automatically. Retrying a domain resumes the existing connection instead of
  creating a duplicate, and **Finish setup** now works on failed connections.
- **Honest pre-flight.** The connect flow refuses domains that don't resolve
  (unregistered / undelegated) and hosting-platform subdomains (`*.vercel.app`
  and friends) with an explanation, instead of parking them on "waiting for DNS".
- **Root domains on GoDaddy / Namecheap / Name.com** show the A records to add
  (those panels have no ALIAS type); the docs now say plainly which providers
  connect automatically and which are manual.
- **Sign-up recovery.** *Check your email* has a **Resend the link** button and
  says so honestly if sending fails; an expired verification link lands on a
  page that issues a new one.
- **Route 53** accepts a session token for temporary (`ASIA…`) credentials.
- **Clearer errors.** A DNS-provider write that fails is reported as a 422
  `dns_write_failed` with the provider's reason, not a 503.
- **Tenant-scoped connection webhooks**: connection lifecycle envelopes now
  include the optional `user_id` echoed from the connection's `end_user_ref`,
  allowing integrators to associate events with the originating tenant or end
  user. Connections created without an `end_user_ref` continue to omit it.
- **Integrator-supplied record sets**: `PUT /v1/connections/{id}/records`
  replaces a connection's desired records with a set the integrator authored, for
  records no template can derive (Amazon SES mints three Easy-DKIM CNAMEs per
  domain). Server-to-server only, and the one-click template rail refuses such a
  connection. See [Create a connection](/docs/connect-flow/create-a-connection#supplying-your-own-records).
- **Money-safe domain buying**: embedded checkout that authorizes the card,
  registers the domain server-side (webhook-driven), and captures only after a
  successful registration; purchased domains land in the console pre-connected.
  See [Buying a domain](/docs/sell/buying-a-domain).
- **Hosted MCP server live**: `https://mcp.customdomain.ai/mcp` (Streamable
  HTTP) with eleven agent tools, plus a console **MCP server** page under
  *Integrate* with credentials and client configs.
- **One-click setup template catalog live upstream**: the full customdomain.ai
  template catalog (apex A/AAAA/CNAME/www, subdomain, www, wildcard, verify,
  connect-verified, CAA, and the email set) is merged into the provider-hosted
  one-click protocol's upstream template registry, and prod embeds the shipped
  catalog.
- **One-click sync rail live at registry-mirroring DNS providers**: apply URLs
  are RS256-signed with the `_dck1` selector (pubkey published at
  `_dck1.customdomain.ai`) and a conformance CI gate keeps the catalog valid.
  Providers that mirror the public template registry serve the catalog today
  (measured 2026-07-28: NameSilo and Glauca Digital serve all 18 templates,
  Domain Chief 16 of 18), and the rail is offered per-provider via the
  `DC_SYNC_PROVIDERS` allowlist. Providers that hand-curate their template sets
  (GoDaddy, IONOS, Cloudflare) require direct onboarding, which has not
  completed. For domains hosted there the widget offers the API-key and manual
  paths, plus one-click OAuth where the provider runs an OAuth rail (Cloudflare
  does; GoDaddy and IONOS do not). See
  [Setup types & the ask gate](/docs/concepts/ownership-and-setup-types).
- **Share links**: forward a connect flow to a colleague with a link that carries
  a 30-day expiry; expired share tokens return `404`.
- **Frontend overhaul**: the console gained a shared component library, dark mode,
  a `⌘K` command palette, and a mobile-friendly layout.
- **Shop-style domain search**: buying-domain search now groups results into the
  exact name, other TLDs (`.com .net .org .io .co .ai .app .dev .xyz .me`), and
  close name variants. See [Buying a domain](/docs/sell/buying-a-domain#shop-style-search).
- **Opt-in credential reuse**: you can optionally save a provider API key
  (encrypted at rest, per tenant + provider) to reuse it for other domains in one
  click, and revoke it any time under **Settings → Connected provider accounts**.
  Off by default; the plaintext never leaves the server. See
  [Provider setup](/docs/dns/provider-setup#remembering-a-key-optional).
- **Bulk connect**: after providing a provider key, connect the other domains on
  that account (all or a subset) in one step, with per-domain status. Supported
  for Cloudflare, GoDaddy, Route 53, and Namecheap. See
  [Bulk connect](/docs/connect-flow/verify-and-go-live#bulk-connect-more-domains-on-one-account).
- **Server-enforced roles**: the role → permission matrix is now enforced at the
  control-plane, not just the console: API-key minting and member/role changes
  require admin or owner, billing requires owner. See
  [Roles & permissions](/docs/security/overview#roles--permissions).
- **Per-provider credential fields**: the console's connect flow collects API
  credentials as separate labeled fields (with links to each provider's
  credential portal and numbered steps) instead of a colon-joined paste; used
  once and discarded by default, unless you opt in to remembering a key.
- **Resumable setup**: the Domains list's **Finish setup** reopens an abandoned
  guided connect flow at the right step.
- **Four connect rails**: OAuth into the DNS provider (flagship), provider-hosted
  one-click setup (sync + async), BYO API-token apply, and guided-manual, all
  converging on the same `pending → propagating → live` lifecycle.
- **Broad DNS auto-write fleet**: 38 built-in provider adapters (Cloudflare,
  Route 53, Google Cloud DNS, Azure DNS, GoDaddy, Namecheap, and many more) plus a
  full parity census that routes ~63 target providers to their working mode, and
  one-click setup for tokenless applies.
- **Embeddable widget/SDK**: `customdomain-js`, `window.customdomain`, the
  `customdomain:*` events, ~90-token white-label theming, and embedded mode.
- **Signed webhooks**: HMAC-SHA256 deliveries with a replay window, retries, and
  a delivery log at `GET /v1/webhook-deliveries`.
- **Billing & metering**: a Stripe-backed plan catalog with metered domain
  usage and overage on the Growth tier.
- **This documentation site**: a proper information architecture with a
  generated, always-in-sync API reference (see
  [how it stays in sync](/docs/api-reference#keeping-this-in-sync)).
