Authenticated requests send `Authorization: Bearer <token>`. Four credential
types share the surface, each with a different blast radius.

## API keys (tenant)

- Prefix `cd_live_` (production) or `cd_test_` (staging and development),
  followed by 32 lowercase hex characters, sent as
  `Authorization: Bearer cd_live_…`.
- **Keys created before the switch to `cd_` start with `sk_live_` /
  `sk_test_`, and they keep working everywhere** with the same tenant scope
  and role as before. There is no need to replace them; every new key is issued
  as `cd_live_` or `cd_test_`.
- **The prefix is not the mode.** A `cd_test_` key is made for a staging or
  development environment and works on real domains. A key is a
  [test mode](/docs/guides/test-mode) key only when its application was made with
  `"sandbox": true`; read that field from `GET /v1/applications`.
- Stored only as a hash; the full key is shown **once**, at creation.
- **The default key is the exception you can view any time.** Every workspace has one, labelled
  `Default key`, made with the workspace (or the first time an owner or admin opens the **API & SDK**
  page in a workspace that is older than it), with no card needed. It is an ordinary key with full workspace access. An owner or
  admin sees it at the top of **API & SDK** as `CUSTOMDOMAIN_API_KEY=cd_live_…`, masked; the eye
  shows it for 30 seconds and **Copy** copies it without showing it. Other members see only its
  prefix. The control plane still keeps only its hash: the console keeps a copy sealed with its own
  secret (AES-256-GCM), and every view is recorded in the audit log, without the key; a view the
  audit log cannot record is refused.
  **Rotate** makes a new default key and the old one stops working at once; your other keys are
  untouched. If someone revokes it in the list, the page says **Default key revoked** and offers
  **Make a new default key**. When a default key is still active but this page holds no copy of it,
  **Make a new default key** asks first, because the old key stops working at once.
  In the key list of an application it is flagged `is_default: true`.
- **Tenant-scoped**: an API key only ever reaches its own tenant's applications,
  connections, webhooks, and billing. Anything outside that tenant is a `404`.
- **How much authority it carries inside the tenant depends on the key.** There
  are two kinds:
  - A **plain tenant key** (the one minted at provisioning, or minted by an
    operator) has no member attached and acts with **owner** authority. This is
    the key the console seals and proxies with, and the one most API
    integrations use.
  - A **member-scoped key**, minted for an invited member when they accept, is
    tied to that member and is gated by **their current role**, resolved
    server-side on every request. A `viewer`'s key can read but **cannot
    mutate**: it is refused with `403` on connection, SSL, Power, webhook,
    member, key and billing mutations. Demote or remove the member and the next
    request already reflects it; a key whose member no longer exists is denied
    everything.
- Revocable; a revoked key stops authenticating on its next request. Removing a
  member revokes their member-scoped key.
- **Every application in the tenant.** A key belongs to one application, but it
  reads and acts on a connection of any application in its tenant: detail,
  records, diagnose, recheck, the apply rails (API token, provider sign-in,
  one-click setup, the Route 53 access role), managed mode, SSL, Power and
  disconnect. Calls whose answer depends on the application take an
  `application_id` of the key's tenant, defaulting to the key's own:
  `POST /v1/connections`, `POST /v1/domains:check` and
  `POST /v1/sharing/connect`.
- **A test mode key is the exception.** A key of a [test mode](/docs/guides/test-mode)
  application is pinned to that application. It runs the connect flow for it and reads
  its webhooks, and every other route, and every other application of the tenant, is
  refused or answers as if it were someone else's. `403 sandbox_not_allowed` names what
  it cannot do.

In the console, create and revoke keys on the **API & SDK** page. Creating a key
(any key besides the default key) needs `admin` or `owner` and a card on file (the 14 day free trial; nothing is
charged until it ends): a workspace that has not started it gets
`402 billing_required` and is sent to **Billing**.

The key the console itself uses to reach your workspace is marked **This console**
in the list and has no **Revoke** button; revoking it would cut the console off
from the workspace, so the console refuses it (`409 console_key`). A teammate's
key carries a **Team member** badge, and its revoke dialog warns that their
console may lose access.

Manage keys under an application:

```
POST   /v1/applications/{id}/keys           # create (key returned once)
GET    /v1/applications/{id}/keys           # list (metadata only, never the secret)
DELETE /v1/applications/{id}/keys/{keyId}   # revoke
```

Deleting an application (`DELETE /v1/applications/{id}`, admin and above)
revokes its keys. It is refused for the tenant's default application, for the
application the calling key belongs to, and while the application still has
domains.

Each application also has a `client_secret` (`sk_` plus 32 hex characters),
returned once at application creation over the API, or from `tenants:provision`.
The `client_secret` is **not** an API key: its only job is to mint
[widget JWTs](/docs/authentication/widget-tokens), and an API key placed in the
`client_secret` field is refused with `401`. An application created in the
console never shows its client secret; the console keeps it sealed and mints
tokens for you when you call `POST https://app.customdomain.ai/api/widget-token`
with an API key. See
[Widget tokens](/docs/authentication/widget-tokens) for which path applies.

## Widget JWTs (browser)

Short-lived JWTs minted server-side, with an API key through the console's
`/api/widget-token` or with the application's client secret through
`POST /v1/tokens`. Scoped to one application and, optionally, one domain. They authorize only the browser-facing
Connect endpoints. This is the only credential that ever reaches the browser;
see [Widget tokens](/docs/authentication/widget-tokens).

## Agent tokens (delegated)

When a person approves an AI agent, the agent receives a delegated **agent
token** instead of a key. It is an **ES256** JWT signed by the control plane and
valid for **15 minutes**. The agent renews it with a **rotating refresh token**:
every refresh returns a new refresh token and retires the old one, and a retired
token presented again later revokes the grant (see
[The OAuth flow](/docs/agents/oauth-flow#refresh) for the one exception). A token
carries:

- **Scopes** the person approved: `domains:read`, `domains:connect`,
  `domains:disconnect` and `domains:purchase`. A call that needs a scope the grant
  lacks is refused.
- **An application binding.** A grant acts within one application and cannot
  read another application's connections.
- **An audience**: the MCP endpoint by default, or the API origin when the client
  asks. The MCP refuses a token issued for anything else.
- **The workspace and the member who approved it**, so access is always delegated
  from a person and revocable by them.

An agent token works at the [MCP server](/docs/mcp/overview), which verifies it
locally against the JWKS, and on the connection and order routes the MCP tools
call. It cannot manage keys, members, billing or webhooks; the one billing route
it reaches is the read only standing. Revoke the grant and its tokens stop
working within one token lifetime. See
[Agent access](/docs/agents/overview) and [The OAuth flow](/docs/agents/oauth-flow).

## Management & provision secrets (operator)

- The **management key** gates operator provisioning (`POST /v1/tenants`,
  `GET /v1/tenants/{id}`) and cross-tenant reads (e.g. the full audit log). In
  production the control-plane refuses to start these routes open.
- The **provision secret** gates `POST /v1/tenants:provision` (one-call
  signup) and the workspace default key routes
  (`POST /v1/tenants/{tenant_id}/default-key` and its `:rotate` verb), sent as
  `X-Provision-Secret` (or a Bearer token). The customer console's server holds
  this narrow secret instead of the management key. A missing and a wrong secret
  get the same `401`. The console reaches the default key routes on the internal
  network only: the public API refuses them, and they refuse every caller when no
  provision secret is configured.

## Member roles

Human access is governed by tenant **membership**, not per-key scopes. A member
has a role (`owner`, `admin`, `member`, or `viewer`), invited and managed via
`POST /v1/members`, `PATCH /v1/members/{id}`, and `POST /v1/members:accept`. The
role/permission matrix is served as static reference at `GET /v1/rbac`.

Roles are **enforced at the control-plane**, not just the console: each sensitive
mutation resolves the acting member from the presented credential and re-checks
their role server-side; no client-supplied role is trusted. Managing members,
minting/revoking API keys and approving/revoking delegated-agent grants
(`agent:manage`) require `admin` or `owner`; billing requires `admin` or `owner`; and only
an owner can create or demote an owner.

Mutating a **connection** (creating, applying, re-applying, re-checking or
deleting one, disabling its managed grant, provisioning/renewing/importing or
deprovisioning **SSL**, changing **Power**, or registering/deleting a
**webhook**) requires `app:write`, which `member` and above hold and `viewer`
does not. See
[Roles & permissions](/docs/security/overview#roles--permissions) for the full
matrix and the exact route list.

## Unauthenticated surfaces

- `GET /healthz`: liveness + database readiness. No secrets, no tenant data.
- `POST /internal/ask`: the edge host-authorization gate. Not bearer-auth: it
  uses a shared secret (`X-Edge-Auth` / `EDGE_ASK_SECRET`) and must be
  network-isolated to the edge in production. It answers only `{ approved }`.
- `GET /v1/connect/oauth/callback`: the OAuth redirect target, authenticated by
  its signed single-use `state` rather than a bearer token.

Public catalog reads (`GET /v1/providers`, `/v1/plans`, `/v1/rbac`,
`/v1/templates`) require no credential.
