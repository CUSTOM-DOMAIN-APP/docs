Authenticated requests send `Authorization: Bearer <token>`. Three credential
types share the surface, each with a different blast radius.

## API keys (tenant)

- Prefix `cd_live_` (production) or `cd_test_` (staging and development),
  followed by 32 lowercase hex characters, sent as
  `Authorization: Bearer cd_live_…`.
- **Keys created before the switch to `cd_` start with `sk_live_` /
  `sk_test_`, and they keep working everywhere** with the same tenant scope
  and role as before. There is no need to replace them; every new key is issued
  as `cd_live_` or `cd_test_`.
- Stored only as a hash — the full key is shown **once**, at creation.
- **Tenant-scoped**: an API key only ever reaches its own tenant's applications,
  connections, webhooks, and billing. Anything outside that tenant is a `404`.
- **How much authority it carries inside the tenant depends on the key.** There
  are two kinds:
  - A **plain tenant key** (the one minted at provisioning, or minted by an
    operator) has no member attached and acts with **owner** authority. This is
    the key the console seals and proxies with, and the one most API
    integrations use.
  - A **member-scoped key**, minted for an invited member when they accept, is
    tied to that member and is gated by **their current role**, resolved
    server-side on every request. A `viewer`'s key can read but **cannot
    mutate**: it is refused with `403` on connection, SSL, Power, webhook,
    member, key and billing mutations. Demote or remove the member and the next
    request already reflects it; a key whose member no longer exists is denied
    everything.
- Revocable; a revoked key stops authenticating on its next request. Removing a
  member revokes their member-scoped key.

Manage keys under an application:

```
POST   /v1/applications/{id}/keys           # create (key returned once)
GET    /v1/applications/{id}/keys           # list (metadata only, never the secret)
DELETE /v1/applications/{id}/keys/{keyId}   # revoke
```

Each application also has a `client_secret` (returned once at application
creation, or from `tenants:provision`). The `client_secret` is **not** an API
key — its only job is to mint [widget JWTs](/docs/authentication/widget-tokens).

## Widget JWTs (browser)

Short-lived JWTs minted server-side via `POST /v1/tokens`. Scoped to one
application and, optionally, one domain. They authorize only the browser-facing
Connect endpoints. This is the only credential that ever reaches the browser —
see [Widget tokens](/docs/authentication/widget-tokens).

## Management & provision secrets (operator)

- The **management key** gates operator provisioning (`POST /v1/tenants`,
  `GET /v1/tenants/{id}`) and cross-tenant reads (e.g. the full audit log). In
  production the control-plane refuses to start these routes open.
- The **provision secret** gates only `POST /v1/tenants:provision` (one-call
  signup), sent as `X-Provision-Secret` (or a Bearer token). The customer
  console's server holds this narrow secret instead of the management key.

## Member roles

Human access is governed by tenant **membership**, not per-key scopes. A member
has a role — `owner`, `admin`, `member`, or `viewer` — invited and managed via
`POST /v1/members`, `PATCH /v1/members/{id}`, and `POST /v1/members:accept`. The
role/permission matrix is served as static reference at `GET /v1/rbac`.

Roles are **enforced at the control-plane**, not just the console: each sensitive
mutation resolves the acting member from the presented credential and re-checks
their role server-side; no client-supplied role is trusted. Managing members,
minting/revoking API keys and approving/revoking delegated-agent grants
(`agent:manage`) require `admin` or `owner`; billing requires `owner`; and only
an owner can create or demote an owner.

Mutating a **connection** (creating, applying, re-applying, re-checking or
deleting one, disabling its managed grant, provisioning/renewing/importing or
deprovisioning **SSL**, changing **Power**, or registering/deleting a
**webhook**) requires `app:write`, which `member` and above hold and `viewer`
does not. See
[Roles & permissions](/docs/security/overview#roles--permissions) for the full
matrix and the exact route list.

## Unauthenticated surfaces

- `GET /healthz` — liveness + database readiness. No secrets, no tenant data.
- `POST /internal/ask` — the edge host-authorization gate. Not bearer-auth: it
  uses a shared secret (`X-Edge-Auth` / `EDGE_ASK_SECRET`) and must be
  network-isolated to the edge in production. It answers only `{ approved }`.
- `GET /v1/connect/oauth/callback` — the OAuth redirect target, authenticated by
  its signed single-use `state` rather than a bearer token.

Public catalog reads (`GET /v1/providers`, `/v1/plans`, `/v1/rbac`,
`/v1/templates`) require no credential.
