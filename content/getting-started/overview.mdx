CustomDomain™ is one product with four front doors. The model underneath is
the same everywhere: **a workspace has applications; an application owns
connections (and its origin, keys and webhooks); a connection is one domain
moving `pending → propagating → live`; live means the edge terminates TLS
and proxies the domain to the application's origin.**

| You are… | Use | Start |
| --- | --- | --- |
| Pointing **your own** domain at your app | the **console** | [Console](/docs/getting-started/console) (no code) |
| A product that provisions domains for customers **server-to-server** | the **API** (`/v1`, `cd_` API key) | [API](/docs/getting-started/api) |
| A product whose customers connect **their** domains inside **your** UI | the **widget** (`customdomain-js`) | [Widget](/docs/getting-started/widget) |
| An AI agent or MCP client | the **MCP server** (`mcp.customdomain.ai`) | [MCP](/docs/getting-started/mcp) |
| Running the stack yourself | Docker Compose | [Self-hosted quickstart](/docs/getting-started/quickstart) |

## Shared truths

These hold on every path. If a screen or a response seems to contradict one
of them, that is a bug. Tell us.

- **Four statuses.** `pending` (records not yet seen), `propagating` (a rail
  wrote them, we are watching DNS), `live`, `failed`.
- **`pending` has no deadline.** Checks run every five seconds at first and
  back off to every 15 minutes; after 72 hours the connection stays `pending`
  with `error_code: setup_incomplete` and is re-checked every six hours,
  forever. It goes live the moment the records appear.
- **Records written for the user usually verify in seconds.** A rail's write
  is checked at once, and when public resolvers still hold an old answer we
  ask the zone's own nameservers.
- **`propagating` fails after 24 hours** (`error_code: propagation_timeout`):
  records were written but never resolved. Usually a wrong value or a
  Cloudflare proxy (orange cloud) in the way.
- **`failed` is not terminal.** *Resume* / `:recheck` revives it; re-creating
  the same domain revives it (`200`); real traffic at the edge revives it.
- **The diagnosis is on the connection**: `error_code` and `error_message` on
  `GET /v1/connections/{id}`, on every list, and on the webhook events.
- **HTTPS only after `live`.** The certificate issues on the first request
  once the connection is live; a domain pointed at us before that gets a
  clear "not active yet" page, never a raw error.
- **Root domains work everywhere**, but the record differs by provider
  (ALIAS/flattened CNAME vs `A` records); see [Root domains](/docs/dns/root-domains).
- **"Automatic" means an adapter exists**, not "the user types nothing". Read
  `rails` / `recommended_rail` / `end_user_automatic` on the pre-flight (see
  [Rail truth](/docs/concepts/ownership-and-setup-types#rail-truth-what-to-actually-tell-the-user)).
- **Drift monitoring** watches live connections hourly; alerts are not
  delivered on the hosted service yet.

## Which credential do I have?

| You got it from | It is | Use it for |
| --- | --- | --- |
| The console → **API & SDK** → **Create key** | a `cd_live_…` / `cd_test_…` API key (tenant-scoped; keys created earlier start `sk_` and still work). Shown once. Needs a card on file (14 day free trial) | server-to-server API calls, the MCP server, and minting widget tokens through `POST https://app.customdomain.ai/api/widget-token` |
| `POST /v1/applications` (an application created over the API) | the application's **client secret** (`sk_…`, shown once in that response). A console signup never shows one | minting widget tokens from your server with `POST /v1/tokens` |
| A widget token endpoint (above) | a short-lived **widget JWT** (one application, optionally one domain, optionally one end user) | the browser: `customdomain-js` `open({ token })`, or direct `/v1` calls from the page |
| An agent grant | a delegated **agent token** | the agent's scoped API calls |

Most customers sign up in the console, so they hold an API key and mint widget
tokens through `/api/widget-token`; the client secret path is for applications
created over the API. An API key is not a client secret and the two are not
interchangeable. See [Widget tokens](/docs/authentication/widget-tokens).

A widget JWT can never mint another token, never read another application's
data, and never choose the records we write. Anything that chooses records
requires an API key.
