title: Self-hosted quickstart
description: "Run CustomDomain™ locally with Docker Compose, then provision a tenant, mint a widget token, detect a domain and create and apply a connection through the API."
---

This walks the **API** against a **local** stack. On the hosted service, start
from the [Which path are you on?](/docs/getting-started/overview) page. The
[API](/docs/getting-started/api), [widget](/docs/getting-started/widget),
[console](/docs/getting-started/console) and [MCP](/docs/getting-started/mcp)
pages cover each path with hosted URLs.

## 0. Run the stack (local)

```bash
make up   # docker compose: Postgres + control-plane + edge
```

The local control-plane listens on `http://localhost:8080`. In production you
talk to the hosted control-plane at `https://api.customdomain.ai` instead;
the calls below are identical apart from the base URL.

## 1. Provision a tenant, app, and key

One call creates a tenant, its owner, a default application, and a long-lived API
key. It's guarded by the provision secret (`X-Provision-Secret`; in local dev the
management/provision secrets may be unset).

```bash
curl -X POST http://localhost:8080/v1/tenants:provision \
  -H "X-Provision-Secret: <PROVISION_SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"tenant_name":"Acme","app_name":"Acme Sites","owner_email":"you@acme.example"}'
# → { "tenant_id": "...", "application_id": "...", "api_key": "cd_live_...", "client_secret": "..." }
```

`api_key` (`cd_live_` plus 32 hex characters) and `client_secret` (`sk_` plus 32
hex characters) are different credentials, and both are shown **once**. Store
them. (You can also
create tenants and applications individually via `POST /v1/tenants` and
`POST /v1/applications` with the management key.)

## 2. Mint a widget token

Trade the app's `client_secret` for a short-lived widget JWT (server-side only).
This works because step 1 created the application over the API, so you hold its
secret. An account that signed up in the console never sees one; it mints with an
API key through `POST https://app.customdomain.ai/api/widget-token` instead (see
[Widget tokens](/docs/authentication/widget-tokens)).

```bash
curl -X POST http://localhost:8080/v1/tokens \
  -H "Content-Type: application/json" \
  -d '{"application_id":"<APP_ID>","client_secret":"<CLIENT_SECRET>","domain":"app.customer.com"}'
# → { "token": "eyJ...", "token_type": "Bearer", "expires_in": 900, "scope": "connect" }
```

## 3. Detect the domain

```bash
curl -X POST http://localhost:8080/v1/domains:check \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"domain":"app.customer.com"}'
```

The response tells you which rails can run for this domain and why not when
they can't (`rails`), the server's pick (`recommended_rail`), whether that pick
needs nothing typed by the end user (`end_user_automatic`), capability flags,
any `record_conflicts`, and a `blocked_reason` when the domain can't be
connected at all. See [Rail truth](/docs/concepts/ownership-and-setup-types#rail-truth-what-to-actually-tell-the-user).

## 4. Create a connection

```bash
curl -X POST http://localhost:8080/v1/connections \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"domain":"app.customer.com"}'
```

The response carries the connection `id` (also the `jobId`), its `status`
(`pending`), and the authoritative desired `records` (by default a
`CNAME app.customer.com → edge.customdomain.ai`).

## 5. Apply the records

Pick a [rail](/docs/connect-flow/overview#the-four-rails). The manual path needs
nothing more than the customer adding the records above. To write them
programmatically with a scoped provider token (Rail B):

```bash
curl -X POST http://localhost:8080/v1/connections/<ID>/apply \
  -H "Authorization: Bearer <WIDGET_JWT>" \
  -H "Content-Type: application/json" \
  -d '{"provider":"cloudflare","zone":"customer.com","credential":{"token":"<scoped>"},
       "records":[{"type":"CNAME","host":"app","value":"edge.customdomain.ai"}]}'
```

The connection moves to `propagating`. (Rail C is `oauth:start`, Rail A is
`domainconnect:start`; see [Apply records & go live](/docs/connect-flow/verify-and-go-live).)

## 6. Go live

The background poller (running automatically) promotes the connection to `live`
once every desired record resolves. Watch it:

```bash
curl http://localhost:8080/v1/connections/<ID> -H "Authorization: Bearer <WIDGET_JWT>"
```

When `status` is `live`, the edge issues the TLS certificate on the next
handshake and proxies `https://app.customer.com` to your origin. Register a
[webhook](/docs/webhooks/overview) for `connection.live` to be notified.
